# 내전 기록·평가·팀 추천 서비스 명세

이 문서는 서비스가 따라야 할 현재 제품·설계 기준이다. 약 30명의 친구가 진행한 리그 오브 레전드(LoL) 내전을 참가자 한 명이 등록하고, 누구나 전적·활약 순위·누적 랭킹을 보며 경기 전 팀을 추천받도록 한다. 운영자가 경기에 참여하지 않아도 기록할 수 있고, 사람이 내전으로 확인한 경기만 집계하는 것이 핵심이다.

기준일은 2026-10-24다. 2026-10-21에 승인한 [기획](superpowers/specs/2026-10-21-lol-inhouse-design.md)과 [개발 계획](superpowers/plans/2026-10-21-lol-inhouse-development-plan.md)에 이후 결정을 반영했다. 목표물 공격 지표는 같은 날 확정한 [D24](superpowers/decisions/2026-10-22-overnight-decisions.md#d24--2026-10-24-목표물-공격-평가-기준-사용자-확정)를 따른다. 이 문서에 규칙이 있다는 사실은 해당 구현이나 실제 환경 검증이 완료됐다는 뜻이 아니다.

## 문서의 역할과 결정 상태

제품 동작과 계산·저장 원칙은 이 문서에서 관리한다. 프로그램 간 데이터 형식·요청 주소·오류 응답은 [API 계약](contracts/api.md), 설치·실행 명령과 개발 도구는 [개발 환경 안내](development/setup.md), 구현·검증 상태와 남은 작업·제외한 수용 조건은 [진행 상태](status.md)에서 관리한다. API는 프로그램끼리 자료를 주고받는 접점을 뜻한다. 결정의 대안·장단점·선택 이유·재검토 조건은 연결한 결정 기록에 보존한다.

LCU(League Client API)는 롤 클라이언트가 로컬 PC에 제공하는 데이터 접근 기능이며 Riot 공식 API와는 별도 경로다. JSON은 항목 이름과 값으로 자료를 표현하는 형식이다.

## 제품 범위와 사용자

대상은 사전 등록된 친구 10명이 소환사의 협곡에서 진행한 일반적인 5대5 사용자 설정 경기다. 경기마다 참가자는 달라질 수 있다. 초기 운영 규모는 약 30명, 모임 전체 경기 빈도는 2주에 3–6경기 정도를 전제로 한다. 각 팀은 탑·정글·미드·원딜·서포터 한 명씩이며, 실제 포지션은 경기 등록 때 확인한다.

개발 환경은 macOS, 일반 사용자용 수집 프로그램의 지원 환경은 Windows다. 집의 Windows 데스크탑에서 Docker로 서버를 운영하고 Cloudflare Tunnel로 외부 접속을 제공한다. Docker는 실행 환경을 묶어 배포하는 도구이며, Tunnel은 집 서버가 외부로 연결해 웹 접속을 중계받는 방식이다. 기존 장비를 활용해 유지 비용을 줄이는 방향이다.

| 사용자 | 허용하는 작업 |
| --- | --- |
| 일반 방문자 | 로그인 없이 등록된 전적·통계·랭킹 조회, 등록 참가자 10명으로 팀 추천 요청 |
| 인증된 수집자 | 자신이 참가한 적격 경기 수집·임시 저장·내전 여부와 실제 포지션 확인·등록 |
| 운영자 한 명 | 참가자와 포지션·초기 실력 관리, 코드 발급·폐기, 인증 폐기, 등록 후 포지션 정정·등록 취소, 평가 기준·재계산 관리와 변경 이력 조회 |

여러 기기·브라우저에서 운영자를 인증해도 운영자는 한 명이다. 수집자는 등록 완료 경기의 포지션을 바꾸거나 등록을 취소할 수 없다. 서버는 각 요청의 권한을 최종 확인한다. 전적 공개 동의는 친구별로 서면 확보하며, 온라인 동의 요청·화면은 만들지 않는다.

## 참가자와 포지션 관리

운영자가 먼저 사람을 등록한 뒤 그 사람이 참가한 내전을 등록한다. 게스트와 여러 LoL 계정의 전적 통합은 지원하지 않는다. 사람 등록과 수집 프로그램의 기기 등록은 별개이므로 10명 모두 프로그램을 설치할 필요가 없다.

내부 참가자 식별자와 LoL 계정의 안정적인 식별값을 연결하고, 공개 표시 이름은 분리한다. PUUID는 계정을 구분하는 식별값이며 이름이 바뀌어도 같은 참가자의 과거 기록이 유지되어야 한다. 친구 목록을 조회해 사람을 찾지 않고 경기 상세의 참가자 정보를 사용한다. 비활성화된 참가자의 과거 연결·기록은 유지하고 새 팀 추천의 선택 대상에서는 제외한다.

운영자는 참가자의 주 포지션·부 포지션·추가 가능한 포지션과 팀 편성용 초기 실력값을 관리한다. 처음에는 주·부 포지션을 가능한 포지션으로 취급하고 추가 포지션은 운영자가 지정한다. 플레이 기록이 없다는 이유만으로 불가능한 포지션이라고 판단하지 않는다. 현재 프로필의 포지션 변경이 과거 경기의 실제 포지션을 바꾸지는 않는다.

### 초기 포지션 참고 자료

과거 내전과 솔로랭크는 주·부 포지션을 제안하는 참고 자료다. 시스템의 제안은 운영자가 확인·수정하며, 제안을 가져오거나 편집란에 적용하는 것만으로 회원 설정을 바꾸지 않는다. 운영자가 명시적으로 저장한 값만 변경하고 이후 수집으로 자동 덮어쓰지 않는다.

솔로랭크는 Riot 공식 API의 Account-v1과 Match-v5 경로를 사용한다. 사용자 설정 내전은 LCU로 수집한다. 두 경로에서 받은 PUUID는 별도로 다룬다. Riot ID로 공식 계정을 해석하고, 회원의 LCU 계정과 같은 사람이라는 명시적 연결 확인을 거쳐야 한다. 이름이나 두 식별값이 비슷하다는 이유로 연결하지 않는다.

위임받은 참고 표본 기준은 솔로랭크 구분값 420, 알려진 포지션, 5분 이상, 조기 종료가 아닌 경기다. 잘못된 기간·수치·계정 연결과 중복 표본을 거른다. 이 5분 조건은 솔로랭크 참고 자료에만 적용하며 내전 적격성이나 점수 기준으로 확대하지 않는다.

적격 솔로랭크와 등록된 내전 중 최근 최대 20경기의 포지션 빈도로 상위 두 포지션을 제안한다. 동률은 최근 플레이, 이어서 탑·정글·미드·원딜·서포터 순으로 정한다. 알 수 없는 포지션은 제외하며 표본이 없거나 한 포지션뿐이면 부족한 제안은 비워 둔다. 표본 수·출처·제안 이유를 함께 제공한다. 최근 20경기는 실제 기간이 일정하지 않고 오래된 주 포지션을 놓칠 수 있는 위임 선택이다. [D18](superpowers/decisions/2026-10-22-overnight-decisions.md#d18--솔로-참고-자료와-검증-범위의-정직한-handoff), [D21](superpowers/decisions/2026-10-22-overnight-decisions.md#d21--확인한-공식-계정-매핑과-남은-외부-gate)

공식 API를 사용할 수 없으면 이유와 이용 불가 상태를 알린다. 예제 자료를 실제 조회 성공으로 표시하지 않는다. 개인 검증용 키와 공개 운영용 키 승인은 구분하며, 실제 연동 상태는 [진행 상태](status.md)와 [공식 API 검증 기록](validation/riot-solo-reference.md)을 따른다.

솔로랭크 자료는 모임 경기 수·전적·활약 점수·누적 랭킹·팀 실력 보정에 넣지 않는다. 운영자가 직접 지정하는 0–100의 초기 실력도 팀 편성용으로만 사용하고, 경기에서 계산한 값과 구분해 보관한다.

## 인증과 개인정보

### 수집자 기기 인증

운영자가 참가자별 일회용 코드를 발급한다. 수집자는 최초 온라인 등록 때 코드를 입력하고, 서버는 코드 소유 회원과 현재 LCU 계정을 대조한 뒤 별도 기기 인증 정보를 발급한다. 이후 인증이 유효한 동안 반복 로그인을 요구하지 않는다. 재설치·기기 변경이나 인증 복구가 필요하면 새 코드로 재등록하며 운영자는 기존 인증을 폐기할 수 있다.

LCU의 이름·식별값 자동 인식은 서버 로그인 증명이 아니다. 코드와 연결된 회원과 현재 계정이 다르거나 수집자가 해당 경기 참가자가 아니면 이유를 안내하고 차단한다. 권한과 전송 대기의 소유자를 다른 계정으로 자동 이전하지 않는다. 이 서비스는 친구 모임의 수집 프로그램을 신뢰하는 방식이며 Riot이 서명한 경기 증명이나 Riot 소셜 로그인(RSO)을 제공하는 것은 아니다.

기기 토큰은 앱의 내부 처리 영역에서 운영체제 보호 기능으로 암호화해 별도 파일에 저장한다. 보호 기능을 사용할 수 없거나 복호화가 실패하면 재등록을 안내하며 평문 저장으로 전환하지 않는다. 화면에는 토큰·기기 인증 식별값·원본 응답을 전달하지 않는다. 이 보호가 같은 Windows 사용자 권한의 악성 프로그램까지 차단한다고 설명하지 않는다. [D15](superpowers/decisions/2026-10-22-overnight-decisions.md#d15--인증lcu렌더러-경계)

### 운영자 인증과 복구

운영자는 소셜 로그인이나 아이디·비밀번호 없이 전용 코드로 브라우저를 인증한다. 최초 코드는 서버의 로컬 관리 명령으로 발급하며, 이후 인증된 관리 화면에서도 다른 기기·브라우저용 코드를 발급할 수 있다. 코드는 사용 즉시 폐기하고 브라우저에는 별도 인증을 유지한다. 모든 브라우저 인증을 잃으면 서버에서 기존 인증을 폐기하고 새 코드를 발급해 복구한다. 일반 방문자는 코드를 발급할 수 없고 새 코드 소비로 새 운영자 계정을 만들지 않는다.

운영자·수집자 코드는 권한을 분리하고 유효기간·단일 사용을 적용한다. 브라우저 인증에는 만료·로그아웃·개별 및 전체 폐기를 제공한다. 코드·토큰은 서버에 복원할 수 없는 해시값으로 저장하고 URL·일반 로그·진단 자료에 남기지 않는다. 로컬 복구 코드는 실행자의 터미널에 한 번만 표시한다.

운영 환경은 암호화된 HTTPS 접속과 보호 쿠키를 사용한다. 비암호화 HTTP 예외는 개발·테스트 환경에서만 명시적으로 허용한다. 운영자 쓰기 요청은 같은 출처인지 확인하고 다른 사이트의 요청 위조를 막는 CSRF 토큰도 검사한다. 코드 입력 시도·요청 크기 제한을 적용한다. 코드 길이·유효기간·쿠키·만료·시도 제한의 정확한 기본값은 [인증과 권한 계약](contracts/api.md#인증과-권한), 요청 크기와 실패 처리는 [공통 형식과 오류](contracts/api.md#공통-형식과-오류)에서 관리한다.

별도 로그인 제품과 공유 제한 저장소를 두지 않아 운영 부담을 줄이는 대신, 코드 전달·복구를 직접 관리하고 재시작 때 실패 횟수가 초기화되는 비용을 받아들인다. 접속 중계 환경에서는 같은 주소로 묶일 수 있으므로 전달 주소의 신뢰 범위를 실제 운영 환경에 맞춰 정해야 한다. 다중 서버·여러 운영자나 실제 제한 문제가 생기면 [D10의 재검토 조건](superpowers/decisions/2026-10-22-overnight-decisions.md#d10--인증과-http-기본값의-명시적-운영-한계)을 적용한다.

### 공개 자료의 경계

공개 전적에는 표시용 참가자 정보와 경기 기록만 제공한다. PUUID·원본 LCU 응답·기기 인증·운영자 인증 자료는 제외한다. 인증된 수집기의 회원 명단은 참가자 매칭에 필요한 범위만 제공한다. 확인 대기 경기는 그 경기에 참가한 인증된 수집자와 운영자만 보고, 취소 경기는 운영자가 내부 확인용으로 보관한다.

## 경기 수집·확인·등록

### 사용 흐름

1. 참가자 한 명이 롤 클라이언트에 로그인된 Windows PC에서 수집기를 실행한다. 앱 시작은 계정 인식과 기존 대기 복구를 수행하며 새 경기 기록을 자동 조회하지 않는다.
2. 수집자가 ‘과거 경기 조회’를 누르면 그때 LCU에서 조회 가능한 완료 경기 목록과 상세를 가져온다. 새 조회에는 연결 가능한 롤 클라이언트가 필요하다.
3. 수집자가 참가한 적격 경기는 로컬에 안전하게 저장한 뒤 서버에 임시 저장을 요청한다. 새 자료는 ‘확인 대기’이며 공개·집계하지 않는다. 부적격 경기는 이유를 안내한다.
4. 수집기는 참가자 10명·양 팀·결과와 자동 수집 기록을 보여준다. 인증된 해당 경기 참가자가 모임 내전인지, 양 팀의 실제 포지션이 맞는지 확인한다. 임시 저장한 사람과 확인하는 사람이 달라도 된다.
5. ‘내전 등록’을 누른 명시적 요청으로만 서버의 확인 대기를 등록 완료로 한 번 전환한다. 서버에서 등록 완료를 확인한 뒤 공개·집계 대상이 된다.

수집기를 경기 전후 언제 실행하든 버튼 조회 절차는 같다. 경기 중 선행 수집이나 시작·종료 이벤트에 의존하지 않는다. LCU에서 조회할 수 없는 자료를 가져왔다고 표시하지 않으며 무제한 과거 조회나 복구 가능한 기간을 보장하지 않는다. 서버에 이미 저장한 확인 대기 경기는 LCU 목록에서 사라져도 다시 불러와 확인할 수 있다.

다음 목록 페이지가 요청한 개수 이상을 돌려주면서 앞서 읽은 경기만 반복해 새 경기 ID가 없으면 추가 페이지 조회를 중단한다. 앞서 확보한 고유 경기의 상세 조회·검증·저장은 계속하되, 더 오래된 기록을 확인하지 못했다는 경고를 표시한다. 반복 응답을 전체 기록의 끝으로 확정하지 않으며, 적격성 검사를 통과한 경기만 저장한다. 이 처리의 판단 근거는 [반복 페이지 대응 결정](superpowers/decisions/2026-10-22-overnight-decisions.md#d28--2026-10-28-반복-페이지에서-확보한-경기-처리와-조회-한계-표시)에 있다.

### 적격성과 원본 검사

- 사전 등록한 서로 다른 참가자 10명, 팀당 5명인 완료 사용자 설정 경기여야 하고 인증된 수집자가 참가해야 한다.
- 참가자 연결·팀·승패가 서로 맞고 경기 시간이 양수여야 한다. 사람은 표시 이름이나 배열 순서로 연결하지 않는다.
- 등록 때 각 팀의 탑·정글·미드·원딜·서포터가 정확히 한 명씩 확인되어야 한다. 포지션은 지정된 문자열만 받으며 숫자 순번으로 대체하지 않는다.
- 킬·피해량·골드 등 원본 수치는 자동 수집한다. 수집자가 직접 입력·편집하는 기능은 두지 않는다.
- 실제 0과 필드 누락·잘못된 형식을 구분한다. 필수 값 누락·파싱 실패·모순된 자료는 0으로 채우지 않고 등록을 막아 원인을 알린다. 빈 아이템 슬롯과 필드 부재도 구분한다.
- 서버는 수집기의 사전 검사와 별개로 원본을 다시 검사·정규화한다. 정규화는 서로 다른 원본 형식을 서비스의 공통 형식으로 바꾸는 처리다. 필요한 값이 유효하면 추가 필드가 있다는 이유만으로 거절하지 않되, JSON의 중복 항목 이름은 거절한다.
- 확인한 응답 조합만 지원한다. 다른 큐·모드·형식을 같은 뜻이라고 추정하지 않으며, 검증하지 않은 확장 지표를 필수로 삼지 않는다. 정확한 지원 조합·필수 항목·오류는 [API 계약](contracts/api.md)과 [LCU 필드 맵](validation/lcu-field-map.md)에 둔다.

탈주·접속 장애로 제대로 진행하지 못했거나 재경기로 정한 경기는 등록하지 않는다. 임시 저장되더라도 확인 대기에 남겨 공개·집계하지 않는다. 초기 서비스는 문제 경기를 자동 판정하지 않고 수집자의 등록 전 확인을 사용한다.

### 중복·동시 요청·취소

경기는 플랫폼과 경기 식별자를 합친 안정적인 키로 구분한다. 경기 식별자는 문자열로 보존해 큰 숫자가 반올림되지 않게 한다. 같은 경기 키는 확인 대기·등록 완료·등록 취소 전체에 걸쳐 데이터베이스에서 하나만 존재해야 한다.

같은 수집기의 재시도나 다른 참가자의 전송이 겹쳐도 기존 원본·상태·포지션을 덮어쓰지 않는다. 기존 상태만 응답하고 집계·변경 번호·재계산 작업도 추가하지 않는다. 동일 자료 재전송과 최초의 명시적 등록 확정은 별도 동작이다. 동시 확정에서는 첫 확정만 적용하고 이후 요청은 이미 등록된 상태를 알린다.

등록 후 실제 포지션 정정과 등록 취소는 운영자만 한다. 정정은 양 팀의 포지션 구성을 다시 검사하고 이력을 남긴다. 취소는 즉시 일반 공개에서 숨기고 모든 누적·평가·팀 실력 보정에서 제외한다. 취소된 경기의 최소 식별자와 이력은 유지한다. 수집자의 재전송으로 복원하지 않고 초기 버전에는 취소 복원 기능도 만들지 않는다. [D08](superpowers/decisions/2026-10-22-overnight-decisions.md#d08--단계-1의-작은-규모-트랜잭션-직렬화), [D11](superpowers/decisions/2026-10-22-overnight-decisions.md#d11--v1-소비자-계약과-안정적-조회)

## 오프라인 대기와 재시도

| 사용자에게 보이는 상태 | 뜻 |
| --- | --- |
| 전송 대기 | LCU에서 가져와 PC에 저장했지만 서버 임시 저장을 확인하지 못함 |
| 확인 대기 | 서버에 임시 저장했으며 아직 내전 등록을 확정하지 않음 |
| 등록 대기 | 수집자가 내전·포지션을 확인하고 등록을 요청했지만 서버 확정을 확인하지 못함 |
| 등록 완료 | 서버 등록 완료를 확인함 |
| 등록 취소 | 서버에서 취소 상태를 확인함. 자동 복원하지 않음 |
| 확인 필요 | 인증·자료·저장 문제 등 사용자나 운영자의 조치가 필요함 |

대기 자료와 사용자가 명시적으로 요청한 확정은 앱 종료·PC 재시작 후에도 남긴다. 실행 중 연결이 복구되거나 다음 실행 때 자동 재시도한다. 자료 전송 후 서버가 확인 대기임을 확인해야 등록 확정을 보내며, 조회만 하고 등록을 누르지 않은 경기의 확정 요청은 만들지 않는다. 임시 저장 성공을 등록 완료로 안내하지 않는다.

LCU 조회 실패는 서버 업로드 실패와 구분한다. 가져오지 못한 경기에는 전송 대기를 만들 수 없다. 로컬 저장 실패는 ‘전송 대기 저장 실패’로 안내하고 저장됐다고 표시하지 않는다. 이미 확보한 자료의 전송·기존 경기 확인은 롤 클라이언트가 꺼져 있어도 원래 권한으로 할 수 있고, 전송 복구 때문에 새 LCU 조회를 시작하지 않는다. 다만 다른 LCU 계정이 확인되면 차단한다.

위임받은 대기열 정책은 다음과 같다. [D16](superpowers/decisions/2026-10-22-overnight-decisions.md#d16--로컬-원본소유자순서-보존), [D17](superpowers/decisions/2026-10-22-overnight-decisions.md#d17--느린-서버꺼진-league와-명시적-사용자-확인)

- 같은 회원·경기·요청 종류의 미완료 요청은 하나로 합친다. 재조회가 확인한 포지션·초안·확정 대기를 덮어쓰지 않는다. 등록 완료 표시에서는 서버가 확정한 포지션을 우선한다.
- 대기열 전체에서 먼저 들어온 작업부터 하나씩 전송한다. 선두가 재시도를 기다리면 뒤의 독립 경기까지 기다리는 비용을 받아들인다. 강제 종료 때 전송 중이던 작업도 다음 실행에 복구한다.
- 네트워크·서버 오류는 5초 → 15초 → 1분 → 5분 → 최대 15분 간격으로, 상한 안의 무작위 지연을 더해 재시도한다. 과다 요청 제한 응답은 서버가 지정한 재시도 시간을 따른다.
- 인증 폐기·자료 오류·취소 등 계속 보내도 해결되지 않는 결과는 무한 재시도하지 않는다. 취소는 등록 취소로 표시하고 전송을 끝낸다.
- 원래 회원·기기 자격·계정 소유자를 보존한다. 다른 회원에게 대기를 이전하지 않는다. 같은 회원의 새 인증으로 이어 보내려면 새 인증 명단으로 회원·계정을 확인하고 사용자가 명시적으로 재개한다. 원래 소유자 기록은 바꾸지 않는다.
- 응답만 유실됐을 수 있으므로 서버 상태를 다시 확인한다. 이미 등록됐으면 완료, 취소됐으면 종료, 확인 대기면 필요한 확정만 진행한다. 성공 기록은 이후 재조회에서 서버 상태를 갱신하는 데 사용한다.
- 미완료 자료는 자동 삭제하지 않는다. 등록 완료와 전송 성공이 확인된 경기의 큰 원본만 30일 뒤 정리하고 키·상태·정규화 기록·포지션은 남긴다. 경기 자료는 로컬 SQLite 데이터베이스에 평문으로 저장하며 인증 정보는 별도 보호 파일에 둔다.

앱 창과 로컬 기록은 느린 서버 응답을 기다리지 않고 먼저 보여준다. 최초 온라인 기기 등록·회원 명단 확인 후에는 마지막 정상 명단을 캐시해 사용하고 따로 갱신한다. 오래된 명단일 수 있으므로 서버의 최종 검증은 유지한다. 순서 대기로 인한 지연·저장량·자료 보호 요구가 문제가 되면 D16·D17의 대안을 검토한다.

## 공개 전적과 통계

경기 상세는 양 팀 5명씩을 비교해 경기 일시·시간·승패와 참가자 10명의 챔피언·최종 실제 포지션·킬/데스/어시스트·피해량·받은 피해량·CS·골드·시야·아이템·활약 점수와 순위를 보여준다. CS는 미니언·정글 몬스터 처치 수다. KDA는 `(킬 + 어시스트) / 데스` 비율이며 표시용 기록이지 별도 점수 항목은 아니다.

기본 가한 피해량은 챔피언 대상 피해량이다. 목표물·포탑 피해는 구분하며 적용한 평가 기준도 확인할 수 있어야 한다. 받은 피해량과 아이템은 보여주되 자체 가산점으로 쓰지 않는다.

개인 화면은 참가 경기 목록, 경기 수·승·패·승률, 합계 킬·데스·어시스트와 KDA, 포지션별·챔피언별 기록, 누적 활약 점수·랭킹을 제공한다. 누적 KDA는 경기별 비율 평균 대신 `(총 킬 + 총 어시스트) / 총 데스`로 계산한다. 데스 합계가 0인 유효 기록은 무한대 숫자 대신 ‘Perfect’와 원래 기록을 표시한다.

경기 목록은 참가자·챔피언·포지션·승패 조건을 조합한다. 복합 조건은 같은 참가자의 기록에 적용하고 조건에 맞는 사람이 여러 명이어도 경기를 중복 표시하지 않는다. 경기 시각과 고유 키를 함께 내림차순으로 정렬해 다음 목록을 잇는다. 페이지를 넘기는 동안 취소·정정된 기록은 최신 상태를 따르며 전체 조회 시점을 고정하는 기능은 아니다. [D11](superpowers/decisions/2026-10-22-overnight-decisions.md#d11--v1-소비자-계약과-안정적-조회)

화면은 로딩·빈 자료·계산 중·서버 오류를 구분하고 키보드로 이용할 수 있어야 한다. 좁은 화면의 전적 표는 가로 스크롤을 제공한다. 챔피언·아이템 이미지를 가져오지 못하거나 오래된·새 ID의 자료가 없으면 대체 아이콘과 ID를 남기고 숫자 기록은 계속 보여준다. 이미지 자료를 점수 계산 입력으로 쓰지 않는다. [D20](superpowers/decisions/2026-10-22-overnight-decisions.md#d20--팀-열거공개-웹관리-경계)

## 경기별 활약 점수

최종 확인한 실제 포지션을 기준으로 각 경기 참가자 10명의 사후 활약을 0–100 척도로 평가한다. 딜러는 피해량·성장, 정글은 교전 관여·목표물 공격, 서포터는 시야·어시스트를 중시한다. 같은 포지션 기준으로 비교하므로 원딜과 서포터의 원시 피해량을 직접 비교하지 않는다. 승패의 비중은 작으며 패배 팀 참가자도 경기 전체 1위가 될 수 있다.

공개 점수에는 등록 완료 상태의 유효 내전만 사용한다. 확인 대기·취소 경기, 솔로랭크, 운영자 초기 실력은 제외한다. 이 값은 모임이 정한 평가이며 Riot 공식 등급이나 랭크 추정치로 표시하지 않는다.

### 같은 포지션의 지표 환산

현재 참가자의 지표를 `x`, 같은 경기 상대 포지션의 지표를 `y`라고 한다. 모두 음수가 아닌 유효한 값이어야 한다. 과거 비교 표본은 현재 계산에 사용하는 모든 유효 내전 중 같은 포지션의 참가 기록이며, **현재 경기의 양쪽 참가 기록은 모두 제외**한다. 아래 ‘과거’는 계산 자료의 다른 경기를 뜻하므로 이후 등록한 경기도 전체 재계산의 비교 표본에 들어갈 수 있다.

1. 경기 내 비교 `P`: `x + y = 0`이면 50. 그 외에는 `P = 50 + 0.5 × (100x / (x + y) − 50)`. 상대 비교만으로 극단적인 점수가 나오지 않도록 25–75 범위로 줄인다.
2. 다른 경기 비교 `H`: 같은 포지션 표본 수를 `N`, 그중 `x`보다 작은 값의 수를 `L`, 같은 값의 수를 `E`라 하면 `H = 100 × (L + 0.5E + 5) / (N + 10)`. 표본이 적을 때 중립값 쪽으로 보정한다.
3. 다른 경기 표본 비중은 `a = N / (N + 20)`이다. 최종 환산 지표는 `clamp((1 − a) × P + a × H, 5, 95)`이며, `clamp`는 5보다 작으면 5, 95보다 크면 95로 제한한다는 뜻이다.
4. 팀 전체 킬·챔피언 피해량 분모가 실제 0이면 해당 비율을 0으로 정의한다. 분모 누락은 계산 오류이며 0으로 대체하지 않는다. 모든 값이 같으면 중립 50이 된다. 모든 계산값은 유한해야 한다.

기록이 적으면 같은 경기 상대 비교를 더 많이 사용하고, 쌓이면 모임의 같은 포지션 기록 비중을 높인다. 극단적인 원시 기록도 항목 환산 상한을 넘지 않는다. 새 내전이 등록되면 비교 표본도 바뀌므로 과거 점수가 변할 수 있음을 평가 기준 설명에 표시한다. 임시 저장·중복 전송만으로는 표본과 점수를 바꾸지 않는다.

### 평가가 설명하지 못하는 기여

목표물 피해만으로 용·바론을 위한 견제·시야·강타 판단을 모두 알 수 없다. 팀의 용·바론 획득을 정글 한 사람의 공로로 그대로 가산하지 않는다. 탑의 에픽 몬스터 공격은 목표물 항목에 직접 반영하지 않는 D24의 제약을 받아들인다. 다른 지표 선택보다 공정하다는 비교 검증을 마쳤다고 주장하지 않는다.

받은 피해량이 많다는 이유로 좋은 탱킹이라 판단하지 않는다. 최종 수치만으로 좋은 희생과 불필요한 사망을 구분하기 어렵고, 같은 포지션 안의 탱커·딜러·지원형 챔피언 차이도 초기 규칙에서 완전히 보정하지 못한다. KDA와 받은 피해량은 직접 가산하지 않는다.

개인별 목표물 참여 이벤트·특정 시점의 성장 차이·아군 회복·보호막·군중 제어 등의 확장 지표는 실제 사용자 설정 경기에서 수집 안정성과 의미를 확인한 뒤 검토한다. 기본 기능을 경기 중 실시간 수집에 의존하게 바꾸지 않는다.

## 누적 랭킹과 점수 표시

시즌을 나누지 않고 등록한 전체 유효 내전을 누적한다. 참가 횟수만으로 점수를 합산해 순위를 올리지 않고, 경기별 점수 평균을 모임 평균 쪽으로 보정한다. 사용자 확정 초기 보정 강도는 `k = 5`, 즉 모임 평균 다섯 경기분이다.

`누적 점수 = (본인 경기 점수 합계 + 5 × G) / (n + 5)`

여기서 `n`은 본인의 유효 경기 수, `G`는 같은 평가 세대에서 계산한 유효 내전 참가자 점수 전체의 평균이다. 평균의 단위는 회원별 평균이 아니라 경기 참가 기록이다. 계산에는 표시 전 원래 정밀도의 경기 점수를 사용한다.

- 0경기는 점수·순위를 만들지 않는다.
- 1–2경기는 ‘평가 중’으로 표시하고 정식 누적 순위에 넣지 않는다. 개인 전적·경기별 활약 순위는 볼 수 있다.
- 3경기부터 정식 누적 순위에 넣되 평균 보정을 계속 유지하고 경기 수를 함께 표시한다.
- 취소로 3경기 미만이 되면 다시 ‘평가 중’으로 돌아간다.

경기별·누적 점수는 화면에서 소수 둘째 자리로 반올림하고 동일한 표시 점수에는 공동 순위 `1, 1, 3`을 적용한다. 같은 순위의 화면 정렬만 내부 회원 식별자로 안정화한다. 내부 누적 계산에는 반올림 전 값을 유지한다. 이 동점 표시는 위임받은 선택이다. [D19](superpowers/decisions/2026-10-22-overnight-decisions.md#d19--같은-세대의-불변-평가와-작업-시도-fencing)

## 팀 편성용 실력과 팀 추천

### 포지션별 실력 보정

공개 누적 점수와 팀 편성용 실력은 목적이 다르다. 팀 편성은 운영자의 초기 실력값에서 시작하고 실제 맡은 포지션의 등록 내전 기록이 쌓일수록 그 기록의 비중을 높인다. 위임받은 공식은 다음과 같다.

`포지션 r 실력 = (5 × 운영자 초기 실력 + r 포지션 유효 경기 점수 합) / (5 + r 포지션 경기 수)`

그 포지션 기록이 없으면 초기 실력을 그대로 쓴다. 초기값 다섯 경기분을 섞어 한 경기로 크게 흔들리는 것을 줄인다. 초기값과 산출 실력을 구분해 보관하고 취소·솔로랭크 기록은 제외한다. 이 값이나 초기값을 공개 누적 랭킹에 섞지 않는다. [개발 계획의 팀 편성 기준](superpowers/plans/2026-10-21-lol-inhouse-development-plan.md#팀-편성용-실력과-후보)

### 후보 선택 규칙

방문자는 로그인 없이 서로 다른 활성 참가자 10명을 고른다. 운영자가 지정한 가능한 포지션에만 배정하며, 각 팀은 다섯 포지션을 하나씩 채워야 한다. 가능한 포지션이 비어 있으면 운영자 확인을 안내하고 임의의 역할을 넣지 않는다.

위임받은 탐색·선택 기준은 다음과 같다. [D20](superpowers/decisions/2026-10-22-overnight-decisions.md#d20--팀-열거공개-웹관리-경계)

1. 참가자 식별자를 정렬하고 첫 사람을 A팀에 고정해 진영만 뒤집힌 중복을 없앤다. 5명씩 나누는 서로 다른 선수 구성 126개와 각 팀에서 가능한 포지션 배정을 조사한다.
2. 각 선수 구성에서 양 팀의 포지션별 실력 합 차이가 가장 작은 배정을 고른다. 동률은 선호 비용, 이어서 안정적인 식별자 순으로 정한다. 선호 비용은 주 포지션 0, 부 포지션 1, 추가 가능한 포지션 2다.
3. 전체 최선의 팀 합 차이를 `d`라 하면 `차이 ≤ d + 5`인 선수 구성에서 차이 → 선호 비용 → 안정적인 식별자 순으로 최대 3개를 제공한다. 개인 실력은 0–100, 팀 합은 0–500 척도이므로 5는 팀 합 차이의 추가 허용값이다.
4. 선수 구성이 같고 포지션만 다른 결과는 한 후보로 합친다. 조건에 맞는 후보가 1–2개면 그만큼만 제공한다.
5. 가능한 팀이 없으면 부족한 포지션이나 겹치는 배정 제약을 설명한다. 각 포지션을 할 수 있는 사람 수만 충분해도 전체 조합이 불가능할 수 있으며, 불가능한 포지션을 강제 배정하지 않는다.

후보에는 양 팀의 참가자·추천 포지션과 실력 차이를 보여준다. 최선에 가까운 균형을 우선하는 대신 조건에 따라 후보가 적어질 수 있다. 허용 차이 5가 최적이라는 운영 비교 결과로 설명하지 않는다. 목표 서버의 응답 목표는 2초 이내이며 실제 성능 확인 상태는 [진행 상태](status.md)를 따른다.

반복 요청에는 같은 자료·평가 기준의 캐시를 활용하고 과도한 호출을 제한한다. 캐시 키·보관 수·요청 제한의 정확한 값은 [API 계약](contracts/api.md)에서 관리한다. 계산 중에는 오래된 세대의 실력을 섞어 추천하지 않는다.

추천은 참고 자료다. 사용자가 롤 클라이언트에서 실제 팀을 구성한다. 웹에서 선수 교환·포지션 재편집, 로비 자동 생성·팀 변경, 선택한 후보·후속 변경 추적은 하지 않는다. 추천을 실제 경기로 확정하지 않고 경기 등록 때 수집한 팀과 최종 확인한 포지션으로 기록·평가한다.

## 변경·재계산·일관성

### 변경 번호와 재계산 입력

명시적 경기 등록, 운영자의 실제 포지션 정정·등록 취소, 평가 기준 변경, 계산에 사용하는 회원의 팀 편성 입력 변경은 관련 이력과 재계산 요청까지 함께 반영한다. 중간 저장 오류로 경기만 바뀌거나 관련 이력·재계산이 빠지면 안 된다. 변경 번호와 저장 단위의 내부 계약은 [API 계약](contracts/api.md)에 둔다.

신규 임시 저장은 원본·정규화 자료와 수집 감사 정보만 기록하고 평가 변경 번호를 올리지 않는다. 중복 전송·중복 확정이나 가능한 포지션 목록의 순서만 바뀐 요청도 불필요한 변경 번호·작업을 만들지 않는다. 원본과 실제 포지션, 운영자 초기값과 계산값은 분리한다. [D08](superpowers/decisions/2026-10-22-overnight-decisions.md#d08--단계-1의-작은-규모-트랜잭션-직렬화), [D11](superpowers/decisions/2026-10-22-overnight-decisions.md#d11--v1-소비자-계약과-안정적-조회)

### 평가 버전과 한 묶음 공개

평가 규칙은 가중치뿐 아니라 알고리즘·항목 내부 비율·표준화 상수·누적 보정값을 함께 보관하는 불변 버전이다. 운영자가 가중치를 바꿀 때는 포지션별 합계 100, 음수 없음, 승패 최대 5를 확인하고 새 버전을 만든다. 기존 버전을 덮어쓰지 않는다. 새 알고리즘은 명시적인 구현을 추가해야 하며 표준화 상수를 화면에서 임의 수정하지 않는다.

새 유효 경기도 다른 경기의 비교 표본을 바꾸므로 모든 유효 경기 점수·경기 순위·누적 통계·랭킹·포지션 실력을 같은 기준으로 재계산한다. 원본은 유지하고 취소된 경기는 되살리지 않는다. 초기 실력 변경으로 작업을 다시 계산하더라도 공개 랭킹에 그 값을 넣지는 않는다.

평가 세대는 같은 자료 변경 번호와 평가 버전에서 만든 경기·누적·포지션 실력 결과 한 묶음이다. 계산 관련 변경이 생기면 새 세대가 완성될 때까지 공개 점수·누적 통계·팀 추천은 ‘계산 중’으로 응답한다. 원본 경기의 숫자 기록은 계속 볼 수 있으며 취소 경기의 공개 제외는 즉시 적용한다.

최신 입력과 평가 기준으로 완성한 결과만 한 번에 공개한다. 계산 도중 입력이 바뀌면 옛 결과를 공개하지 않는다. 작업 중단 후 재시작이나 운영자의 재시도로 복구하며, 늦게 끝난 이전 계산이 새 결과를 덮어쓰지 못하게 한다. 입력을 같은 시점으로 읽는 방법과 작업 소유권·시도 구분·공개·복구의 내부 계약은 [API 계약](contracts/api.md)에 둔다. 선택 근거와 비용은 [D19](superpowers/decisions/2026-10-22-overnight-decisions.md#d19--같은-세대의-불변-평가와-작업-시도-fencing)를 따른다.

전체 재계산·한 묶음 공개는 표본 누락과 버전 혼합을 피하기 쉽지만 자료가 늘수록 계산량·저장 크기가 커지고 계산 중에는 점수를 볼 수 없는 비용이 있다. 실제 지연이 문제가 되면 D19의 부분 재계산·이전 세대 표시·저장 방식 대안을 검토하되 최종 공개 조건과 실패 복구 원칙은 유지한다.

### 원본·계약·호환성

서버와 클라이언트는 JSON 계약과 공통 예제 자료로 연결한다. Java와 TypeScript 구현이 같은 계산 소스를 공유한다는 전제는 두지 않는다. 각 언어의 독립 검사·기대값을 실제 응답과 대조한다. 식별자는 문자열, 교환 시간은 UTC(세계 표준시), 웹 표시 시간은 한국 시간을 사용한다. 과거 저장 원본과 미전송 요청을 계속 읽을 수 있게 형식 버전별 해석기를 유지한다.

공개 예제 자료는 계정·경기 식별자와 시각을 가명·합성값으로 바꾸고 출처·변환 내용을 남긴다. 후보 자료와 검증 완료 자료를 구분하며, 실제 계정명·원본·화면·가명 대응표는 공개하지 않는다. 합성 시각을 실제 반영 시간 측정에 쓰거나 실제 기반 후보를 공개 서비스의 데모 경기로 사용하지 않는다. [D02](superpowers/decisions/2026-10-22-overnight-decisions.md#d02--공개-후보와-검증-완료-fixture-분리)

서버는 원본 JSON과 정규화 JSON을 별도 text 열로 저장하고 검색 항목은 관계형 열에 둔다. 원본의 추가 필드와 큰 정수·정밀한 소수의 수치값을 보존하되, 공백·항목 순서·소수 표기까지 같은 원문 바이트 보존을 약속하지 않는다. 원본에 없었던 정보나 이미 잃은 정밀도를 복원할 수는 없다. JSON 내부 검색이 필요해지면 저장 타입·검색용 사본의 비용을 다시 검토한다. [D09](superpowers/decisions/2026-10-22-overnight-decisions.md#d09--보존마이그레이션후속-평가-경계), [D13](superpowers/decisions/2026-10-22-overnight-decisions.md#d13--독립-리뷰의-json-계약-결함-수정)

로컬 대기열은 SQLite의 트랜잭션과 장애 복구용 기록 방식으로 원본·요청 의존성·소유자를 보존한다. 인증은 별도 보호 파일에 둔다. 수집기 내부 처리 영역만 LCU·인증·파일에 접근하고 화면 영역은 제한된 요청만 보낸다. 화면의 Node 직접 접근은 막고 화면과 내부 사이 요청의 발신 창·정확한 로컬 주소·최상위 프레임·내용을 검사한다. LCU 연결은 요청마다 접속 파일을 다시 읽고 로컬 연결 한 요청에만 인증서 예외를 적용한다. [D15](superpowers/decisions/2026-10-22-overnight-decisions.md#d15--인증lcu렌더러-경계), [D16](superpowers/decisions/2026-10-22-overnight-decisions.md#d16--로컬-원본소유자순서-보존)

도구·의존성·컨테이너 이미지는 재현 가능한 정확한 버전·해시로 고정하고 저장 구조 변경은 새 마이그레이션으로 수행한다. 마이그레이션은 기존 자료를 유지하면서 저장 구조를 바꾸는 절차다. 실제 버전의 기준은 빌드 설정·잠금 파일·컨테이너 설정이며 이 문서에 복제하지 않는다. 로컬 검사와 원격 자동 검사, 공통 예제 검사와 실제 Windows·LCU 연동 결과는 구분한다. ## 설치·운영 설계

기본 백업·복원과 인증 폐기·변경 이력은 사용자 확정 범위다. 아래 수치·설치 방식은 개발 계획의 위임된 세부안이며 실제 적용·검증 상태는 [진행 상태](status.md)에서 관리한다. 실행 명령·배포 환경값은 [개발 환경 안내](development/setup.md)에 둔다.

- Windows 수집기는 수동 설치·업데이트를 기본으로 한다. 앱 버전이 바뀌어도 기존 사용자 저장 경로·대기 자료·인증을 유지한다. 읽지 못하는 저장소를 빈 데이터베이스로 자동 교체하지 않고 원인을 안내한다. 자동 업데이트 서버는 초기 범위에서 만들지 않는다.
- 설치 파일과 파일 무결성 확인값을 제공하고, 진단 내보내기는 오류 코드·버전·상태만 포함한다. LCU 원본·접속 인증·토큰은 제외한다. 유료 서명 인증서 구매는 이 설계에 포함된 결정이 아니다.
- 서버·PostgreSQL·Tunnel을 컨테이너로 운영하고 데이터베이스는 컨테이너 교체 후에도 유지되는 볼륨에 둔다. 웹·API만 Tunnel로 연결하고 데이터베이스 포트·로컬 관리 명령은 외부에 노출하지 않는다. 접속 출처·데이터베이스·Tunnel 비밀 설정은 분리하고 저장소에 비밀값을 넣지 않는다.
- 서버 생존 상태와 서비스 준비 상태를 구분한다. 데이터베이스 연결이나 저장 구조 준비가 안 됐으면 준비 완료로 표시하지 않는다. 건강 상태·버전 응답에 비밀값을 넣지 않는다.
- Windows 시작 시 서비스 시작·재시작 정책·절전 대응을 실제 장비에 맞춰 관리한다. 집의 전원·회선·재부팅과 Tunnel에 가용성이 영향을 받는다. 서버가 중단되면 공개 조회·관리는 사용할 수 없으며, 이미 확보한 참가자 PC의 전송·등록 대기는 보존한다.
- 데이터베이스는 매일과 버전 변경 전에 백업하고 일간 14개·주간 8개를 보관하는 안을 사용한다. 지정한 PC 밖 저장소로 백업과 체크섬을 복사하며 외부 경로·권한이 설정되지 않으면 성공으로 표시하지 않는다. 같은 PC의 저장장치 장애에 대비하는 목적이다.
- 복원 검사는 별도 데이터베이스에서 경기 수·취소 이력·재계산 결과를 대조한다. 운영 데이터베이스 복원은 별도의 명시적 실행으로 제한하고 기존 코드·인증을 폐기한 뒤 로컬 운영자 코드로 복구한다. 최근 백업 이후의 손실 가능 구간을 알린다. 컨테이너 실행 성공을 백업·복원 성공으로 대신하지 않는다.

백업 위치·운영 도메인·접근 권한은 실제 환경에서 설정하며 유료 외부 저장소·새 도메인 구매를 자동 승인한 것은 아니다. 백업 세부안과 설치·운영 근거는 [개발 계획 T13–T14](superpowers/plans/2026-10-21-lol-inhouse-development-plan.md#t13-windows-설치업데이트진단)에 있다.

다음 제품 기능은 초기 범위에 포함하지 않는다.

- macOS용 일반 수집 프로그램, 게스트, 여러 LoL 계정의 전적 통합, 시즌·시즌 초기화
- 온라인 공개 동의 절차, Riot 비밀번호 수집, Riot 소셜 로그인, 사용자 아이디·비밀번호·소셜 로그인, 여러 운영자 관리
- 모든 사용자 설정 경기 자동 등록, 수집자의 등록 후 수정·취소, 원본 수치 수동 편집, 취소 복원 기능
- 웹에서 추천 후 선수 교환·포지션 편집, 롤 로비·팀 자동 조작, 선택한 추천과 후속 변경 추적
- 경기 중 실시간 코칭, 영상·리플레이 분석, 솔로랭크의 모임 랭킹·팀 실력 반영

검증 작업·수용 조건에서 제외한 항목은 [진행 상태](status.md)에서 관리한다. [D22](superpowers/decisions/2026-10-22-overnight-decisions.md#d22--2026-10-23-사용자-요청에-따른-검증-작업-제외)의 범위 변경을 유지하며 제외를 검증 성공으로 바꾸거나 후속 완료 조건으로 되살리지 않는다.

# 반복 경기 목록의 확보 자료 처리 검증

기록일·편집일: 2026-10-28. 수집기는 뒤 페이지가 반복돼도 먼저 찾은 적격 경기의 상세 조회와 저장을 진행하고, 확인하지 못한 과거 구간을 화면에 안내하도록 수정했다. 사용자의 실제 Windows 진단으로 반복 현상을 확인했고, 준비 당시 수정 동작은 macOS의 가상 게임·서버 응답으로 검사했다. 이후 사용자가 수정 설치판의 경기별 안내와 온라인 조회 후 확인 대기 3건을 보고했으며, 후속 관측은 아래에서 준비 당시 검사와 구분한다.

동작 기준은 [경기 수집 명세](../spec.md#경기-수집확인등록), 선택 이유와 대안은 [반복 페이지 대응 결정](../superpowers/decisions/2026-10-22-overnight-decisions.md#d28--2026-10-28-반복-페이지에서-확보한-경기-처리와-조회-한계-표시), 다음 실기는 [대기 생성 절차](../runbooks/collector-acceptance.md#2-전송등록-대기-생성과-기준-백업)를 따른다. 프로젝트의 최신 진행 상태는 [상태 정본](../status.md)에 둔다.

## 실제 Windows 관측

출처는 사용자가 이 채팅으로 전달한 `civil-war-history-pages-v1` 출력이다. 실행 시각은 UTC `2026-10-27T16:51:34.423Z`, 한국 시각 2026-10-28 01:51:34이며 Node.js는 `v24.22.1`, 플랫폼은 `win32`다. 이번 출력에는 Windows 세부 버전·수집기 설치판 버전·게임 패치가 없어 추정하지 않았다. 식별자 없는 수신 자료는 [공개 진단 근거](assets/history-pagination-windows-20261028.json)에 남겼다.

## 수정과 재현 검사

기존 구현은 `HISTORY_PAGINATION_STALLED`를 던졌고, 호출 측은 전체 목록을 받은 다음에만 상세를 조회했다. 이 조합 때문에 확보한 첫 목록도 저장 단계로 넘어가지 못했다. 새 구현은 해당 중단 사유를 목록과 함께 반환한다. 반복된 ID는 중복 처리하지 않고, 경기별 기존 검사를 통과한 자료에만 저장 요청을 만든다. 조회 경고와 개별 경기의 실패 사유는 화면에 함께 표시한다.

첫 재현 검사에서 기존 구현의 중단 오류와 변경 전 반환 형식을 확인한 뒤 수정했으며, 단위 검사 전체가 통과했다. 서비스 검사는 반복 목록에서 적격 한 건·상세 조회 실패 19건을 구분해 적격 한 건만 전송 대기에 넣고, 등록 확정은 보내지 않는지 확인한다. 실제 사용자의 목록에 적격 내전이 있다는 증거로 사용하지 않는다.

처음 화면 검사는 샌드박스의 Electron 실행 제한으로 시작하지 못했으며, 실행 권한을 확보한 재검사에서 위 8개가 통과했다. 패키징도 최초 네트워크 제한을 해소한 뒤 고정 런타임으로 완료했다. 수집기 버전 변경에 따른 의존성 상태 재확인에서는 고정 잠금 파일의 설치를 다시 수행했다. 이 준비 중 실패를 Windows 제품 실패나 통과로 세지 않는다.

별도 읽기 전용 코드 검토는 변경 전 파일 사본과 비교해 목록·경고 전달, 소유권, 화면 오류 표시, 개인정보 경계를 확인했으며 차단할 문제를 보고하지 않았다. 이 검토에서 테스트나 실제 Windows를 별도로 실행하지 않았다.

## 후속 Windows 조회·회원 등록 상태

2026-10-28 사용자는 제거 파일 복구 후 설치한 `0.2.3`에서 온라인 확인 단계는 정상이라고 보고했다. Tunnel 중단 뒤 과거 경기를 조회하자 목록 반복 경고와 함께 `UNSUPPORTED_SCHEMA`·`UNREGISTERED_PARTICIPANT` 안내가 표시됐다. 전송 대기는 0건이고 경기 목록은 비어 있었으며, 추가 확인에서 시험 서버에는 본인 한 명만 등록했다고 답했다. [수신 결과](assets/collector-membership-windows-20261028.json)에 관측 범위를 남겼다.

현재 코드는 목록 확보 후 경기 형식·필수 자료를 검사하고, 그 경기 참가자가 수집기의 보관 명단에 모두 있는지 대조한다. 최초 오프라인 실행에서는 개별 경기 검사 사유가 반환된 사실만 확인했으며 저장 가능한 모임 내전을 확보했다고 판정하지 않았다. 당시 다음 조치는 시험할 실제 경기의 나머지 참가자를 등록하고 수집기가 새 명단을 받은 뒤 재시도하는 것이었다. 회원 확인 기준은 [수집 명세](../spec.md#적격성과-원본-검사)를 따른다.

Tunnel 중단 중 서버 확인 대기를 불러온 요청은 `SERVER_ERROR`를 표시했다. [요청 처리 코드](../../apps/collector/src/main/server-api.ts)는 오류 응답에 해석 가능한 서버 코드가 없을 때 이 일반 코드를 사용한다. 실제 HTTP 상태·응답 본문은 받지 않았으므로 프록시의 특정 오류 번호로 단정하지 않았다. 연결 복구 후에도 실패하는지와 이번 경기별 거절은 별도로 확인한다.

그 뒤 사용자는 Tunnel을 켜고 과거 경기를 조회해 확인 대기 3건이 생겼다고 보고했다. 다시 Tunnel을 끄고 조회했을 때 기존 안내 문구가 같고 전송 대기는 0건이었으며, 추가 질문에서 확인 대기 3건과 해당 경기 목록이 그대로 남아 있다고 답했다. 이 후속 결과도 위 수신 자료에 순서를 구분해 기록했다. 등록 명단의 최종 인원수·개별 경기 ID·실제 서버 요청 로그는 받지 않았다.

[로컬 저장 코드](../../apps/collector/src/main/outbox.ts)의 `enqueueCollected`는 같은 회원·경기의 기존 전송 작업을 반환하고 새 작업을 만들지 않는다. [상태 계산](../../apps/collector/src/main/history-sync.ts)도 성공한 원본 전송 작업을 전송 대기로 세지 않는다. 따라서 같은 경기를 온라인 전송 후 다시 조회한 경우의 0건은 중복 전송 방지와 맞는다. 화면 안내는 경기별 실패 코드를 합쳐 표시하므로 남은 미지원·미등록 안내를 확인 대기 3건 전체의 실패로 해석하지 않는다. 다만 이 실행의 개별 실패 경기와 오류의 대응은 확인하지 않았다.

이후 기존 확인 대기 경기로 오프라인 등록 요청을 만드는 분기를 안내했다. 상세 분기는 [실기 절차](../runbooks/collector-acceptance.md#2-전송등록-대기-생성과-기준-백업)를 따른다. 이 경로의 등록 요청 보존과, 아직 전송하지 않은 경기 원본의 요청 보존은 구분해 기록한다.

같은 날 후속 보고에서 사용자는 Tunnel을 끈 상태로 등록 대기 1건·확인 대기 2건을 만들고 백업했으며, 재실행 후에도 기기 등록·경기·포지션이 유지된다고 답했다. 위 수신 자료에 별도 후속 관측으로 추가했다. 이는 실제 Windows에서 사용자가 확인한 결과이며 담당자의 직접 실행과 구분한다. 이 보고 시점에는 재실행 후 건수의 별도 출력·인증 파일 해시를 받지 않았고, 제거 후 재설치·다른 버전 업데이트·인증 손상 복구는 수행 전이었다.

이어 사용자는 `0.2.3` 제거 후 같은 판 재설치를 완료했고, 안내한 인증 파일 비교가 모두 `True`이며 기기 등록·경기·포지션과 등록 대기 1건·확인 대기 2건이 유지된다고 보고했다. 이 결과를 위 수신 자료의 재설치 후속 항목에 추가하고, 동일 버전 제거 후 재설치 보존을 사용자 실행 보고 기준으로 통과 기록했다. 인증 파일의 실제 해시 문자열·화면·설치 로그는 수신하지 않았다. 같은 판 재설치 결과를 다른 버전 업데이트나 인증 손상 복구의 성공으로 확대하지 않는다.

이후 사용자는 두 추가 시험을 생략하고 기존 등록 요청을 재개하는 경로를 요청했다. [D30](../superpowers/decisions/2026-10-22-overnight-decisions.md#d30--2026-10-28-업데이트인증-손상-시험-제외와-기존-요청-처리)에 따라 이번 범위에서 제외하고, 유효한 기존 인증으로 연결을 복구하는 절차를 안내했다.

후속 보고에서 사용자는 Tunnel을 켠 뒤 확인 대기 경기 한 건도 추가로 등록해 등록 완료 2건·확인 대기 1건이 됐다고 답했다. 서버 웹에서 중복 등록 없이 포지션이 일치하고, 마지막 재실행 후에도 인증과 최종 상태가 유지된다고 보고했다. 위 수신 자료에 별도 최종 관측으로 추가했다. 이 결과로 선택한 기존 인증의 연결 복구·등록 요청 처리·서버 대조·최종 재실행 확인은 사용자 보고 기준으로 완료 기록한다. 재개 버튼 사용 여부·재시도 경과 시간·서버 원본 로그는 받지 않았으며, 의도적으로 추가 등록한 경기 한 건을 중복 등록으로 세지 않는다.

## 산출물과 남은 실기

이 보고서의 최초 준비 당시 수정 설치판은 `0.2.2-provisional`이었다. 이전 `0.2.0-provisional`과 `0.2.1-provisional` 설치판은 별도로 보존했다. 이전 판의 설치·시험 성과는 [당시 준비 기록](2026-10-26-collector-acceptance-preparation.md)에서 바꾸지 않는다. 당시 판은 저장 구조·설치 식별자·서버 API를 바꾸지 않은 서명 없는 시험 배포였다. 후속 설치판과 당시 판의 재사용 제한은 [제거 프로그램 보고서](2026-10-28-uninstaller-integrity-report.md#산출물남은-확인)를 따른다.

최초 준비에서는 같은 계정·서버 주소에서 수정판으로 조회하고, Tunnel을 끈 상태의 적격 경기 전송 대기를 보존 시험의 시작 자료로 정했다. 후속 Windows 실행은 먼저 온라인 조회를 마친 경로였으므로 위 등록 요청 분기로 이어간다. 실제 경기나 보존할 대기가 없으면 오류·건수를 기록하고 멈춘다. 새 내전이나 제외한 과거 범위 측정을 추가로 요구하지 않는다.

사용자 보고로 수정판의 Windows 온라인 조회 후 확인 대기 표시, 오프라인 등록 대기 생성·백업, 재실행과 같은 판 제거 후 재설치의 인증·경기·포지션 보존, 연결 복구 뒤 서버 등록과 최종 상태 유지를 확인했다. 이번에 선택한 Windows 실기 흐름은 완료했으며, 두 추가 시험은 사용자 요청으로 제외한 미실행·미검증 항목이다. 원본 미전송 요청 보존도 미확인으로 남긴다. 현재 남은 운영·구현 작업은 [상태 정본](../status.md#남은-작업-순서)을 따른다. 이번 수정은 게임 클라이언트가 더 오래된 페이지를 제공하도록 만드는 변경이 아니며, 실제 보관 자료 전체의 복구나 전체 조회 완료를 보장하지 않는다.

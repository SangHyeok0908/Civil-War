# 서버 자동 교체와 수집기 Release 공개 검증

master 병합마다 집 서버가 새 이미지로 스스로 교체되고, 수집기 설치 파일이 새 버전일 때 GitHub Release로 공개되도록 구현했다. 이 기록은 **개발 PC에서 한 로컬 검사**의 환경·방법·결과와, 아직 확인하지 못한 실제 GitHub·GHCR·집 PC 항목을 구분한다. 로컬 모의 시험의 성공은 집 PC 교체 성공이 아니다.

기록일: 2026-11-21. 편집·보완일: 2026-11-21(전체 브랜치 최종 검토에서 찾은 오류를 고치고 검사 수를 갱신함). 결정 이유와 대안은 [설계 기록](../superpowers/specs/2026-11-21-ghcr-auto-deploy-design.md), 현재 제품 기준은 [명세](../spec.md#설치운영-설계), 운영 절차는 [집 서버 운영 절차](../runbooks/home-server.md#자동-교체)·[수집기 설치 안내](../runbooks/collector-install.md), 현재 상태는 [상태 정본](../status.md)을 따른다.

## 실행 환경

macOS(arm64) 개발 PC, Node.js v23.11.0(저장소 지정 24.22.1과 달라 pnpm이 엔진 경고를 출력하며 검사 자체에는 영향 없음), pnpm 11.5.0, Docker 28.1.1, JDK 25.0.1. 작업 전 `node_modules`의 끊어진 연결을 복구했고 추적 파일은 바뀌지 않았다. 실제 GitHub Actions·GHCR·Discord·집 Windows PC는 쓰지 않았다.

`pnpm test:collector-release`의 실패 1개는 `nsis-integrity` 시험의 "default NSIS icons … stored CRC"(macOS에서 `std::bad_alloc`)로, 이 작업 이전부터 macOS에서 나던 알려진 실패다. Windows 자동 검사가 이 항목을 다룬다. 이번 작업의 사례가 아니며 이번에 고치지 않았다.

모의 시험의 다섯 시나리오는 정상 시작, 성공 교체(백업 1개 생성·알림 없음), 시작에 실패하는 이미지의 되돌림과 DB 복원, 같은 실패 이미지의 재시도 금지, 교체 도중 교체 담당이 죽은 뒤의 복구다. 근거 코드는 [모의 시험 스크립트](../../scripts/updater-simulation.mjs), 실행은 [개발 안내](../development/setup.md#서버-자동-교체-시험)에 있다. 이 시험은 Discord 실제 전송을 다루지 않아 알림은 "건너뜀" 로그로만 확인했다.

## 검토에서 찾아 고친 오류

각 작업은 구현자와 다른 검토자가 따로 검토했다. 그 결과로 다음을 고쳤다.

- 교체 성공 순서를 "새 서버 정상 → Tunnel 시작 → 상태 기록 → 오래된 백업 정리"로 바꿨다. 정상이 된 뒤 담당이 죽어도 불필요한 복원을 하지 않게 하기 위해서다. 되돌림 완료·백업 실패처럼 대기 상태로 끝나는 결과는 알림 전에 상태를 먼저 저장해, 알림 도중 중단돼도 같은 복원을 반복하지 않게 했다.
- 복원을 임시 파일 변환 성공 뒤에만 기존 DB를 비우는 방식으로 바꿨다. 깨진 덤프가 DB를 지우지 않음을 위 복원 확인으로 검증했다.
- 교체 담당이 주기마다 상태 파일을 다시 읽도록 해, 멈춤 상태에서 `--reset`을 실행하면 다음 주기에 반영된다.
- 문서 대조에서 설계의 "성공은 로그에 커밋과 시각을 남긴다"가 코드에 없음을 찾아, 교체 시작·교체 완료·되돌림 완료·재시작 복구 줄을 교체 담당 로그에 추가했다(사례 1개 추가로 51개).
- 전체 브랜치 최종 검토에서 다음을 고쳤다. 사례 수는 `pnpm test:updater`가 센 교체 담당 `node:test` 사례이며 51개에서 60개가 됐다.
  - `--reset`은 멈춤만 풀고 실패한 이미지는 계속 막도록 고쳤다(이전에는 둘 다 지워 운영 절차 문서와 달랐다). 같은 이미지를 다시 시도하는 `--retry`를 새로 추가했다.
  - 멈춤 상태 수동 조치에 구체적인 PowerShell 절차를 넣고, 멈춤 상태에서만 지정 백업을 복원하는 `--restore <백업파일>`을 추가했다(복원 명령을 한 줄로 직접 쓰면 PowerShell 따옴표 처리가 불안정해 교체 담당의 기존 복원 코드를 재사용했다).
  - 알 수 없는 인자는 사용법과 종료 코드 2로 끝나고, `docker compose run` 일회성 컨테이너에서는 교체 반복을 시작하지 않아 두 번째 반복이 생기지 않는다.
  - 서버·교체 담당 이미지 게시에서 움직이는 이름표(`:master`·`:latest`)는 처음에 "실행한 커밋이 master 최신일 때만" 올리게 했으나, 경로 필터가 있는 작업 흐름에서는 문서만 바뀐 커밋이 중간에 들어와도 이름표가 건너뛰어지고 그 커밋은 이미지를 만들지 않아 변경이 집 서버에 닿지 못하는 결함이 있었다(`ls-remote` 실패를 최신이 아님으로 취급하는 문제도 있었다). 이제 `sha-` 이름표는 항상 올리고, 움직이는 이름표는 master에 더 새로운 커밋 중 **그 작업 흐름의 `on.push.paths`와 같은 경로를 바꾼 커밋이 없을 때** 올린다(있으면 그 커밋의 실행이 게시하므로 알림만 남긴다). 가져오기 실패는 단계 실패이고, 이 커밋이 master 기록에 없으면 경고를 남기고 올리지 않는다. 판정 스크립트는 임시 git 저장소로 로컬에서 확인했고 작업 흐름 자체는 아직 실행하지 않았다.
  - 멈춤 복구 절차의 `docker tag civil-war-server:previous civil-war-server:current`를 상태 파일의 `previousId`를 쓰는 `docker tag <previousId> civil-war-server:current`로 고쳤다. 되돌림이 이름표를 다시 붙이기 전에 실패하면 `:previous`가 옛 값일 수 있기 때문이다.
  - `infra/home-server/secrets/`를 `.gitignore`에 추가했다. Release 공개 스크립트는 `gh` 실패 때 오류 출력을 보여 주도록 했다. 운영 절차 문서의 최초 전환(웹훅 저장·`ADMIN_LOGIN_CODE` 확인·실패 시 복구)과 평소 확인 설명을 고쳤다.
- 모의 시험의 판정을 강화했다(되돌림 알림이 시험 중에 늘었는지, 컨테이너가 실행·정상인지 확인). 중단 신호를 받으면 정리 후 종료한다.

## 아직 확인하지 못한 것

| 항목 | 상태 |
| --- | --- |
| GitHub Actions의 새 작업 흐름(`server.yml`·`updater.yml`·`client.yml` 변경) 실행 | PR 병합 후 확인 예정. 아직 한 번도 실행하지 않았다. 문법 검사기(actionlint)도 쓰지 못했다 |
| GHCR에 이미지가 실제로 올라가는지, PR에서는 올라가지 않는지 | PR 병합 후 확인 예정 |
| GHCR 패키지의 공개 여부 | 미확인. 처음 생성 시 비공개일 수 있어 사용자가 공개로 바꿔야 할 수 있다 |
| 새 Release 공개와 같은 버전 재병합 시 불변 | PR 병합 후 확인 예정 |
| Release로 올라간 설치 파일의 Windows 설치 | 사용자 실행 필요 |
| 실제 Discord 전송과 웹훅 파일 | 사용자 실행 필요(`--test-alert`) |
| 집 PC의 최초 전환과 실제 자동 교체·되돌림 | 사용자 실행 필요. 로컬 모의 시험 성공으로 대신하지 않는다 |
| 수집기 업로드 경로 | 업로드 단계가 `dist/collector`에 설치 파일 하나만 있다고 가정한다. 실제 실행에서 확인 필요 |
| 서버 JAR 전달 경로 | 검사 작업이 올린 JAR가 `server-jar/<파일>.jar`로 내려받아진다는 가정은 첫 실행에서 확인 필요(없거나 둘 이상이면 작업이 실패하도록 해 두었다) |
| 라벨만 출력하는 `docker inspect` 명령 | 실제 집 PC의 PowerShell에서 아직 실행하지 않음. 사용자 실행 필요 |
| 백업 크기·복원 시간 | 측정하지 않음 |
| 로컬 모의 시험이 다루지 않은 경로 | 모의 시험은 5개 시나리오만 실행했다. 설계 기록의 검증 항목에 있던 **되돌림 자체의 실패, 백업 실패, 가짜 웹훅 수신기로 알림 전송을 확인하는 시나리오는 실행하지 않았다.** 이 경로는 가짜 Docker·가짜 알림을 쓰는 단위 시험으로만 확인했다. 최종 검토에서 추가한 `--retry`·`--restore`·일회성 실행 차단은 단위 시험으로만 확인했고, 이미지 게시의 이름표 조건은 임시 git 저장소에서 판정 스크립트만 확인했고 작업 흐름은 아직 실행하지 않아 미확인이다 |

## 남은 작업과 알려진 제한

- **남은 필수 작업:** PR 병합 후 위 "병합 후 확인 예정" 항목, 집 PC 최초 전환([운영 절차](../runbooks/home-server.md#최초-전환한-번-사람이-실행))과 첫 실제 교체 확인.
- **후속 과제(이번 범위 밖):** `infra/home-server/secrets/`는 최종 검토 수정에서 `.gitignore`에 추가했다. 공유 ZIP 생성 스크립트가 이 폴더를 제외하는지는 확인하지 않았다.
- **사용상 제한:** 성공 알림이 없어 교체 담당·Docker Desktop이 멈추면 조용히 반영되지 않는다. 교체마다 서버가 몇 분 멈춘다. 서버 경로 조건에 걸리지 않는 master 병합은 이미지를 만들지 않아 교체되지 않는다. 교체 담당은 Docker 전체 제어권을 가지며 수동으로 갱신한다. 이미지 게시는 `server.yml`의 `server` 작업, Release 공개는 `client.yml`의 `client` 작업 통과 뒤에만 이어지고 다른 작업 흐름의 결과는 조건이 아니다. 움직이는 이름표는 같은 경로를 바꾼 더 새로운 커밋의 실행에 맡기므로, 그 실행이 실패·취소되거나 `[skip ci]`로 생략되면 앞선 변경도 다음에 통과하는 실행 전까지 집 서버에 반영되지 않는다.

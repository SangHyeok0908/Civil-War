# 팀 추천 시점의 솔로랭크 조회와 초기 포지션 참고 자료 제거 설계

> 기록일 2026-11-25. 현재 제품 기준: [포지션별 실력 보정](../../spec.md#포지션별-실력-보정). 현재 API 계약: [api.md](../../contracts/api.md). 현재 상태: [status.md](../../status.md).

팀 추천을 누르는 사람이 누구든, 운영자가 따로 조회하지 않아도 **그 순간의 솔로랭크 등급**이 반영된 추천을 받게 한다. 지금은 서버가 1초마다 참가자 한 명씩 등급을 미리 조회해 두고, 저장된 값은 성공 후 24시간 동안 다시 조회하지 않는다. 그래서 추천 결과가 최대 하루 전 등급을 쓸 수 있다. 함께 쓰이지 않는 관리자 기능인 **초기 포지션 참고 자료**를 제거한다. 이 기능에 넣을 솔로랭크 경기 기록을 만들어 주는 경로는 2026-10-29에 사용자 결정으로 수집기에서 제거되었다([결정 보완](../decisions/2026-10-28-ux-requirements.md#2026-10-29-보완--솔로랭크는-웹-팀-추천에서만-사용)).

이 문서는 설계이며 구현·검증 완료를 뜻하지 않는다.

## 목표·비목표

**목표**

- 팀 추천 요청이 들어오면 서버가 선택한 10명의 현재 솔로/듀오 등급을 Riot에서 조회하고, 그 값으로 포지션별 실력을 계산해 추천한다.
- 일부 조회가 실패해도 추천은 응답한다. 실패한 사람에게 어떤 값을 썼는지 응답과 화면에 드러낸다.
- 관리자 화면에서 초기 포지션 참고 자료 영역과 그 서버 기능·저장 자료를 없앤다.

**비목표**

- Riot 호출 한도 초과를 막는 장치(결과 재사용, 호출 수 제한, 대기열 등). — 사용자 확정, [한계](#한계와-후속-작업)에 기록
- 등급 환산식(티어→0~100)과 보정식(다섯 경기분 강도)의 변경. 기존 [정책 파일](../../../apps/server/src/main/resources/policies/rank-seed-v1.json)과 [R04](../../spec.md#포지션별-실력-보정)를 그대로 쓴다.
- 공개 순위·종합 점수에 솔로랭크를 넣는 것. 지금처럼 넣지 않는다.
- 주·부 포지션 자동 추천을 다른 형태로 다시 만드는 것.

**피해야 할 결과**

- Riot 조회가 실패했는데 그 사실을 숨긴 채 오래된 값이나 50으로 추천하는 것.
- 조회 실패 때문에 팀 추천 자체가 막히는 것.

## 접근 방식 비교

판단 기준은 (1) 운영자 개입 없이 최신 등급을 반영하는지, (2) 조회 실패 때도 추천을 받을 수 있는지, (3) Riot 호출 수다.

| 방식 | 장점 | 단점·비용 |
|------|------|-----------|
| **1. 요청 때 조회, 실패한 사람은 마지막 성공값 사용 — 선택** | 성공한 사람은 항상 최신 값. 한도 초과·장애 때도 추천이 나온다. 정확도가 떨어진 사람을 화면에 표시한다. | 실패한 사람은 오래된 값으로 계산된다. 요청마다 최대 20번 호출한다. |
| 2. 요청 때 조회, 한 명이라도 실패하면 추천 실패 | 결과가 나오면 모두 최신 값이다. | 한도에 걸리면 그동안 추천을 쓸 수 없다. |
| 3. 방식 1에 현재 백그라운드 조회도 유지 | 실패 때 대신 쓰는 값이 더 최신이다. | 호출 출처가 둘이라 한도에 더 빨리 걸리고 관리할 부분이 늘어난다. |

사용자는 방식 1을 골랐다. 처음 비교에서는 개발용 키가 24시간마다 만료된다는 전제를 썼으나, 사용자가 키가 만료되지 않는 Personal API Key임을 알려 주어 전제를 바로잡은 뒤 다시 골랐다. 남은 실패 원인은 주로 호출 한도 초과와 Riot 장애다.

**재검토 조건:** 호출 한도 초과로 "이전 값 사용" 표시가 자주 나타나면 결과 재사용이나 호출 제한 장치를 후속 작업으로 구현한다.

## 동작 변경 전후

| 상황 | 변경 전 | 변경 후 |
|------|---------|---------|
| 등급 조회 시점 | 서버가 1초마다 한 명씩. 성공 후 24시간, 실패 후 5분 동안 다시 조회하지 않음 | 팀 추천 요청이 들어올 때 선택한 10명을 조회 |
| 포지션별 실력 계산 시점 | 내전 재계산 때 저장된 등급으로 미리 계산 | 팀 추천 요청 때 방금 조회한 등급으로 계산 |
| 등급 변경 시 | 재계산 번호를 올려 전체 평가를 다시 계산 | 재계산하지 않음. 등급은 평가 결과에 들어가지 않음 |
| 조회 실패 | 이전 시드 유지, 화면 표시는 관리자 참가자 목록에서만 | 이전 성공값 또는 50을 쓰고, 추천 응답과 화면에 사람별로 표시 |
| 관리자 참가자 목록의 등급 표시 | 백그라운드 조회 결과 | 마지막 팀 추천에서 저장된 결과. 추천에 한 번도 포함되지 않은 사람은 "조회 전" 상태 |
| 초기 포지션 참고 자료 | 관리자 편집 화면에 있음 | 없음 |

**예시:** 다이아몬드 I(시드 90)인 참가자가 미드 내전을 5판 해서 점수 합이 300이면 미드 실력은 (5×90 + 300)/10 = 75다. 이 참가자의 등급이 그 사이 에메랄드 I(시드 77)로 내려갔다면, 변경 전에는 최대 24시간 동안 75로 계산되고 변경 후에는 다음 추천부터 (5×77 + 300)/10 = 68.5로 계산된다.

## 설계

### 서버: 팀 추천 처리 순서

1. 기존과 같이 입력을 검사한다. 10명이고, 중복이 없고, 모두 팀 추천 대상(`active`)이어야 한다.
2. **DB 트랜잭션 밖에서** 10명의 등급을 [동시에 조회](#동시-조회와-대기-상한)한다. 사람마다 기존 [`SoloRankService.refresh`](../../../apps/server/src/main/java/cw/riot/SoloRankService.java)의 절차를 재사용한다. Riot ID로 공식 PUUID를 확인하고, 솔로/듀오 등급을 조회하고, 결과를 `solo_rank_snapshots`에 저장한다. 저장 규칙도 기존과 같다. 성공(`ranked`·`unranked`)이면 시드·티어·조회 시각을 갱신하고, 실패하면 이전 시드와 조회 시각을 그대로 둔다.
3. 저장 후 사람마다 **이번 요청에서 쓴 값과 그 출처**를 정한다.
4. 현재 평가 결과의 경기별 점수(`gameScores`)와 3번의 시드로 포지션별 실력을 계산한다. 계산식은 지금의 [`RoleSkillCalculator`](../../../apps/server/src/main/java/cw/domain/RoleSkillCalculator.java)와 같다.
5. 기존 [`TeamRecommender`](../../../apps/server/src/main/java/cw/domain/TeamRecommender.java)로 후보를 만든다.
6. 후보와 사람별 등급 반영 상태를 함께 응답한다.

평가 결과가 아직 없으면(재계산 중) 지금처럼 202 `RECALCULATING`을 돌려준다. 이 경우 Riot 조회도 하지 않는다. — 개발 담당자 제안

### 동시 조회와 대기 상한

처음 설계안은 10명을 차례로 조회하는 것이었다. 지금의 [`HttpRiotGateway`](../../../apps/server/src/main/java/cw/riot/HttpRiotGateway.java)가 요청을 한 번에 하나씩만 보내기 때문이다. 이렇게 하면 응답이 20번 호출 시간의 합만큼 느려진다. 사용자는 문서 검토 중 동시 조회로 바꾸고, 동시에 진행하는 수를 제한하며, 전체 대기 시간에 상한을 두도록 정했다. — 사용자 확정(2026-11-25)

- **사람 단위로 동시에 처리한다.** 10명을 동시에 시작한다. 한 사람 안에서는 지금처럼 계정 조회가 끝난 뒤 등급을 조회한다. — 사용자 확정
- **전체 대기 상한은 4초다.** 사용자가 제시한 3~5초 범위의 가운데 값이다. 추천 요청이 조회를 시작한 때부터 4초가 지나도 끝나지 않은 사람은 기다리지 않는다. 그 사람은 조회 실패와 똑같이 마지막 성공값이나 50을 쓰고, 화면에도 실패와 같은 방식으로 표시한다. 응답의 `status`는 `timeout`으로 구분한다. — 상한 적용은 사용자 확정, 4초와 `timeout` 이름은 개발 담당자 제안
- **상한이 지난 조회는 취소한다.** 진행 중인 Riot 요청을 끊고 그 사람의 결과는 저장하지 않는다. 늦게 끝난 결과가 응답과 다른 값을 저장하는 일을 막고, 동시 진행 자리를 바로 비우기 위해서다. — 개발 담당자 제안
- **서버 전체에서 동시에 보내는 Riot 요청은 10개까지다.** 여러 사람이 동시에 추천을 눌러도 이 수를 넘지 않는다. 자리가 없으면 자리가 날 때까지 기다리며, 이 기다림도 4초 상한에 포함된다. 10개는 한 번의 추천에서 10명이 동시에 진행할 수 있는 수이고, Riot의 1초 20번 한도 안에 든다. — 제한 적용은 사용자 확정, 10개는 개발 담당자 제안
- **Riot 요청 하나의 제한 시간은 남은 상한 시간을 넘지 않는다.** 지금의 요청당 5초 제한을 그대로 두면 4초 상한보다 길기 때문이다.
- **429 처리는 지금과 같다.** Riot이 429를 돌려주면 대기 종료 시각을 기록하고, 그 시각까지 다른 요청은 Riot에 보내지 않고 바로 실패로 처리한다. 동시에 여러 요청이 이 시각을 읽고 쓰므로 안전하게 공유되도록 바꾼다. — 사용자 확정

**예시:** 10명 중 9명은 1초 안에 끝났고, 1명은 Riot 응답이 늦어 4초가 지났다. 추천은 4초 시점에 응답한다. 늦은 1명은 `source: saved`(마지막 성공값) 또는 `default`(50), `status: timeout`으로 표시된다.

### 사람별 등급 반영 상태

팀 추천 응답에 `rankLookups` 배열을 추가한다. 선택한 10명 모두에 대해 한 항목씩 넣는다. — 개발 담당자 제안

| 필드 | 뜻 |
|------|----|
| `memberId` | 참가자 |
| `source` | 이번 추천에 쓴 값의 출처. `live`(방금 조회 성공), `saved`(이번 조회는 실패, 마지막 성공값 사용), `default`(성공한 적 없음, 중립값 사용) |
| `status` | 이번 조회 결과. 기존 값인 `ranked`, `unranked`, `unavailable`, `not_found`, `conflict`와 대기 상한을 넘긴 `timeout` 중 하나 |
| `teamSeed` | 이번 계산에 쓴 시드(0~100) |
| `tier`, `division` | 계산에 쓴 등급. 등급 없음이나 `default`이면 null |
| `observedAt` | 계산에 쓴 등급을 조회한 시각. `default`이면 null |

등급 없음(`unranked`)은 조회에 성공한 것이므로 `source`는 `live`이고 시드는 50이다. 조회 실패와 등급 없음은 지금처럼 구분한다.

### 웹: 팀 추천 화면

추천 결과 아래에 "솔로랭크 반영" 목록을 둔다. 한 줄에 한 명씩, 이름과 반영 상태를 보여 준다. 모두 `live`이면 한 줄 요약만 보여 준다. — 개발 담당자 제안

```
솔로랭크 반영 · 10명 중 8명 최신 조회
  김철수   다이아몬드 I   방금 조회
  이영희   등급 없음      방금 조회 (기준값 50)
  박민수   골드 II        조회 실패 · 11월 24일 오후 9:10 조회값 사용
  최지훈   —              조회 실패 · 기준값 50 사용
```

### 웹: 관리자 참가자 편집

[`Members.tsx`](../../../apps/web/src/features/admin/Members.tsx)의 "초기 포지션 참고 자료" 영역 전체(제안 보기, PUUID 입력, JSON 입력, 연결 확인, 가져오기, 제안 적용, 안내 문구)를 제거한다. 참가자 요약의 솔로랭크 상태 문구는 유지하되, 조회 기록이 없으면 "팀 추천 때 조회" 같은 문구로 바꾼다. 문구는 구현 때 정한다.

## 한계와 후속 작업

- **호출 한도 대책 없음(사용자 확정).** 팀 추천 1번에 Riot 호출이 최대 20번 생긴다. 키의 한도가 2분에 100번이라면 2분 안에 추천을 5번 넘게 요청할 때 한도에 걸릴 수 있다. 그동안 조회는 실패로 처리되고 마지막 성공값이나 50이 쓰이며, 화면에 그렇게 표시된다. 기존 IP별 제한(10분에 60번)은 그대로 남지만 Riot 한도를 막기에는 부족하다.
- **응답 시간 증가.** 추천 응답은 Riot 조회가 끝날 때까지 늦어지며, 최대 약 4초(대기 상한)가 더해진다. 정상일 때의 실제 시간은 측정하지 않았다.
- **추천에 포함되지 않은 사람의 등급은 갱신되지 않는다.** 관리자 참가자 목록의 등급 표시는 마지막으로 추천에 포함된 시점의 값이다.
- **공개 요청이 Riot 호출을 만든다.** 팀 추천은 로그인 없이 쓸 수 있으므로 누구나 Riot 호출을 일으킬 수 있다.
- **동시 진행 제한은 한도 대책이 아니다.** 동시에 보내는 요청 수만 제한하므로 2분 100번 한도는 여전히 넘을 수 있다.
- 후속 후보: 짧은 시간 결과 재사용, 이미 확인한 공식 PUUID가 있으면 계정 조회 생략(호출 절반).

## 2026-11-27 보완 — API 키 교체 뒤 저장된 PUUID 갱신

편집일: 2026-11-27. 위 설계 당시에는 다루지 않은 경우다. 운영 키를 바꾼 뒤 참가자 대부분의 조회가 `conflict`로 끝나 등급이 반영되지 않았다. 관측과 시험 결과는 [검증 보고서](../../validation/2026-11-27-riot-key-change-report.md)에 있다.

| 분류·주체 | 결정 | 현재 상태 |
| --- | --- | --- |
| 오류 수정 · 개발 담당자 | 저장된 PUUID를 Riot이 현재 키로 해독하지 못할 때만 새 PUUID로 교체 | 구현·로컬 시험 완료, 운영 반영 전 |
| 위임받은 선택 · 개발 담당자 | 아래 비교의 "저장 값 확인 후 교체" 채택 | 바꾸고 싶으면 알림 |

판단 기준은 실제 충돌(Riot ID가 다른 계정으로 넘어간 경우)의 차단을 유지하는지, 운영자가 할 일이 생기는지, Riot 호출이 얼마나 늘어나는지다.

| 대안 | 장점 | 단점·비용 |
| --- | --- | --- |
| 저장 값 확인 후 교체(채택) | 실제 충돌은 계속 막는다. 운영자 작업과 DB 변경이 없다 | PUUID가 달라진 참가자마다 Riot 호출 1번 추가. 키 교체 뒤 첫 추천은 한 사람당 최대 3번 |
| 키 식별값을 DB에 저장하고 달라지면 저장 PUUID를 모두 비움 | Riot 호출이 늘지 않는다 | 키에서 만든 값을 DB에 보관해야 하고, 비운 직후에는 실제 충돌도 걸러내지 못한다. 구현·시험하지 않은 대안이다 |
| 운영자가 DB에서 직접 비움 | 코드 변경 없음 | 키를 바꿀 때마다 수동 작업이 필요하고 빠뜨리면 같은 문제가 반복된다 |

감수할 불이익은 Riot의 400 응답 본문에 있는 `decrypting` 문구에 의존한다는 점이다. Riot이 이 문구를 바꾸면 교체가 일어나지 않고 이전처럼 `conflict`로 남는다. 등급이 잘못 저장되지는 않는다. 그런 변화가 관측되면 키 식별값 방식을 다시 검토한다.

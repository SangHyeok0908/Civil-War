# LoL 내전 기록·평가·팀 추천 서비스 기획서

> 기록일 2026-10-21. 현재: [제품 명세](../../spec.md).

> 2026-10-25: 반복 설명을 정본 링크로 정리했다. 날짜별 사실·근거는 보존하며, 현재 링크의 값은 당시와 다를 수 있다.

- 작성일: 2026-10-21
- 상태: 사용자 승인 완료 — 제안한 기본안까지 포함하여 확정
- 보완 확정: 과거 경기 조회 버튼 → 서버 임시 저장 → 수집자 확인 후 등록. 동일 경기 재전송은 기존 기록과 집계를 변경하지 않는다.
- 승인 내용: LCU 실기 검증을 첫 단계로 하는 개발 계획 작성. 이 승인은 실기 검증이나 구현이 이미 수행되었다는 뜻이 아니다.
- 기술 결정 (2026-10-21): 서버 Java 25 + Spring Boot 4.1.x의 최신 정식 패치 버전, 서버 DB PostgreSQL, DB 접근과 동적 조회 Spring Data JPA + Specification, 서버 빌드 Gradle + Groovy DSL(`build.gradle`)을 사용자와 확정. 후속 대화에서 LCU 검증 도구는 Node.js 24로 확정했으며 Windows 실측은 추후 진행한다. 나머지 기술 스택은 대화하며 결정한다.
- 목적: 대화에서 정한 제품 범위와 동작을 보존하고, 이후 기술 설계와 개발 계획의 기준으로 사용한다.
- 기술 선택 근거: [기술별 대안과 장단점 및 결정 과정](../decisions/2026-10-21-tech-stack-decisions.md).
- 이 문서는 구현 완료나 LCU 실기 검증 완료를 의미하지 않는다.
- 2026-10-22 실행 승인: 단계 0–3을 순차 진행하고 권고 결정을 기록하며 [D01–D04](../decisions/2026-10-22-overnight-decisions.md)에 따라 임시 구현을 허용했다. 운영 준비 완료·단계 0 PASS의 승인은 아니다.
- **2026-10-23 범위 변경 기록:** 경기 종료 후 첫 조회(C01), 미리 실행한 도구와의 조회 비교(C02), 반영 시간·과거 조회 범위 측정(C10), 실제 3–5경기 시범 운영(T15)을 사용자 결정으로 제거한다. 남은 순서는 피해량 의미와 점수 기준 확정 → Windows 설치·업데이트 검증 → 서버 외부 접속과 백업·복원이다. [결정 D22](../decisions/2026-10-22-overnight-decisions.md#d22--2026-10-23-사용자-요청에-따른-검증-작업-제외). 제외한 항목을 실측 성공으로 바꾸지 않는다.

## 1. 만들려는 서비스

2026-10-21 사용자는 약 30명, 2주 3–6경기 규모에서 운영자 없이도 참가자 한 명이 기록을 등록하고 친구들이 공개 조회·팀 추천을 이용하는 기획을 승인했다. 현재 범위의 상세 설명은 [제품 범위와 사용자](../../spec.md#제품-범위와-사용자)를 따른다.

## 2. 확정한 운영 환경

macOS 개발, Windows 수집기, 집 Windows의 Docker 운영과 Cloudflare Tunnel 사용은 당시 사용자 확정이다. 현재 구성은 [설치·운영 설계](../../spec.md#설치운영-설계)에 둔다.

2026-10-21에 Java 25·Spring Boot 4.1.x 정식 패치·PostgreSQL·Spring Data JPA와 Specification·Gradle Groovy DSL을 확정했고 후속 대화에서 검증 도구 Node.js 24를 확정했다. Gradle은 사용자의 기존 경험을 반영한 선택이었다. 당시 JDK 배포판, DB·Gradle 세부 버전, 마이그레이션·테스트 도구, 웹·수집기는 미정이었다. 이전 PostgreSQL 17 및 클라이언트 후보를 승인된 기술로 해석하지 않는다. 대안과 결정 순서는 [기술 결정 기록](../decisions/2026-10-21-tech-stack-decisions.md), 현재 고정 버전의 원본은 [개발 환경 안내](../../development/setup.md)를 참조한다.

## 3. 사람과 권한

운영자는 사용자 한 명으로 승인했고 친구별 전적 공개 동의는 서면으로 확보하기로 했다. 온라인 동의 화면은 초기 범위에서 제외했다. 권한별 동작은 [사용자 구분](../../spec.md#제품-범위와-사용자)과 [인증·개인정보](../../spec.md#인증과-개인정보)에 모았다.

## 4. 참가자 등록과 계정

### 확정 사항

사전 등록된 사람만 참가하는 경기, 단일 LoL 계정, 경기마다 확인하는 실제 포지션을 승인했다. 친구 목록 조회를 등록 절차로 요구하지 않는다는 후속 사용자 결정도 유지한다. 상세 기준은 [참가자와 포지션 관리](../../spec.md#참가자와-포지션-관리)를 참조한다.

### 설계 기본안

안정적인 내부 식별자, 이름과 식별자의 분리, 운영자가 지정하는 추가 가능 포지션, 비활성화 후 과거 연결 보존은 기획 승인에 포함됐다. 당시에는 PUUID를 우선 검토하는 표현이었으며, 현재 확정된 연결 방식은 [참가자와 포지션 관리](../../spec.md#참가자와-포지션-관리)에 있다.

## 5. 초기 포지션과 초기 실력

과거 내전·솔로랭크를 초기 포지션 제안에만 쓰고 운영자가 확인한다는 방향은 사용자 확정이다. 초기 실력의 입력 범위와 보정식은 기술 설계에 위임했다. 현재 제안 기준은 [초기 포지션 참고 자료](../../spec.md#초기-포지션-참고-자료), 실력 보정은 [포지션별 실력 보정](../../spec.md#포지션별-실력-보정)을 따른다.

**2026-10-22 실측 보완:** 다른 참가자 1명의 솔로랭크 6경기를 조회해 C11을 PASS로 기록했다. 두 종류의 PUUID가 달라 Riot ID를 Account-v1로 해석했고, 조기 종료를 제외한 4경기를 참고 표본으로 남겼다. 이 표본으로 주·부 포지션을 확정하지 않았고 전체 LCU 판정은 HOLD였다. 실제 경로·응답 근거는 [공식 API 검증 기록](../../validation/riot-solo-reference.md)에 있다.

## 6. 수집자 인증

운영자가 발급한 개인별 코드와 별도 기기 인증을 쓰기로 승인했다. 코드 수명, Windows 보호 저장과 재등록은 기술 설계의 책임이었다. 실제 계정 자동 인식과 서버 권한을 구분하는 상세 규칙은 [수집자 기기 인증](../../spec.md#수집자-기기-인증), 요청 형식은 [인증 계약](../../contracts/api.md#인증과-권한)을 참조한다.

## 7. 경기 수집과 등록

### 사용 흐름

기획 보완에서 ‘과거 경기 조회 → 서버 임시 저장 → 내전 여부와 실제 포지션 확인 → 별도 등록’ 순서를 사용자와 확정했다. 실행 시점에 관계없이 버튼으로 조회한다는 요구는 유지한다. 현재 단계별 동작은 [경기 수집·확인·등록](../../spec.md#경기-수집확인등록)에 있다.

기존 Windows 자료에서 사용자 설정 경기 3건의 목록·상세를 확보했다. 이 사실은 모든 과거 경기의 보관 기간이나 반영 시간을 검증했다는 뜻이 아니다. 2026-10-23 사용자는 새 경기의 조회 시점 비교·반영 시간·과거 범위 추가 측정을 제외했다([D22](../decisions/2026-10-22-overnight-decisions.md#d22--2026-10-23-사용자-요청에-따른-검증-작업-제외)).

### 등록 검증 기본안

사전 등록·참가 여부·실제 포지션을 서버에서 검증하고 누락값을 0으로 대체하지 않는 기본안을 승인했다. 필수 원본 필드는 실측 후 정하도록 남겼다. 현재 제품 조건은 [적격성과 원본 검사](../../spec.md#적격성과-원본-검사), 관찰한 응답 조합은 [LCU 원본 계약](../../contracts/api.md#lcu-원본을-정규화하는-규칙)을 따른다.

## 8. 서버 장애와 전송·등록 대기

전송 대기·확인 대기·등록 대기를 구분하고 재시작 뒤 복구하는 방향을 승인했다. 간격, 저장 형식, 보관 정리는 기술 설계에 맡겼다. 확정된 후속 수치는 [오프라인 대기와 재시도](../../spec.md#오프라인-대기와-재시도)에서 관리한다.

## 9. 중복 등록과 취소된 경기

동일 경기 재전송이 기존 기록·포지션·집계를 바꾸지 않으며 취소 경기를 자동 복원하지 않는 기본안은 사용자 승인에 포함됐다. 현재 중복·동시 요청 처리는 [중복·동시 요청·취소](../../spec.md#중복동시-요청취소)를 참조한다.

## 10. 공개 경기 상세와 개인 통계

양 팀 10명 비교와 사람별 누적 통계 제공을 승인했다. 챔피언 피해를 기본 표시로 쓰는 것은 승인된 기본안이고 조회 필터·화면 형식은 후속 설계에 남겼다. 현재 표시 항목과 누적 KDA 기준은 [공개 전적과 통계](../../spec.md#공개-전적과-통계)에 둔다.

## 11. 경기별 개인 활약 평가

### 확정한 방향

KDA 단독 평가를 피하고 실제 포지션별로 평가하며 패배자도 경기 1위가 될 수 있게 하자는 사용자 방향을 확정했다. 아래 초기 가중치도 승인 범위였다. 현재 계산 기준은 [경기별 활약 점수](../../spec.md#경기별-활약-점수)에 있다.

### 초기 가중치

2026-10-21 사용자가 승인한 일곱 항목 가중치는 현재 [포지션별 전체 가중치](../../spec.md#포지션별-전체-가중치)로 옮겼다. 2026-10-24 D24에서도 이 바깥 가중치는 유지했다. 이 기록을 향후 가중치 변경에 대한 포괄 승인으로 해석하지 않는다.

### 지표 구성

당초 항목 구성을 기술 설계로 구체화했다. 목표물 항목의 이전 설계는 미드·원딜에서 포탑 피해와 목표물 피해를 50:50으로 섞는 안이었다. 2026-10-22 [D04](../decisions/2026-10-22-overnight-decisions.md#d04--c07-hold와-중복-가중을-피하는-잠정-정책)는 중복 가중을 피하려고 단일 지표를 임시 채택했고, 2026-10-24 사용자는 [D24](../decisions/2026-10-22-overnight-decisions.md#d24--2026-10-24-목표물-공격-평가-기준-사용자-확정)에서 이를 최종 선택했다. 탑은 분당 포탑 피해, 다른 네 포지션은 분당 목표물 피해다. 이전 혼합안을 현재 승인으로 남기지 않는다. 전체 지표 표는 [항목 내부 지표](../../spec.md#항목-내부-지표)를 참조한다.

### 점수화 원칙

같은 포지션끼리 보수적으로 비교하되 함수·혼합 비율·보정 강도·극단값·동점 표시의 정확한 수치는 기술 설계에 위임했다. 현재 환산식은 [같은 포지션의 지표 환산](../../spec.md#같은-포지션의-지표-환산), 표시 기준은 [누적 랭킹과 점수 표시](../../spec.md#누적-랭킹과-점수-표시)에 있다.

### 평가의 한계

당시 검토는 최종 통계로 탱킹·희생·강타 판단을 모두 설명할 수 없고 챔피언 성향 차이를 완전히 보정하지 못한다는 한계를 전제로 했다. 확장 지표는 안정적인 수집과 의미 확인 후 검토하기로 했다. 현재 설명은 [평가가 설명하지 못하는 기여](../../spec.md#평가가-설명하지-못하는-기여)를 따른다.

## 12. 누적 랭킹

3경기부터 정식 랭킹에 넣고 1–2경기는 평가 중으로 표시하는 기준, 시즌 없이 평균을 사용하고 모임 평균 5경기분(k=5)을 섞는 기본안은 사용자 승인이다. 후속 정규화의 기술 위임과 구분한다. 공식과 표시·0경기 처리는 [누적 랭킹과 점수 표시](../../spec.md#누적-랭킹과-점수-표시)에 모았다.

## 13. 평가 기준 변경과 재계산

새 기준으로 과거 유효 경기까지 함께 계산하고 원본·변경 이력을 보존하는 방향을 승인했다. 계산 중 공개·실패 복구의 구체적 방법은 당시 미정이었다. 현재 기준은 [변경·재계산·일관성](../../spec.md#변경재계산일관성)을 참조한다.

## 14. 팀 추천

### 사용 범위

공개 화면에서 10명을 골라 최대 세 팀 후보를 참고하는 범위를 승인했다. 현재 입력·출력 범위는 [팀 편성용 실력과 팀 추천](../../spec.md#팀-편성용-실력과-팀-추천)에 있다.

### 추천 원칙

가능 포지션을 지키고 균형을 먼저, 선호를 그다음으로 보는 방향과 같은 선수 구성 중복 제거는 승인됐다. 균형 허용 차이와 선호 비용 수치는 기술 설계에 남겼다. 현재 수치는 [후보 선택 규칙](../../spec.md#후보-선택-규칙)을 따른다.

### 관여하지 않는 범위

추천 후 선수 교환·로비 조작·선택 추적은 초기 범위에서 제외했다. 추천을 실제 경기 포지션으로 간주하지 않는 기준도 유지한다. [현재 범위 제외](../../spec.md#범위-제외)를 참조한다.

## 15. 비정상 경기와 운영자 수정

문제 경기는 확인 대기로 두거나 운영자가 취소하고 수정 이력을 보존하는 방향을 승인했다. 자동 판정과 수집자의 등록 후 수정은 제외했다. 현재 적격성은 [적격성과 원본 검사](../../spec.md#적격성과-원본-검사), 정정 권한·결과는 [공개 기록과 관리자 정정](../../contracts/api.md#공개-기록과-관리자-정정)을 따른다.

## 16. 운영자 코드 인증

단일 운영자에게 코드로 새 브라우저 인증을 추가하고, 모든 인증을 잃으면 집 서버 명령으로 복구하는 방식은 사용자 확정이다. 만료·시도 제한·위조 요청 방어의 수치는 기술 설계에 위임했다. 현재 [운영자 인증과 복구](../../spec.md#운영자-인증과-복구) 및 [로컬 복구 실행법](../../development/setup.md#최초-관리자와-복구)을 참조한다.

## 17. 저장·운영 기본안

집 서버 운영·영속 저장·PC 밖 백업·복원과 최소 감사 이력은 승인된 설계 기본안이다. 백업 주기·위치·보관 기간은 이때 결정하지 않았고 유료 서비스 구매도 승인하지 않았다. 현재 설계는 [설치·운영 설계](../../spec.md#설치운영-설계), 미검증 범위는 [진행 상태](../../status.md#남은-작업-순서)에 있다.

## 18. 개발 초기에 반드시 확인할 사항

초기에는 LCU 실기 통과를 본 구현의 선행 조건으로 뒀다. 2026-10-22 사용자가 [D01](../decisions/2026-10-22-overnight-decisions.md#d01--hold-중-단계-13의-조건부-draft-개발)의 임시 개발을 허용했지만 실기 PASS나 운영 완료 승인은 아니었다.

기존 Windows G1–G3에서 C03(10명·팀·승패·시간), C06(통계·챔피언·아이템), C09(세 경기 구조), 공식 경로 C11을 확인했다. G1을 대표 화면으로 쓰고 G2·G3 추가 화면, 재시작 후 같은 경기 조회, 다른 PC의 경기 키 대조는 사용자 결정으로 생략했다. 생략을 실측 PASS로 기록하지 않는다.

**2026-10-23 보완:** C01/C02/C10과 T15는 사용자가 제외했다([D22](../decisions/2026-10-22-overnight-decisions.md#d22--2026-10-23-사용자-요청에-따른-검증-작업-제외)). **2026-10-24 보완:** C07 포함 관계 조사와 D24 지표 선택을 마쳤다. 당시 새 계산 버전 반영·전 경기 재계산·검증은 남았다. 최신 상태는 [진행 상태](../../status.md), 당시 환경·근거는 [실측 보고서](../../validation/lcu-report.md)를 확인한다.

실시간 선행 수집이나 수동 기록으로 요구를 대체해야 한다면 범위를 먼저 확인한다는 원래 진행 조건은 유지한다.

## 19. 주요 수용 기준

이 절은 기획 승인 당시 사용자 행동별 수용 기준을 정리한 위치다. 현재 동작의 세부 표는 중복 보관하지 않으며 [제품 명세](../../spec.md)의 해당 절을 따른다.

검증 연결은 기록·중복·권한(T01–T04), 오프라인 순차 재시도(T05–T07), 평가·누적·팀·공개/관리 화면(T08–T12), 설치·운영(T13–T14)로 나눴다. 구체적인 테스트 이름과 미실행 수용 절차는 [개발 계획의 작업별 구현 계획](../plans/2026-10-21-lol-inhouse-development-plan.md#4-작업별-구현-계획)에 보존했다. C01/C02/C10/T15의 후속 제외를 다시 완료 조건으로 넣지 않는다.

## 20. 범위에 포함하지 않는 것

초기 제품의 제외 목록은 [현재 제품 범위 제외](../../spec.md#범위-제외), 이후 사용자 검증 제외와 미확인 사실은 [진행 상태](../../status.md#범위-제외와-미확인-사실)에 모았다. 2026-10-23 D22의 범위 축소를 미완료 요구나 성공 결과로 바꾸지 않는다.

## 21. 승인된 기본안과 이후 작업

2026-10-21 사용자는 본문의 ‘설계 기본안’까지 승인했다. 소환사의 협곡 5포지션, 주·부에서 시작하는 가능 포지션, 챔피언 피해 기본 표시, 누적 평균과 k=5, 취소 자료 보존·복원 UI 제외, 백업·인증 폐기·변경 이력이 그 범위다.

사용자와 확정한 서버 구성 이외의 기술 제품은 후속 대화로 정하기로 했다. 데이터 물리 구조, 세부 계산·실력 보정, 인증 수명, 로컬 저장·재시도, 화면 배치, 배포·백업 세부 절차는 개발자에게 위임했다. 제품 범위 변경은 위임에 포함되지 않는다. 대안별 승인 경계는 [기술 선택 기록](../decisions/2026-10-21-tech-stack-decisions.md)에 남긴다.

당시 [개발 계획](../plans/2026-10-21-lol-inhouse-development-plan.md)을 작성했고 이후 도구·Windows 자료와 단계 1–3 임시 구현을 확보했다. 2026-10-24까지의 조사·선택은 위 §18의 날짜 기록이며 최신 작업 순서는 [현재 진행 상태](../../status.md#남은-작업-순서) 한 곳에서 관리한다.

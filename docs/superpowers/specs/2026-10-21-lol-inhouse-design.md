# LoL 내전 기록·평가·팀 추천 서비스 기획서

- 작성일: 2026-10-21
- 상태: 사용자 승인 완료 — 제안한 기본안까지 포함하여 확정
- 보완 확정: 과거 경기 조회 버튼 → 서버 임시 저장 → 수집자 확인 후 등록. 동일 경기 재전송은 기존 기록과 집계를 변경하지 않는다.
- 승인 내용: LCU 실기 검증을 첫 단계로 하는 개발 계획 작성. 이 승인은 실기 검증이나 구현이 이미 수행되었다는 뜻이 아니다.
- 기술 결정 (2026-10-21): 서버 Java 25 + Spring Boot 4.1.x의 최신 정식 패치 버전, 서버 DB PostgreSQL, DB 접근과 동적 조회 Spring Data JPA + Specification, 서버 빌드 Gradle + Groovy DSL(`build.gradle`)을 사용자와 확정. 후속 대화에서 LCU 검증 도구는 Node.js 24로 확정했으며 Windows 실측은 추후 진행한다. 나머지 기술 스택은 대화하며 결정한다.
- 목적: 대화에서 정한 제품 범위와 동작을 보존하고, 이후 기술 설계와 개발 계획의 기준으로 사용한다.
- 기술 선택 근거: [기술별 대안과 장단점 및 결정 과정](../decisions/2026-10-21-tech-stack-decisions.md).
- 이 문서는 구현 완료나 LCU 실기 검증 완료를 의미하지 않는다.

## 1. 만들려는 서비스

약 30명의 친구가 진행하는 리그 오브 레전드 5대5 사용자 설정 게임을 기록하는 서비스다. 각 경기의 참가자는 달라질 수 있으며, 모임 전체로는 2주에 3~6경기 정도 진행한다.

운영자가 경기에 참여하지 않아도 참가자 한 명이 Windows 수집 프로그램의 ‘과거 경기 조회’ 버튼으로 기록을 가져와 서버에 임시 저장하고, 확인한 경기를 모임의 내전으로 등록할 수 있어야 한다. 수집 프로그램의 실행 시점은 경기 전후와 무관하게 한다. 친구들은 공개 웹사이트에서 경기별 전적, 사람별 누적 통계, 경기별 활약 순위와 누적 랭킹을 확인한다. 경기 전에는 참가자 10명을 선택하여 균형이 비슷한 팀 구성 후보를 최대 3개 추천받는다.

핵심 목표는 기록을 놓치지 않는 것, 등록한 내전만 집계하는 것, 포지션별 역할을 고려하여 평가하는 것, 운영자 없이도 친구들이 내전을 진행할 수 있게 하는 것이다.

## 2. 확정한 운영 환경

| 구분 | 결정 |
| --- | --- |
| 개발 환경 | macOS |
| 수집 프로그램 지원 환경 | Windows만 지원 |
| 실기 테스트 | 사용 가능한 실제 Windows PC에서 진행 |
| 서비스 운영 | 집의 Windows 데스크탑에서 Docker 사용 |
| 외부 접속 | Cloudflare Tunnel을 통해 웹사이트와 API 제공 |
| 공개 조회 | 로그인 없이 누구나 가능 |
| 운영자 접근 | 집 밖에서도 웹사이트에서 관리 가능 |
| 비용 방향 | 기존 장비를 활용하여 유지 비용 최소화 |

수집 프로그램의 Windows 지원과 서버의 실행 환경은 별개다. 2026-10-21 기술 논의에서 서버는 Java 25 + Spring Boot 4.1.x의 최신 정식 패치 버전, 서버 DB는 PostgreSQL, DB 접근 방식은 Spring Data JPA + Specification, 서버 빌드는 기존 사용 경험에 따라 Gradle + Groovy DSL(`build.gradle`)로 확정했다. 일반 저장·변경은 JPA, 선택적 조건을 조합하는 동적 조회는 Specification을 사용한다. 서버 프로젝트 생성 시 최신 정식 Spring Boot 4.1.x 패치를 확인하고 정확한 버전으로 고정한다. LCU 검증 도구는 후속 대화에서 Node.js 24로 확정했다. JDK 배포판·PostgreSQL·Gradle 세부 버전, 서버 마이그레이션·테스트 도구, 웹·수집기는 사용자와 이어서 결정한다. Gradle은 Java 25 실행과 Spring Boot 4.1 호환 조건에 맞춰 9.1.0 이상의 9.x 범위에서 선택한다. 기존 개발 계획의 나머지 기술 선택은 제안이며 사용자 확정으로 간주하지 않는다.

## 3. 사람과 권한

초기 운영자는 사용자 본인 한 명이다. 여러 브라우저나 기기에서 인증하더라도 운영자가 여러 명 생기는 것은 아니다.

| 사용자 | 가능한 작업 |
| --- | --- |
| 일반 방문자 | 경기 조회, 참가자 통계·랭킹 조회, 등록된 참가자로 팀 추천 요청 |
| 인증된 수집자 | 자신이 참가한 경기를 가져오고, 결과와 실제 포지션을 확인하여 등록 |
| 운영자 | 참가자 관리, 포지션·초기 실력 관리, 등록 코드 발급·폐기, 등록된 경기의 포지션 수정·등록 취소, 평가 기준 관리 |

수집자는 등록 완료 후 경기의 포지션을 바꾸거나 등록을 취소할 수 없다. 공개 웹 기능을 사용한다고 회원 정보나 등록된 경기의 수정 권한이 생기지 않는다. 서버가 요청마다 권한을 확인한다.

친구별 전적 공개 동의는 서면으로 확보한다. 온라인 동의 화면이나 동의 요청 기능은 초기 범위에 포함하지 않는다.

## 4. 참가자 등록과 계정

### 확정 사항

- 운영자가 미리 등록한 참가자끼리 진행한 경기만 등록한다.
- 새로운 사람이 참여하려면 운영자가 먼저 참가자로 등록한다.
- 별도 게스트 기능과 여러 LoL 계정의 전적 통합은 지원하지 않는다.
- 참가자마다 주 포지션, 부 포지션, 팀 편성용 초기 실력값을 관리한다.
- 실제 포지션은 경기마다 달라질 수 있다.
- 참가자 등록과 수집 프로그램 사용 등록은 별개다. 10명 모두 수집 프로그램을 설치할 필요는 없다.

### 설계 기본안

- 내부 참가자 ID와 LoL 계정의 안정적인 식별자를 연결한다. PUUID를 우선 검토하고, 표시 이름 변경으로 다른 사람이 되지 않도록 한다.
- 공개 화면의 이름 표기와 내부 계정 식별값을 구분한다.
- 주·부 포지션 이외에 실제로 가능한 포지션을 명시할 수 있게 한다. 처음에는 주·부 포지션만 가능한 것으로 취급하고, 추가 가능한 포지션은 운영자가 지정한다. 플레이 기록이 없다는 이유로 불가능한 포지션이라고 자동 단정하지 않는다.
- 참가자를 비활성화하더라도 과거 경기의 연결과 기록은 유지한다. 비활성화된 참가자는 새 팀 추천의 선택 대상에서 제외한다.

## 5. 초기 포지션과 초기 실력

초기 주·부 포지션을 정할 때 과거 내전과 솔로랭크 기록을 참고한다. 시스템이 제안한 결과를 운영자가 확인하고 수정·관리한다. 운영자가 정한 값은 이후 기록 수집 때문에 자동으로 덮어쓰지 않는다.

솔로랭크 기록은 초기 포지션을 정하기 위한 참고 자료로만 사용한다. 모임의 누적 전적, 활약 점수, 누적 랭킹, 팀 편성용 실력 보정의 경기 자료에는 넣지 않는다.

팀 편성용 초기 실력값은 운영자가 직접 지정한다. 등록된 내전 기록이 쌓이면 해당 기록의 비중을 점차 높여 보정한다. 이 초기 실력값은 공개 누적 랭킹에 영향을 주지 않는다.

초기 실력값의 입력 범위, 포지션별 기록이 적을 때의 보정 방법, 실력 갱신 공식은 기술 설계에 맡긴다. 단, 다음 조건을 만족해야 한다.

- 기록이 적을 때 한 경기만으로 팀 편성용 실력값이 크게 흔들리지 않는다.
- 실제로 플레이한 포지션을 고려한다.
- 등록 취소된 경기와 솔로랭크 기록은 보정에서 제외한다.
- 운영자가 지정한 초기값과 경기에서 계산한 값을 구분해서 보관한다.
- 공개 활약 랭킹과 팀 편성용 실력값은 서로 다른 목적의 값이다.

## 6. 수집자 인증

1. 운영자가 참가자별 등록 코드를 발급한다.
2. 수집자가 프로그램에 최초 한 번 코드를 입력한다.
3. 서버가 코드에 연결된 참가자의 수집 권한을 확인하고, 프로그램에 보관할 별도의 인증 정보를 발급한다.
4. 이후에는 별도 아이디·비밀번호 입력 없이 저장된 인증 정보를 사용한다.
5. LCU로 현재 롤 클라이언트에 로그인된 계정을 자동 인식한다.

서버 인증의 근거는 운영자가 발급한 코드로 얻은 수집 권한이다. LCU에서 얻은 계정 이름이나 식별값만으로 서버 로그인을 허용하지 않는다. Riot 공식 소셜 로그인이나 RSO를 사용하는 방식도 아니다.

설계 기본안으로, 코드에 연결된 참가자와 현재 LCU 계정이 다르거나 현재 계정이 해당 경기의 참가자가 아니면 등록을 막고 이유를 안내한다. 기존 권한을 다른 계정으로 자동 이전하지 않는다.

코드는 일회용이며 유효기간을 둔다. 이후 사용되는 인증 정보는 폐기할 수 있어야 한다. Windows에 저장하는 인증 정보의 보호와 재설치·기기 변경 시 재등록 절차는 기술 설계에 포함한다.

## 7. 경기 수집과 등록

### 사용 흐름

1. 참가자 중 한 명이 롤 클라이언트에 로그인된 Windows PC에서 수집 프로그램을 실행한다.
2. 수집자가 ‘과거 경기 조회’ 버튼을 누르면 프로그램이 그 시점에 LCU에서 조회 가능한 완료 경기 목록과 상세 결과를 가져온다.
3. 프로그램은 수집자가 참가한 등록 회원 10명의 사용자 설정 5대5 경기 자료를 서버에 전송한다. 신규 자료는 `확인 대기`로 임시 저장한다. 조건에 맞지 않는 경기는 이유를 표시하고 모임 전적 저장 대상에서 제외한다. 솔로랭크는 별도의 초기 포지션 참고 흐름에서만 다룬다.
4. 이미 저장된 동일 경기는 기존 자료를 유지하고 `확인 대기 / 등록 완료 / 등록 취소` 중 현재 상태를 응답한다.
5. 수집 프로그램은 확인 대기 경기의 참가자 10명, 팀 구성, 경기 결과와 기록을 표시한다.
6. 해당 경기에 참가한 인증된 수집자가 모임 내전 여부와 참가자별 실제 포지션을 확인·수정하고 ‘내전 등록’을 누른다.
7. 서버가 확인 대기 경기를 등록 완료로 전환하면 공개 전적과 관련 통계·평가에 반영한다. 임시 저장만으로는 반영하지 않는다.

새로운 경기 조회는 버튼을 누른 시점에 시작하며, 프로그램 시작이나 경기 시작·종료 이벤트에 의존하지 않는다. 경기 전에 켜 두어도, 종료 후 처음 켜도 같은 조회 절차를 사용한다. 조회 시에는 LCU에 연결 가능한 롤 클라이언트가 필요하다. 이미 확보한 자료의 서버 전송 재시도는 별도로 동작한다.

실기 검증의 핵심은 버튼 요청 시 과거 경기 기록이 실제로 제공되는지와 조회 가능한 범위다. 현재 LCU의 사용자 설정 경기 조회 범위와 보관 기간은 확인되지 않았으므로, 무제한 과거 경기 조회나 반드시 복구 가능한 기간은 약속하지 않는다.

조회된 적격 경기의 서버 임시 저장과 모임 내전 등록은 별개다. 확인 대기 자료는 해당 경기의 인증된 참가자와 운영자만 조회하며, 공개 전적·누적 통계·랭킹·팀 실력 보정에는 포함하지 않는다. 다른 사용자 설정 게임도 모임 내전으로 확인하지 않으면 통계에 섞이지 않는다.

### 등록 검증 기본안

- 5대5 사용자 설정 경기이며 참가자 10명이 모두 모임에 등록되어 있어야 한다.
- 현재 수집자의 계정이 경기 참가자에 포함되어 있어야 한다.
- 같은 참가자가 중복으로 나타나거나 경기·팀 정보가 모순되는 자료는 등록하지 않는다.
- 양 팀의 실제 포지션을 확인한 뒤 평가한다. 초기 서비스는 팀마다 탑·정글·미드·원딜·서포터 한 명씩인 경기를 대상으로 한다는 설계 가정을 둔다.
- 원본 경기 수치는 자동 수집한다. 수집자가 킬, 피해량, 골드 등을 임의 입력하거나 수정하는 기능은 두지 않는다.
- 핵심 정보가 누락되거나 파싱에 실패한 경우 0으로 바꾸지 않고 등록을 보류하며 확인이 필요한 이유를 표시한다.
- 등록에 필수인 항목은 실제 수집 검증 후 정의한다. 검증되지 않은 확장 지표를 필수 조건으로 삼아 모든 등록을 막지 않는다.

## 8. 서버 장애와 전송·등록 대기

‘과거 경기 조회’로 자료를 가져왔지만 서버에 접속하지 못했다면 PC에 `전송 대기`로 보관한다. 서버 임시 저장 후에는 `확인 대기`, 수집자가 내전 여부와 포지션을 확인했지만 등록 확정 요청이 전달되지 않았으면 `등록 대기`로 구분한다.

- 프로그램을 종료하거나 PC를 재시작해도 대기 기록을 유지한다.
- 프로그램이 실행된 상태에서 연결이 복구되면 자동으로 재시도한다.
- 프로그램이 종료되어 있었다면 다음 실행 시 재시도한다.
- 서버에 등록이 완료되기 전에는 공개 통계와 랭킹에 반영하지 않는다. 임시 저장 성공을 등록 완료로 안내하지 않는다.
- 사용자가 조회한 적격 경기 자료는 자동으로 임시 저장 요청을 전송한다. 사용자가 ‘내전 등록’을 누르지 않은 경기는 자동 등록하지 않는다.
- 오프라인에서 결과와 포지션을 확인했다면 자료 전송과 등록 확정 요청을 순서대로 보관한다. 연결 복구 시 임시 저장이 확인된 뒤에만 등록 확정을 요청한다.
- 서버가 저장했으나 응답만 유실된 경우에도 재시도로 중복 경기를 만들지 않는다.

연결 오류와 데이터·권한 오류는 구분한다. 데이터 오류, 인증 폐기, 미등록 참가자 등의 문제는 무한 재시도하지 않고 `확인 필요`로 안내하는 것을 기본안으로 한다. 재시도 간격·백오프, 로컬 저장 형식과 보관 정리는 기술 설계에 맡긴다.

경기 조회 자체가 실패하여 가져오지 못한 자료는 전송 대기로 저장할 수 없다. 서버 업로드 실패와 LCU 조회 실패를 사용자에게 구분해서 보여준다. 조회 버튼을 반복해서 눌러도 같은 경기의 미완료 전송 요청은 로컬에서 합친다.

## 9. 중복 등록과 취소된 경기

같은 경기를 여러 참가자가 조회·전송하거나 같은 프로그램이 재전송해도 서버에 한 경기만 저장한다. 지역·플랫폼과 경기 식별자를 포함한 안정적인 키를 사용하고, 동시에 요청되더라도 서버에서 중복을 막는다. 임시 저장·등록 완료·등록 취소 전체 상태에 같은 키의 유일성을 적용한다.

이미 저장된 경기 자료가 다시 들어오면 신규 저장·덮어쓰기·집계 변경·재계산을 수행하지 않는다. ‘이미 저장됨’과 현재 상태를 응답하여 수집기가 같은 요청을 계속 재시도하지 않게 한다. 최초의 명시적 내전 등록 확정은 중복 자료 전송과 다른 동작이며, 확인 대기 상태를 등록 완료로 한 번만 전환한다.

이미 등록된 경기와 재전송된 경기의 포지션이 다르더라도 수집자의 재전송으로 기존 포지션을 바꾸지 않는다. 변경은 운영자만 할 수 있다.

취소된 경기를 일반 수집자가 다시 전송해도 자동으로 복원하지 않는다. 등록 취소 상태와 최소 식별 정보는 보관한다. 초기 버전에는 별도 취소 복원 기능을 포함하지 않는 것을 기본안으로 한다.

## 10. 공개 경기 상세와 개인 통계

경기 상세에서는 양 팀 5명씩의 기록을 한눈에 비교할 수 있어야 한다.

| 경기 단위 | 참가자 단위 |
| --- | --- |
| 경기 일시, 경기 시간, 양 팀, 승패 | 참가자, 사용 챔피언, 최종 확인된 포지션 |
| 참가자 10명의 활약 순위 | 킬·데스·어시스트와 KDA |
| 적용된 평가 기준 | 가한 피해량, 받은 피해량, CS, 획득 골드 |
| | 시야 점수, 최종 아이템, 개인 활약 점수 |

가한 피해량의 기본 표시는 챔피언 대상 피해량으로 하는 것을 설계 기본안으로 한다. 평가에 쓰는 오브젝트·포탑 피해량은 별도 항목으로 구분한다. 받은 피해량과 아이템은 전적에 표시하지만 그 자체로 평가 가산점을 주지 않는다.

개인별로 참가 경기 목록, 경기 수, 승·패·승률, 누적 K/D/A 및 KDA, 포지션별·챔피언별 기록, 누적 활약 점수와 랭킹을 확인한다. 조회 필터와 통계 표시 형식은 기술·화면 설계에서 정한다. 서로 다른 경기의 KDA 비율을 단순 평균한 값을 누적 KDA로 잘못 표시하지 않는다.

웹사이트 조회에는 로그인하지 않는다. 원본 LCU 응답과 내부 인증·식별 자료 전체를 공개하는 것은 공개 전적 제공에 포함되지 않는다.

## 11. 경기별 개인 활약 평가

### 확정한 방향

- 참가자 10명의 경기별 활약 순위를 제공한다.
- 최종 확인된 실제 포지션을 기준으로 평가한다.
- KDA가 높다는 이유만으로 좋은 평가를 주지 않는다.
- 딜러는 딜량과 성장, 정글은 킬 관여와 오브젝트 기여, 서포터는 시야와 어시스트를 중요하게 본다.
- 승패는 보조 요소로만 사용한다. 패배한 팀의 참가자도 경기 전체 1위가 될 수 있다.
- 아래 가중치를 초기 기준으로 적용하고 실제 내전 몇 경기의 결과를 확인하면서 조정한다.

### 초기 가중치

각 행의 합은 100%다.

| 포지션 | 피해량 | 성장 | 교전 관여 | 시야 | 오브젝트 | 사망 보정 | 승패 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 탑 | 20 | 25 | 15 | 10 | 20 | 5 | 5 |
| 정글 | 10 | 15 | 35 | 10 | 20 | 5 | 5 |
| 미드 | 30 | 25 | 20 | 5 | 10 | 5 | 5 |
| 원딜 | 40 | 25 | 15 | 5 | 5 | 5 | 5 |
| 서포터 | 5 | 0 | 40 | 40 | 5 | 5 | 5 |

### 지표 구성

| 항목 | 기본 지표 | 해석과 제한 |
| --- | --- | --- |
| 피해량 | 분당 챔피언 대상 피해량, 팀 내 해당 피해량 비중 | 미니언 등에 가한 전체 피해량과 구분 |
| 성장 | 분당 CS, 분당 획득 골드 | 서로 관련된 지표를 성장 항목 안에서 묶음 |
| 교전 관여 | 킬 관여율 `(킬 + 어시스트) / 팀 전체 킬` | 서포터는 분당 어시스트도 반영, KDA 별도 중복 가산 없음 |
| 시야 | 분당 시야 점수 중심 | 와드 제거 수는 보조 자료로 확인 |
| 오브젝트 | 개인 오브젝트·포탑 피해량 | 정글의 오브젝트 공격, 탑의 포탑 압박 등을 일부 반영 |
| 사망 보정 | 포지션·경기 시간을 고려한 사망 횟수 | 적게 죽었다는 이유만으로 높은 총점이 되지 않도록 작은 비중 |
| 승패 | 승리 보너스 | 100점 척도에서 최대 5점 차이 |

### 점수화 원칙

- 원딜과 서포터의 원시 딜량을 직접 비교하지 않는다. 같은 포지션의 기준으로 각 항목을 공통 척도로 환산한다.
- 비교 기준에는 등록된 모임 내전만 사용한다. 솔로랭크와 운영자 초기 실력값을 끌어오지 않는다.
- 기록이 적을 때는 같은 경기의 상대 포지션과의 비교를 보수적으로 활용한다. 기록이 쌓이면 모임의 같은 포지션 기록을 더 많이 참고한다.
- 한 지표의 극단값이 전체 점수를 지배하지 않도록 항목별 상한을 둔다.
- 팀 전체 킬·피해량 등이 0인 경우 비율을 무한대나 허구의 100%로 만들지 않는다. 0인 실제 기록과 누락된 기록은 구분한다.
- 정확한 표준화 함수, 항목 내부의 세부 비율, 초기 표본 보정 강도, 극단값 처리 수치와 동점 표시는 실제 수집 샘플을 토대로 기술 설계에서 정한다.
- 이 점수는 모임이 정한 사후 활약 평가이며 Riot 공식 등급이나 랭크 추정치로 표시하지 않는다.

### 평가의 한계

오브젝트 피해량만으로 용·바론 확보를 위한 견제, 시야 장악, 강타 판단을 모두 알 수 없다. 팀의 용·바론 획득 수를 정글러 혼자의 성과로 그대로 가산하지 않는다.

받은 피해량이 많다는 이유로 탱킹을 잘했다고 판정하지 않는다. 최종 결과 수치만으로 좋은 희생과 불필요한 사망을 구분하기도 어렵다. 같은 포지션 안의 탱커·딜러·유틸형 챔피언 차이는 초기안에서 완전히 보정하지 못한다.

개인 오브젝트 참여 이벤트, 특정 시점의 성장 차이, 아군 회복·보호막·CC 기여 등의 확장 지표는 실제 사용자 설정 경기에서 안정적으로 수집되고 의미가 확인된 뒤 검토한다. 기본 기능을 경기 중 실시간 수집에 의존하게 바꾸지 않는다.

## 12. 누적 랭킹

- 시즌을 나누지 않고 등록된 전체 내전을 계속 누적한다.
- 승패보다 포지션별 개인 활약을 더 중요하게 반영한다.
- 1~2경기 참가자는 `평가 중`으로 표시하고, 3경기부터 정식 누적 랭킹에 포함한다.
- 참가 경기 수를 함께 보여준다.
- 적은 경기 수의 점수는 모임 평균 쪽으로 보정하고, 경기 수가 늘면 개인 기록 비중을 높인다.
- 3경기가 되었다고 표본 보정을 갑자기 없애지 않는다.
- 등록 취소로 경기 수가 3 미만이 되면 다시 `평가 중`으로 표시한다.
- 정식 누적 랭킹에 들지 않아도 개인 전적과 경기별 활약 순위는 확인할 수 있다.

경기별 점수의 평균을 바탕으로 하는 것을 설계 기본안으로 한다. 많이 참가했다는 이유만으로 점수를 단순 합산하여 순위를 올리지 않는다.

확정한 초기 보정식은 다음과 같다. 모임 평균을 섞는 강도는 `k=5`로 시작한다.

`누적 점수 = (본인 경기 점수 합계 + 모임 평균 점수 × k) / (본인 경기 수 + k)`

모임 평균은 같은 평가 기준으로 계산한 유효 내전 참가 기록의 평균으로 정의하는 것을 기본안으로 한다. 경기 수 0인 참가자는 점수를 만들어 순위에 넣지 않는다.

## 13. 평가 기준 변경과 재계산

평가 기준을 바꾸면 과거 경기의 개인 점수·활약 순위와 누적 랭킹도 새 기준으로 함께 재계산한다. 원본 경기 기록은 유지한다. 등록 취소된 경기는 다시 포함하지 않는다.

평가 기준의 변경 이력을 보관하고, 계산 결과가 어떤 기준으로 만들어졌는지 확인할 수 있게 한다. 서로 다른 버전의 점수를 하나의 누적 랭킹에 섞지 않는 것을 설계 기본안으로 한다.

등록·포지션 수정·등록 취소 시 해당 통계와 랭킹을 갱신한다. 계산 결과가 팀 편성용 실력 보정에도 쓰이는 경우 그 값도 함께 갱신한다. 참가자의 현재 주·부 포지션을 바꾸었다고 과거 경기의 실제 포지션을 바꾸지는 않는다.

동일 포지션의 비교 표본이 늘어날 때 기준 통계를 언제 갱신할지, 재계산 중 기존 결과를 어떻게 제공할지, 계산에 실패했을 때 어떻게 복구할지는 기술 설계에서 정한다. 데이터가 적은 서비스 규모를 고려하여 일관성을 우선한다.

## 14. 팀 추천

### 사용 범위

로그인 없이 누구나 웹사이트에서 등록된 참가자 10명을 선택하고 팀 추천을 요청할 수 있다. 운영자가 없어도 친구들끼리 이용할 수 있어야 한다.

균형이 비슷한 후보를 최대 3가지 보여주며, 각 후보에는 양 팀의 참가자와 추천 포지션을 표시한다. 친구들이 참고하여 롤 클라이언트에서 실제 팀을 구성한다.

### 추천 원칙

1. 각 사람에게 가능한 포지션만 배정한다.
2. 가능한 배정 안에서 팀 간 실력 균형을 우선한다.
3. 균형이 비슷하면 주·부 포지션을 더 잘 만족하는 구성을 선호한다.
4. 팀 이름·진영이나 표시 순서만 바뀐 결과는 중복 후보로 세지 않는다.
5. 조건에 맞는 후보가 1~2개이면 그만큼만 제공한다.
6. 아예 구성이 불가능하면 부족한 포지션 등 이유를 설명한다. 못 하는 포지션으로 강제 배정하지 않는다.

선수 구성이 동일하고 포지션만 바뀐 결과를 별도 후보로 반복 표시하지 않는 것을 기본안으로 한다. 후보 사이에 허용할 실력 차이와 선호 포지션의 수치화는 기술 설계에 맡긴다.

### 관여하지 않는 범위

- 추천 이후의 선수 교환이나 포지션 조정용 웹 편집 기능
- 롤 클라이언트의 로비 생성·팀 변경 자동 조작
- 친구들이 실제로 선택한 후보나 이후 변경 사항 추적
- 추천 결과를 실제 경기의 팀·포지션으로 확정하여 통계에 반영

추천과 실제 경기는 별개다. 경기 등록 시 수집한 실제 팀 구성과 최종 확인한 포지션을 사용한다.

## 15. 비정상 경기와 운영자 수정

탈주·접속 장애로 제대로 진행되지 못했거나 재경기를 하기로 한 경기는 내전으로 등록하지 않는다. 조회 과정에서 임시 저장되더라도 확인 대기 상태로 두며 공개·집계하지 않는다. 자동으로 문제 경기를 판정하는 별도 기능은 초기 범위에 포함하지 않는 것을 기본안으로 한다. 수집자가 등록 전에 확인한다.

이미 등록했다면 운영자가 등록을 취소한다. 취소된 경기는 개인 누적 전적·통계, 경기별 활약 순위, 누적 랭킹, 팀 편성용 실력 보정에서 제외한다.

등록 후 실제 포지션을 정정하는 작업도 운영자만 할 수 있다. 정정 이력과 등록 취소 이력을 보관한다. 취소된 자료를 운영자 확인용으로 보관하되 일반 공개 전적과 통계에는 포함하지 않는 것을 기본안으로 한다.

## 16. 운영자 코드 인증

소셜 로그인, 아이디·비밀번호 없이 운영자 전용 등록 코드를 사용한다.

1. 최초 운영자 코드는 집 서버에서 관리 명령을 실행하여 발급한다.
2. 운영자가 웹사이트에 코드를 입력하면 해당 브라우저의 운영자 인증을 설정한다.
3. 사용한 코드는 폐기하고 브라우저에는 별도의 인증 정보를 유지한다. 인증이 유효한 동안 다시 코드를 입력하지 않는다.
4. 이후에는 이미 인증된 운영자 페이지에서도 새 기기·브라우저용 코드를 발급할 수 있다.
5. 모든 브라우저의 인증을 잃었을 때는 집 서버에서 다시 코드를 발급하고 기존 인증을 해제할 수 있게 한다.

일반 방문자가 운영자 코드를 발급할 수는 없다. 새 운영자 코드가 소비되더라도 초기 운영자 한 명의 새 인증 수단을 추가하는 것이며, 별도 운영자 계정을 만드는 기능은 아니다.

운영자 코드와 수집자 코드는 권한을 분리한다. 코드는 충분히 긴 무작위 값으로 생성하고 유효기간과 단일 사용을 적용한다. 브라우저 인증은 보호된 쿠키 등 적절한 수단으로 유지하고, 로그아웃·만료·폐기를 지원한다. 코드·인증 정보를 URL이나 일반 로그에 남기지 않는다.

구체적인 코드 유효기간, 브라우저 인증 유지 기간, 시도 제한과 요청 위조 방어는 기술 설계에 맡긴다. 편의성을 위해 인증을 영구적으로 유효하게 만들지는 않는다.

## 17. 저장·운영 기본안

다음은 확정된 제품 요구를 운영하기 위한 설계 기본안이며, 기술 제품 선택은 아니다.

- 웹사이트·API·DB·Tunnel 연결을 집 Windows의 Docker 환경에서 운영한다.
- DB는 컨테이너를 교체해도 유지되는 저장소를 사용한다.
- 필요한 경기 원본과 확인된 포지션을 보관하여 평가 기준 변경 시 재계산할 수 있게 한다.
- 백업과 복원 절차를 마련한다. 같은 PC의 저장장치 장애에 대비할 수 있도록 PC 밖에도 백업을 보관하는 방안을 포함한다.
- 백업 위치·주기·보관 기간은 배포 계획에서 정한다. 유료 외부 서비스 구매는 이 문서의 결정에 포함되지 않는다.
- 서버가 중단된 동안 공개 조회와 관리는 사용할 수 없지만, 이미 수집한 전송·등록 대기는 참가자 PC에서 보존된다.
- 등록 완료·수정·취소·재계산 같은 상태 변경은 실패 시 재시도하거나 복구할 수 있어야 한다.
- 운영자 코드 발급·폐기와 경기 수정·취소의 최소 감사 이력을 남기되 비밀값을 기록하지 않는다.

## 18. 개발 초기에 반드시 확인할 사항

현재까지는 공개 자료를 확인했으며, 이 프로젝트에서 실제 LCU 응답을 수집한 적은 없다. 문서에 필드가 있다는 사실만으로 기능이 검증되었다고 보지 않는다.

우선 실제 Windows PC의 사용자 설정 경기로 다음을 검증한다.

1. 수집 프로그램의 실행 시점에 관계없이 명시적 조회 요청 시 완료된 과거 경기를 발견할 수 있는가. 특히 경기 종료 후 처음 실행한 경우에도 기록을 가져오는가.
2. 해당 경기 상세에 양 팀 10명의 식별자와 필요한 기록이 모두 포함되는가.
3. 경기 식별자가 참가자마다 같고, 지역 정보와 함께 중복 방지에 사용할 수 있는가.
4. 경기 시간, 승패, 챔피언, K/D/A, 피해량, CS, 골드, 시야, 아이템이 정상적인 값으로 반환되는가.
5. 오브젝트·포탑 피해량 등 평가 후보 지표가 실제로 반환되며 의미를 확인할 수 있는가.
6. 경기 종료 직후의 반영 지연이나 클라이언트 재시작 후 조회 동작은 어떠한가.
7. 초기 포지션 참고용 솔로랭크 기록을 어떤 범위에서 얻을 수 있는가.
8. 선택적으로 조회 가능한 경기 타임라인에 실제로 어떤 정보가 포함되는가.

필수 요구를 충족하지 못하면 수집 방식의 대안을 먼저 제시하고 범위를 다시 확인한다. 실시간 선행 실행이나 수동 기록 입력이 필요해지는 경우 이를 조용히 기존 요구의 대체 구현으로 삼지 않는다.

## 19. 주요 수용 기준

| 상황 | 기대 동작 |
| --- | --- |
| 운영자 없이 등록된 친구 10명이 내전 | 참가자 한 명이 인증된 수집 프로그램으로 등록 가능 |
| 경기 전 또는 후에 수집 프로그램 실행 | ‘과거 경기 조회’를 눌렀을 때 LCU 기록 조회; 경기 중 선행 수집에 의존하지 않음 |
| 조회한 적격 신규 경기 | 서버에 확인 대기로 임시 저장하고 공개 전적·통계에는 미반영 |
| 다른 사용자 설정 경기를 발견 | 임시 저장되더라도 내전으로 확인·등록하지 않으면 공개 전적·통계에 미반영 |
| 미등록 참가자가 포함됨 | 운영자의 참가자 등록 전까지 경기 등록 불가 |
| 조회 후 전송 또는 등록 확정 시 서버 연결 실패 | 자료와 명시적 확정 요청을 로컬에 보존하고 임시 저장→확정 순서로 재시도 |
| 같은 경기를 여러 번 전송 | 기존 상태만 응답; 중복 저장·집계·재계산·포지션 덮어쓰기 없음 |
| 실제 포지션이 추천과 다름 | 등록 시 확인한 실제 포지션으로 평가 |
| 등록 후 포지션 오류 발견 | 운영자만 수정하고 관련 결과 갱신 |
| 탈주·접속 문제·재경기 | 등록하지 않거나 운영자가 취소하여 모든 집계에서 제외 |
| 개인 기록이 1~2경기 | 평가 중 표시, 경기 수와 전적 제공 |
| 개인 기록이 3경기 이상 | 평균 보정을 유지하면서 정식 랭킹에 포함 |
| 평가 기준 변경 | 취소되지 않은 과거 경기와 누적 랭킹을 동일 기준으로 재계산 |
| 팀 추천 요청 | 가능한 포지션 안에서 균형이 비슷한 최대 3개 후보 제공 |
| 팀 추천을 만족하는 구성이 없음 | 불가능한 포지션 강제 배정 없이 이유 안내 |
| 운영자가 외부에서 새 브라우저 사용 | 서버 또는 기존 인증된 관리 페이지에서 발급한 코드로 인증 |
| 수집자 코드로 관리자 접근 시도 | 관리자 권한 부여하지 않음 |

## 20. 범위에 포함하지 않는 것

- macOS용 수집 프로그램
- 게스트와 여러 LoL 계정 통합
- 시즌·시즌 초기화
- 온라인 전적 공개 동의 화면
- Riot 계정 비밀번호 수집, RSO 기반 로그인
- 사용자 아이디·비밀번호 및 소셜 로그인
- 초기 운영자 여러 명 관리
- 자동으로 모든 사용자 설정 경기를 등록하는 기능
- 선수 교환·포지션 변경을 웹에서 직접 조작하는 기능
- 경기 중 실시간 코칭, 영상·리플레이 분석
- 수집자가 등록 완료 후 경기 수정·취소하는 기능
- 솔로랭크를 모임 누적 랭킹에 반영하는 기능

## 21. 승인된 기본안과 이후 작업

아래 항목은 초안 작성 과정에서 제시했으며, 사용자가 기획 확정 시 함께 승인한 기본안이다. 본문의 '설계 기본안' 표현도 이 승인 범위에 포함한다.

- 초기 경기 범위는 소환사의 협곡의 일반적인 5개 포지션 5대5다.
- 가능한 포지션은 주·부 포지션에서 시작하고 운영자가 추가 지정한다.
- 가한 피해량 기본 표시는 챔피언 대상 피해량으로 한다.
- 누적 점수는 경기별 평균을 기반으로 하고, 평균 보정의 초기 강도는 모임 평균 5경기분으로 한다.
- 취소된 경기는 내부 확인용으로 유지하되 일반 수집자의 재전송으로 복원하지 않는다. 별도 복원 UI는 초기 범위에서 제외한다.
- 기본적인 운영 백업·복원, 인증 폐기와 변경 이력을 포함한다.

기술 스택은 사용자와 대화하며 결정한다. 서버 Java 25 + Spring Boot 4.1.x의 최신 정식 패치 버전, PostgreSQL, Spring Data JPA + Specification, Gradle + Groovy DSL(`build.gradle`) 선택은 확정했으며, 나머지 기술은 개발자의 일방적인 결정으로 확정하지 않는다. 개발자가 정할 수 있도록 남긴 사항은 데이터 모델의 물리적 구조, 세부 점수화 공식과 실력 보정 알고리즘, 인증 유효기간, 로컬 저장·재시도 구현, 화면 배치, 배포·백업의 세부 절차다. 제품의 확정 범위를 바꾸는 선택은 먼저 확인한다.

기획 확정에 따라 [개발 계획](../plans/2026-10-21-lol-inhouse-development-plan.md)을 작성했다. 첫 단계는 [LCU 실기 검증과 수집 가능한 필드 확정](../plans/2026-10-21-lcu-validation-plan.md)이며, 이후 본 서비스 구현으로 진행한다. 검증용 CLI를 준비하며, 실제 Windows 검증과 본 서비스 구현은 아직 수행하지 않았다.

# 서버 자동 배포(GHCR)와 수집기 설치 파일 자동 공개 설계

> 기록일 2026-11-21. 현재 운영 기준: [설치·운영 설계](../../spec.md#설치운영-설계). 현재 배포 절차: [집 서버 운영 절차](../../runbooks/home-server.md), [수집기 설치 안내](../../runbooks/collector-install.md).

master에 병합된 서버 변경이 사람 손을 거치지 않고 집 Windows 서버에 반영되도록 한다. 수집기는 버전이 바뀌면 검사를 통과한 설치 파일을 GitHub Releases(저장소의 배포 파일 게시판)에 자동으로 올린다. 친구들은 지금처럼 직접 받아 설치한다. 지금은 개발 PC에서 JAR(자바 실행 묶음)를 만들어 ZIP으로 옮기고, 집 PC에서 직접 이미지를 빌드해 교체한다. 이 절차가 번거로워서 자동화한다. GHCR은 GitHub 컨테이너 이미지 저장소, CI는 변경마다 도는 자동 검사, CD는 검사를 통과한 결과를 운영에 반영하는 자동 배포다.

이 문서는 설계이며 구현·검증 완료를 뜻하지 않는다.

## 목표·비목표

**목표**

- master에 서버 관련 변경이 병합되고 기존 서버 검사가 통과하면, 사람 조작 없이 수 분 안에 집 서버가 새 버전으로 바뀐다.
- 교체 직전마다 DB를 백업하고, 새 버전이 정상 상태가 되지 않으면 DB와 이전 이미지로 자동으로 되돌린다.
- 교체가 실패하거나 되돌렸을 때 Discord로 바로 알린다. 성공은 알리지 않는다.
- 수집기 버전이 바뀐 변경이 master에 병합되고 Windows 검사가 통과하면, 같은 검사에서 만든 설치 파일과 확인값을 GitHub Releases에 자동으로 올린다.

**비목표**

- 수집기 앱의 자동 업데이트. 사용자 PC의 수집기는 지금처럼 직접 받아 설치한다([명세](../../spec.md#설치운영-설계)). — 사용자 확정
- PostgreSQL 이미지의 자동 갱신. 큰 버전 변경은 DB 이전이 필요해 자동 실패 시 운영 DB 전체가 위험하므로 고정 버전을 손으로 올린다. — 사용자 확정
- cloudflared 이미지의 자동 갱신. 지금처럼 고정 버전을 손으로 올린다. — 개발 담당자 제안
- 수집기 설치 파일의 코드 서명. 서명 인증서 구매는 이 설계에 포함하지 않는다.
- 매일 백업·PC 밖 백업 복사·복원 시험. 이는 명세의 별도 운영 과제이며 교체 직전 백업으로 대신하지 않는다.
- 여러 대 서버·무중단 교체. 교체 중 몇 분의 서버 중단을 허용한다.

**실패로 보는 경우(동작은 해도 안 되는 것)**

- 집 PC에 바깥에서 들어오는 포트나 원격 명령 경로가 새로 생긴다.
- 공개 저장소의 PR·작업 파일이 집 PC에서 코드를 실행할 수 있다.
- 검사를 통과하지 못한 코드가 운영 서버에 반영된다.
- 교체가 실패했는데 알림이 오지 않아, 사용자가 새 버전이 운영 중이라고 믿게 된다.
- 비밀값(DB 암호·운영자 로그인 코드·Tunnel 토큰·웹훅 주소)이 이미지·로그·알림·저장소에 들어간다.

## 제약

- 집 PC는 Docker Desktop의 Linux 컨테이너 모드로 서버·DB·Tunnel을 실행하며 바깥에서 들어오는 포트가 없다([운영 절차](../../runbooks/home-server.md#2-서버db-시작)).
- 저장소는 공개다. GitHub는 공개 저장소에 자체 실행기를 쓰지 말라고 경고한다.
- 서버는 시작할 때 Flyway(DB 구조 변경 도구)로 DB 구조를 바꾼다. 새 버전이 한 번 시작하면 이전 이미지와 DB가 맞지 않을 수 있다.
- 서버가 멈춘 동안 수집기는 자료를 보관했다가 다시 보낸다. 교체 중 중단은 기록 지연일 뿐 손실이 아니다.
- 기존 운영 DB 볼륨은 Compose 프로젝트 이름 `cw-collector-acceptance`에 묶여 있다. 이름이 바뀌면 빈 DB로 시작하므로 반드시 유지한다([Compose 원본](../../../infra/home-server/compose.yml)).
- 비밀값은 집 PC의 `.env`·`secrets`에만 둔다([명세](../../spec.md#설치운영-설계)).

## 검토한 방식

판단 기준: 집 PC로 들어오는 경로를 만들지 않는가, 공개 저장소에서 안전한가, 준비·관리 비용, 반영 속도, 결과 확인의 편의.

| 방식 | 장점 | 단점·비용 |
|------|------|-----------|
| **1. 집 PC가 직접 확인 (채택)** | 들어오는 경로가 없다. 공개 저장소·외부 PR이 집 PC에서 실행될 길이 없다. 공개 이미지면 집 PC에 GitHub 토큰이 필요 없다 | 반영이 확인 주기만큼(최대 약 2분) 늦다. 교체 스크립트를 직접 만들고 관리한다. 결과가 GitHub 화면에 나오지 않는다(Discord로 보완) |
| 2. 집 PC에 GitHub 자체 실행기 | 즉시 반영, 결과가 GitHub에 표시 | 공개 저장소에서 외부 PR 작업이 집 PC에서 실행될 위험. 설정 실수 한 번으로 노출. Windows 서비스·Docker 권한 설정 필요 |
| 3. Cloudflare Access 경유 SSH | 즉시 반영, 결과가 GitHub에 표시 | Windows SSH 서버·Cloudflare Access 설정으로 준비가 가장 많다. GitHub 비밀값에 원격 명령 열쇠가 생긴다 |

사용자는 1을 선택했다. 감수하는 불이익은 몇 분의 반영 지연과 스크립트 관리 부담이다. 재검토 조건: 확인 주기 지연이 실제 사용에 문제가 되거나, 저장소를 비공개로 바꿔 2의 위험이 줄어든 경우.

교체 시점은 "버전 태그를 붙일 때만"과 "병합마다" 중 사용자가 **병합마다**를 골랐다. 손 가는 단계가 없는 대신 병합한 변경이 바로 운영 DB 구조를 바꾼다. 이 위험은 교체 직전 백업과 자동 되돌림으로 줄인다.

알림은 "관리자 화면 표시"와 "Discord 웹훅" 중 사용자가 **Discord 웹훅**을 골랐다. 즉시 알 수 있는 대신 웹훅 주소를 집 PC에 비밀값으로 보관한다. 설계 검토 중 사용자는 **성공은 알리지 않기로** 정했다. 병합마다 오는 알림을 줄이는 대신, 알림이 없다는 것만으로 교체 성공을 확신할 수는 없다(교체 담당이 멈춘 경우, [사용상 제한](#사용상-제한) 참조).

## 동작 설계

### 전체 흐름

```text
master 병합
  → GitHub: 서버 검사(기존 server.yml 내용) 통과
  → GitHub: 서버 이미지 빌드 → GHCR에 :master, :sha-<커밋> 이름표로 올림
집 PC 교체 담당 컨테이너 (약 2분마다)
  → GHCR의 :master 이미지 식별값(digest)이 실행 중 이미지와 다르면 교체 시작
  → 서버·Tunnel 정지 → DB 백업 → 새 이미지로 서버 시작 → 정상 상태 대기
     ├ 정상: Tunnel 재시작 → 로그에만 기록(알림 없음)
     └ 실패: DB를 백업으로 복원 → 이전 이미지로 서버 시작 → Tunnel 재시작 → Discord "실패 후 되돌림"
                └ 되돌림도 실패: 서버 정지 상태 유지 → Discord "수동 조치 필요"
```

### GitHub 쪽 (CI)

- 변경 전: master 푸시·PR마다 서버 검사만 실행하고 결과물을 올리지 않는다.
- 변경 후: 기존 검사는 그대로 실행한다. **master 푸시**에서 검사가 모두 통과했을 때만 이미지를 빌드해 GHCR에 올린다. PR·다른 브랜치·검사 실패에서는 올리지 않는다.
- 이미지는 검사를 통과한 같은 커밋으로 만든다. 이미지 안에는 현재 [Dockerfile](../../../infra/home-server/Dockerfile)처럼 실행 JAR와 Java 실행 환경만 넣는다. 비밀값·`.env`는 넣지 않는다.
- 이미지 이름: `ghcr.io/sanghyeok0908/civil-war-server`(GHCR 이름은 소문자). 이름표는 `master`(최신)와 `sha-<커밋 앞 7자>`(추적용)다. — 개발 담당자 제안
- 이미지에 원본 커밋을 표준 표시(OCI 라벨 `org.opencontainers.image.revision`·`source`)로 남긴다. 교체 담당은 이 값을 Discord 알림에 쓴다. — 개발 담당자 제안
- 이미지는 공개로 둔다. 집 PC가 로그인 없이 받을 수 있다. 저장소가 이미 공개이므로 새로 공개되는 코드는 없다. — 개발 담당자 제안
- 빌드 대상은 `linux/amd64` 하나다. — 개발 담당자 제안, [가정](#가정과-미확인-사항) 참조
- 작업 권한은 필요한 범위로 제한한다. 이미지를 올리는 작업만 `packages: write`를 갖고 GitHub가 주는 일회용 토큰(`GITHUB_TOKEN`)을 쓴다. 외부 작업 버전은 기존 작업 파일처럼 커밋 해시로 고정한다.
- 서버 검사의 경로 조건에 걸리지 않는 변경(예: 문서·수집기만 변경)은 이미지를 만들지 않으므로 집 서버도 교체하지 않는다.

### 집 PC 쪽 (CD)

**구성 변경**

- 변경 전: Compose의 서버가 `build: .`로 집 PC에서 JAR를 넣어 이미지를 만든다.
- 변경 후: 서버는 GHCR 이미지를 받아서 쓴다. Compose에 교체 담당 서비스(`updater`)를 추가한다. 프로젝트 이름·DB 볼륨·네트워크·환경값 이름은 그대로 둔다.
- 교체 담당은 Docker 제어 통로(`/var/run/docker.sock`)를 써서 같은 Compose 프로젝트의 서버·Tunnel을 멈추고 시작한다. 이 통로는 Docker 전체 제어권이므로 교체 담당 이미지는 우리 저장소에서 만든 것만 쓰고 외부 네트워크는 GHCR·Discord 접속에만 쓴다. 교체 담당은 바깥에서 들어오는 포트를 열지 않는다.
- 교체 담당 자신은 자동 교체 대상이 아니다. 교체 담당이 바뀌면 사람이 직접 갱신한다. — 개발 담당자 제안(스스로를 교체하다 멈추는 경우를 피한다)

**확인과 교체**

- 확인 주기는 2분이다. — 개발 담당자 제안
- GHCR의 `:master` 식별값이 실행 중 서버 이미지의 식별값과 같으면 아무것도 하지 않는다. GHCR 접속 실패는 다음 주기에 다시 시도하고, 같은 실패가 계속되면 1시간에 한 번만 Discord로 알린다. — 개발 담당자 제안
- 교체는 한 번에 하나만 실행한다. 교체 중 새 이미지가 올라오면 현재 교체를 끝낸 뒤 다음 주기에 처리한다.
- 교체 순서:
  1. 실행 중인 서버 이미지 식별값을 "이전 이미지"로 기록하고, 이 이미지를 집 PC에서 지우지 않는다.
  2. 새 이미지를 먼저 받는다. 받기 실패 시 아무것도 멈추지 않고 다음 주기로 넘긴다.
  3. Tunnel과 서버를 멈춘다(DB는 유지). 수집기의 쓰기가 멈춘 상태가 된다.
  4. DB를 백업한다. 형식은 현재 운영 절차와 같은 `pg_dump -Fc`다. 백업 실패 시 새 버전을 시작하지 않고 이전 서버·Tunnel을 다시 켠 뒤 Discord로 "백업 실패, 교체 안 함"을 알린다.
  5. 새 이미지로 서버를 시작하고 Compose의 정상 상태 검사(현재 `/api/members` 200 응답)가 `healthy`가 될 때까지 최대 5분 기다린다. — 개발 담당자 제안
  6. 정상이면 Tunnel을 켠다. 성공은 Discord로 알리지 않고 교체 담당 로그에만 커밋과 시각을 남긴다.
- 실패 시 되돌림: DB를 4단계 백업으로 복원(기존 DB를 비우고 `pg_restore`)한 뒤 이전 이미지로 서버를 시작하고, 정상 상태가 되면 Tunnel을 켠다. 3단계 이후 서버가 멈춰 있었으므로 백업 이후 새로 쓰인 자료는 없다. 되돌린 커밋은 다시 시도하지 않으며 `:master`가 다른 이미지로 바뀔 때 다시 교체한다. — 개발 담당자 제안
- 되돌림도 실패하면 서버를 멈춘 채로 두고 "수동 조치 필요"를 알린다. 이 상태에서는 자동 교체를 멈추고 사람이 해제할 때까지 기다린다. 공개 조회는 중단되지만 수집기 자료는 각 PC에 보존된다.
- 교체 도중 교체 담당이나 PC가 재시작되면, 시작할 때 남은 진행 기록을 보고 실패로 간주해 되돌림부터 진행한다. — 개발 담당자 제안
- 백업은 배포 폴더의 `backups/`에 두고 교체 직전 백업을 최근 10개까지 보관한다. 이 폴더는 `.env`·`secrets`처럼 공유·저장소에 넣지 않는다. — 개발 담당자 제안

**Discord 알림**

- 웹훅 주소는 `secrets/discord-webhook-url.txt`에 두고 Compose 비밀값으로 교체 담당에만 전달한다. — 개발 담당자 제안
- 알림 종류: 실패 후 되돌림 성공, 되돌림 실패(수동 조치 필요), 백업 실패로 교체 안 함, GHCR 접속이 계속 실패. 교체 성공은 알리지 않는다(사용자 확정). 종류 구분은 개발 담당자 제안이다.
- 알림 내용: 결과, 커밋 앞 7자와 GitHub 커밋 링크, 시각, 실패 단계 이름. DB 내용·비밀값·서버 로그 원문은 넣지 않는다.
- 웹훅 전송이 실패해도 교체·되돌림 동작은 멈추지 않고, 교체 담당 로그에 남긴다.

### 최초 한 번의 전환

자동 교체는 GHCR 이미지를 쓰는 새 Compose 설정이 집 PC에 있어야 시작된다. 그래서 첫 전환은 사람이 한다. 운영 절차 문서에 다음 순서를 추가한다. — 개발 담당자 제안

1. GHCR 패키지가 처음 만들어지면 GitHub 패키지 설정에서 공개로 바꾼다(처음 생성 시 비공개일 수 있다, [미확인](#가정과-미확인-사항)).
2. Discord에서 웹훅을 만들고 주소를 `secrets/discord-webhook-url.txt`에 저장한다.
3. 기존 교체 절차처럼 서버·Tunnel을 멈추고 DB를 백업한다.
4. 새 Compose 설정을 **기존 배포 폴더**에 넣는다(`.env`·`secrets`·프로젝트 이름 유지). 서버·교체 담당·Tunnel을 시작하고 정상 상태를 확인한다. 성공은 평소 알리지 않으므로, 웹훅 주소가 맞는지는 교체 담당의 수동 시험 전송 명령으로 한 번 확인한다. — 개발 담당자 제안

기존 ZIP 배포 절차는 자동 교체가 실제 집 PC에서 확인될 때까지 수동 대체 절차로 남긴다.

### 수집기 설치 파일 자동 공개

**변경 전후**

- 변경 전: `client.yml`이 Windows에서 서명하지 않은 설치 파일을 만들고 무결성까지 검사하지만 어디에도 올리지 않는다. 배포 파일은 개발 PC에서 만들어 직접 전달한다.
- 변경 후: master 푸시에서 같은 검사가 모두 통과하고 수집기 버전이 아직 공개된 적 없는 값이면, 그 검사에서 만든 파일을 GitHub Release로 공개한다. PR·다른 브랜치·검사 실패에서는 공개하지 않는다.

**공개 기준**

- 버전의 원본은 [수집기 package.json](../../../apps/collector/package.json)의 `version`이다. Release 이름(태그)은 `collector-v<버전>`이다(예: `collector-v0.5.0-provisional`). — 개발 담당자 제안
- 같은 이름의 Release가 이미 있으면 아무것도 올리지 않고 넘어간다. 이미 공개한 Release의 파일을 덮어쓰거나 지우지 않는다. 버전이 같고 내용만 다른 설치 파일이 생기지 않게 하기 위해서다.
- 따라서 수집기 코드를 바꿔도 버전을 올리지 않으면 공개되지 않는다. 공개하려면 버전 숫자를 올린다. — 사용자 확정(버전이 바뀔 때만 공개)
- 서명하지 않은 판이므로 Release 설명에 "코드 서명 없음, Windows 경고가 나올 수 있음"과 [수집기 설치 안내](../../runbooks/collector-install.md) 링크를 넣는다. 일반 Release로 공개하고 시험판(prerelease) 표시는 하지 않는다. — 개발 담당자 제안

**첨부 파일**

- 설치 실행 파일 `Civil-War-Collector-Setup-<버전>-x64.exe`, `SHA256SUMS.txt`, `release.json`. 현재 [설치 안내](../../runbooks/collector-install.md)가 배포할 파일로 정한 세 개와 같다. `win-unpacked`·디버그 파일은 올리지 않는다.
- 파일은 검사를 통과한 같은 작업에서 만든 것을 그대로 올린다. 공개 단계에서 다시 빌드하지 않는다.
- Release 설명에 원본 커밋과 설치 파일의 SHA-256 값을 적는다.

**권한과 실패 처리**

- 공개 단계만 `contents: write` 권한을 갖고 GitHub가 주는 일회용 토큰(`GITHUB_TOKEN`)을 쓴다. 외부 작업을 새로 쓰지 않고 실행 환경에 기본으로 있는 `gh` 명령으로 Release를 만든다. — 개발 담당자 제안
- 공개가 실패하면 GitHub 작업이 실패로 표시된다. 수집기 공개는 Discord로 알리지 않는다(Discord 알림은 집 서버 교체 결과용). — 개발 담당자 제안
- 설치 파일 공개는 서버 교체와 독립적이다. 서버 프로토콜 변경처럼 둘의 순서가 중요한 변경은 지금처럼 [서버 전환 절차](../../runbooks/home-server.md#새-계정코드-계약-적용-순서)의 순서를 따른다.

**첫 공개 버전**

- 현재 버전 `0.4.0-provisional`은 이미 손으로 배포된 판이 있는데, 그 뒤 화면·솔로랭크 제거 변경이 같은 버전 숫자로 들어갔다. 이 상태로 자동 공개하면 이름은 같고 내용이 다른 설치 파일이 생긴다.
- 그래서 이 기능을 넣는 변경에서 수집기 버전을 `0.5.0-provisional`로 올려, 첫 자동 공개가 기존 배포판과 확실히 구분되게 한다. — 개발 담당자 제안, 버전 숫자는 사용자가 바꿀 수 있다

## 문서 반영

- [명세의 설치·운영 설계](../../spec.md#설치운영-설계)에 서버 자동 교체 기준(병합마다, 교체 전 백업, 자동 되돌림, Discord 알림)을 짧게 추가한다.
- [운영 절차](../../runbooks/home-server.md)에 최초 전환·자동 교체 확인·되돌림 실패 시 수동 조치·수동 대체 절차를 넣는다.
- [수집기 설치 안내](../../runbooks/collector-install.md)의 "전달받은 설치 파일"을 GitHub Releases에서 받는 방법으로 바꾸고, 공개하려면 버전을 올려야 한다는 개발 절차를 추가한다.
- 새 문서는 [정본 목록](../../ssot.json)에 등록하고 문서 검사를 실행한다. 실행 결과는 검증 보고서에 쓴다.

## 검증 방향

- 실제 GitHub·GHCR 연동과 로컬 모의 시험을 구분해 보고한다.
- 로컬 모의 시험: 로컬 이미지 저장소와 일부러 시작에 실패하는 이미지로 성공·되돌림·되돌림 실패·백업 실패·재시작 중단을 확인한다. 웹훅은 가짜 수신 서버로 내용에 비밀값이 없는지 확인한다.
- 실제 연동: master 병합 후 GHCR에 이미지가 올라가는지, PR에서는 올라가지 않는지 확인한다.
- 수집기 공개: 새 버전 병합 시 Release와 세 파일이 생기는지, 같은 버전의 재병합에서 Release가 바뀌지 않는지, 받은 설치 파일의 해시가 `SHA256SUMS.txt`와 맞는지 확인한다. 공개된 설치 파일의 실제 Windows 설치는 사용자가 확인하며 자동 검사 성공으로 대신하지 않는다.
- 실제 집 PC 교체는 사용자가 실행하고 결과를 보고한다. 로컬 모의 시험 성공을 집 PC 교체 성공으로 쓰지 않는다.

## 사용상 제한

- 성공 알림이 없으므로, 교체 담당 컨테이너 자체가 멈추거나 Docker Desktop이 꺼져 있으면 아무 알림도 오지 않는다. 이때 병합한 변경은 반영되지 않은 채로 남는다. 실제 반영 여부는 교체 담당 로그나 실행 중 서버 이미지의 커밋으로 확인한다.
- 교체마다 서버가 몇 분 멈춘다. 그동안 공개 조회·관리는 쓸 수 없고 수집기 전송은 지연된다.
- 공개 저장소의 Release이므로 수집기 설치 파일은 누구나 받을 수 있다. 서명이 없어 Windows 경고가 나올 수 있고, 해시 일치는 코드 서명을 대신하지 않는다.

## 가정과 미확인 사항

- **가정:** 집 PC는 일반 x64(amd64) Windows PC다. ARM PC라면 빌드 대상에 `linux/arm64`를 추가해야 한다.
- **가정:** 집 PC의 Docker Desktop에서 컨테이너가 `/var/run/docker.sock`을 쓸 수 있다(Linux 컨테이너 모드의 기본 동작).
- **미확인:** GHCR 패키지가 처음 만들어질 때 공개 저장소의 공개 설정을 따르는지, 손으로 공개로 바꿔야 하는지.
- **미확인:** 백업 크기와 복원 시간. 현재 경기 규모에서는 작을 것으로 보지만 측정하지 않았다.

## 구현 담당에게 맡기는 부분

- 교체 담당의 구현 언어와 이미지 구성(셸 스크립트, Node.js 등). 단, 우리 저장소에서 빌드하고 버전을 고정한다.
- 이미지 빌드를 기존 `server.yml`에 이어 붙일지 별도 작업 파일로 나눌지. 단, "같은 커밋의 검사 통과 후에만 올림"을 지킨다.
- 이미지 안에서 JAR를 빌드할지(다단계 Dockerfile), 검사 작업이 만든 JAR를 쓸지.
- 진행 기록의 형식·위치와 수동 조치 후 자동 교체를 다시 켜는 방법.

## P01 — 계정 연결 설계 제안

입력을 줄이면서 이름 변경과 과거 연결을 지키는 것이 기준이다. 기존 참가자 ID는 보존하고, 정식 참가자와 독립된 `player_accounts` 계정 행을 둔다. LCU PUUID와 공식 PUUID는 별도 고유 필드이며 어느 하나의 연결이 없어도 확인 대기 상태를 저장한다. Riot ID는 전체 이름·태그를 다루며 공개 표시의 기본은 해당 Riot ID로 제안한다.

공식 Account-v1 조회와 수집기가 읽은 현재 계정·경기 식별 자료를 연결하는 `AccountIdentityResolver`를 둔다. 공식 키는 서버에만 보관한다. 오래된 경기의 이름 일치만으로 새 회원과 합치지 않는다. 현재 이름·태그와 두 식별 체계의 연결을 확인할 수 있는 LCU 읽기 경로 또는 보유 증거를 조사하고, 확인된 경로만 어댑터에 넣는다. 지원하지 않는 경로를 추측해 호출하거나 모든 참가자에게 수집기 설치·PUUID 수동 입력을 요구하는 대안은 이번 목표를 충족하지 못한다.

현재 보유 근거는 [두 PUUID가 달랐던 조사](../../validation/riot-solo-reference.md#1-조회-경로와-확인-기준)와 [Riot ID 공식 조회 안내](https://developer.riotgames.com/docs/lol#obtaining-puuid-and-summonerid-from-riotid)다. 작성 당시 자동 연결 방식의 성공은 미확인이었다. 이후 구현·검사 근거는 아래 실행 보완에 연결한다. 구현 첫 작업에서 현재 지원 경로·이름 변경·충돌의 입출력을 확인하고, 연결 미해결 시 합산을 보류하는 구체적 계약을 만든다. 계정 필수 입력 축소의 완료를 주장하려면 실제 자동 연결의 증거가 필요하다.

장점은 게스트와 정식 참가자가 같은 계정 키를 공유한다는 점이다. 비용은 별도 계정 테이블과 연결 상태, 기존 자료의 전환이다. 이름만 저장하는 방법은 영구 연결을 지키기 어려워 권고하지 않는다. 기술 경로가 확인되지 않으면 P01의 완료를 보류하고 관련 근거를 보완한다.

## P02 — 게스트 평가·공개 경계 제안

게임 참가자 키 `playerId`를 회원 키와 분리한다. 경기별 비교·순위는 모든 계정으로 계산하고, 회원 누적과 누적 평균 보정의 모집단은 정식 회원으로 제한한다. 계정의 회원 연결이 생기면 기존 경기 행을 다시 생성하지 않고 연결과 재계산을 같은 저장 단위로 처리한다. 이 구조는 null 회원 키 때문에 게스트끼리 같은 사람으로 취급되는 오류를 막는다.

게스트의 공개 동의가 확인되지 않은 동안 공개 이름은 ‘게스트’로 표시하고 개인 페이지 링크를 만들지 않는 안을 제안한다. 원본 연결 자료는 비공개로 보존한다. 기존의 동의 원칙을 게스트에게도 적용하며 별도 온라인 동의 제품은 추가하지 않는다. 사용자 확인 없이 게스트 이름을 전부 공개하는 것으로 해석하지 않는다.

## P03 — 공통 코드·관리자 인증 세부 제안

공통 코드는 현재의 긴 임의 비밀값 생성기를 재사용하고 운영자가 바꿀 때까지 반복 사용한다. 발급 시 한 번 보여주며 이후 재조회는 마스킹한 상태만 제공한다. 숫자 6자리 요구는 관리자 코드에만 적용한다. 짧은 공통 코드보다 전달은 길지만 기존 생성·보관 경계를 활용한다. 다시 보기 기능이 필요해지면 재검토한다.

기존 권한대로 정식 참가자가 자신의 경기만 수집하도록 유지한다. 공통 코드를 아는 게스트나 미등록 계정의 수집 권한 확대는 사용자 확정 사항이 아니다. 기기 토큰에 코드 세대를 연결하고 세대 교체와 전 기기 해제를 한 트랜잭션으로 처리한다. 쓰기 요청은 실제 저장 직전에도 세대를 확인해 교체 직전 시작한 요청이 해제 이후 새로 반영되는 일을 막는다.

관리자 세션·기기 토큰은 기존 긴 형식을 유지한다. 짧은 관리자 코드는 유효 미소비 코드를 하나만 두고, 기존 만료·단일 소비를 유지하는 안이다. 로그인 추측 제한을 서버 재시작 후에도 보존하고, 공통 코드의 정상 사용이 관리자 실패 횟수를 초기화하지 않게 분리한다. 6자리 코드는 긴 비밀값보다 추측 공간이 좁으며 DB의 코드 해시만 노출돼도 사전 대입에 약하다는 한계를 운영 문서에 적는다. 외부 요청 제한과 코드 만료를 함께 검증한다.

## P04 — 등급 환산과 갱신 제안

공통 중간값은 기존 척도의 중앙인 50을 제안한다. 등급은 현재 솔로/듀오만 조회하고 자유랭크·과거 최고 등급을 혼합하지 않는다. 공식 계정·등급 자료는 서버에서 갱신한다. 최초 참가자 등록 때 요청하고 마지막 성공 후 24시간이 지나면 다음 조회에서 배경 갱신한다. 지연·실패가 참가자 화면과 팀 추천 요청을 무한 대기시키지 않는다. 마지막 정상 등급이 있으면 시간과 함께 유지하고, 실제 등급 없음과 조회 실패를 별도 저장한다.

수치 환산은 아직 사용자가 확정하지 않은 계획자의 임시 정책이다. 0–100 시작 척도에 대해 아이언 IV부터 다이아몬드 I까지 28개 구간을 낮은 순으로 0–27, 마스터·그랜드마스터·챌린저를 28–30으로 두고 `round(100 × 구간 / 30)`을 사용한다. 리그 포인트(LP)는 첫 버전에 넣지 않는다. 이 식은 실제 실력 차이를 측정한 결과나 Riot의 비공개 실력값 추정이 아니다. 등급 순서를 보존하는 단순한 팀 편성 시작값이다.

장점은 수동 평가를 없애고 구현·설명을 단순화하는 것이다. 비용은 같은 등급 안의 LP 차이와 등급 간 실제 격차를 반영하지 못한다는 점이다. 내전 누적과 기존 보정 강도가 오차를 줄이지만 정확성을 보장하지 않는다. 소규모 모임에서 균형 문제가 확인되거나 등급 체계가 바뀌면 환산 규칙 버전을 새로 만들고 재계산한다. 운영자의 과거 입력값은 감사·백업용으로 보존하되 새 계산의 우회 입력으로 쓰지 않는다.

## P05 — 보수적인 포지션 제안

명확한 경기 라인·역할 조합을 먼저 읽는다. 팀의 다섯 역할이 충돌하지 않는 후보만 채우고, 원딜과 서포터를 구분할 근거가 없으면 두 사람을 임의 배정하지 않는다. 동일 역할 후보가 겹치면 해당 후보를 비워 둔다. 챔피언·배열 순서·남은 자리만으로 결정하지 않는다.

과거 확정 내전이나 주·부 포지션은 약한 경기 힌트의 보조 근거로만 쓴다. 경기 힌트가 없을 때 주 포지션 하나만으로 실제 포지션을 채우지 않는다. 이 보수적인 경계는 잘못된 기본값의 확정을 줄이는 대신 미지정이 더 남는 비용이 있다. 사람의 수정은 별도 초안에 보존하고 서버 확정값보다 앞서지 않는다. 힌트 누락은 경기를 부적격으로 만들지 않는다. 현재 축소 공개 fixture에 없는 선택 필드를 기존 정규화 필수값에 추가하지 않는다.

## P06 — 챔피언 자료와 진행 조회

한국어 이름·초상화를 고정된 자산 묶음으로 함께 제공해 이미지 호스트가 느리거나 오프라인이어도 첫 표시를 가능하게 하는 안이다. 기존 서버의 자산 원본을 공유하고 이름·이미지·설명 자료의 버전을 한 파일에서 관리한다. 비용은 설치 묶음 크기와 새 챔피언 자료 갱신이다. 원격 이미지를 직접 렌더러에 허용하는 방식보다 현재의 좁은 화면 보안 경계를 유지하기 쉽다.

전송 단계는 수집기의 실제 통신 관측으로, 계산 단계는 서버의 최신 계산 작업과 공개 결과로 판정한다. 화면은 로컬 자료를 먼저 표시하고 계산 상태는 묶음 조회한다. 서버가 답하지 않을 때의 마지막 관측을 현재의 성공·실패로 바꾸지 않는다. 등록 완료 경기의 계산 실패는 별도 보조 상태로 표시하고 목록의 주 상태를 되돌리지 않는다.

## P07 — 관리자 활성 표시와 목록 기본값

사용자가 ‘활성 참가자’의 의미를 질문한 것은 상태 삭제 요청이 아니다. 의미를 유지하면서 포지션 영역 밖으로 옮기고 ‘팀 추천 대상’으로 바꾸는 UI 개선안을 제안한다. 수집기 초기 탭은 전체, 정렬은 경기 시작 시각 내림차순, 같은 시각은 경기 키로 고정하는 안이다. 이는 요구사항을 구체화한 계획자 선택이며 별도 제품 결정으로 사용자에게 확정받았다고 기록하지 않는다.

## 구현에서 유지할 경계

새 요구사항과 관계없는 점수 항목·가중치·과거 측정값·이전 PR의 성과는 변경하지 않는다. [현재 제외 범위](../../status.md#범위-제외와-미확인-사실)의 추가 Windows 업데이트·인증 손상 복구 시험, 과거 조회 범위 실험·친구 목록 조회를 완료 조건으로 되살리지 않는다. 이번 기능의 실제 외부 연동이 확인되지 않은 경우는 해당 기능의 한계로 별도 보고한다.

## 실행 보완과 채택한 세부안

보완일 2026-10-28, 결정 주체는 사용자 지시에 따라 계획을 실행한 개발 담당자다. 사용자는 계획대로 코드 반영과 기존 자료 보존 검증을 요청했다. 제품 목표의 재승인은 필요하지 않았다. 현재 상세 규칙은 정본에만 두고 아래에는 선택과 이유를 남긴다.

| 분류·상태 | 선택·이유 | 비용과 재검토 조건 |
| --- | --- | --- |
| 위임받은 선택 · 반영 | 사람과 계정 분리, Riot ID 전체를 표시 이름으로 사용. 미확인 계정은 연결 대기 상태로 저장 | 이름만으로 과거 기록을 합치지 않아 초기 연결이 늦을 수 있음. 현재 조회 경로가 달라지면 어댑터 재검토 |
| 조사 및 검증 · 가상 응답 검사 | 수집기는 현재 로그인 계정과 PUUID별 현재 LCU 이름을 관측하고 서버에 전달. 공식 Riot ID 조회로 얻은 공식 키는 별도 보관 | 신뢰하는 수집기 경계이며 서버가 Riot 로그인 소유권을 증명하는 기능은 아님. 새 LCU 경로의 Windows 실연동은 미확인 |
| 위임받은 선택 · 반영 | 게스트는 독립 키로 경기 평가에 참여하고 공개 이름을 ‘게스트’로 표시. 정식 등록 시 원래 행에 회원 연결만 추가 | 과거 집계를 다시 계산하며 기존 1–2경기 평가 중 기준도 그대로 적용 |
| 위임받은 선택 · 반영 | 자동 등급의 수치는 정책 파일에서 관리. 비동기 조회 실패가 참가자 입력을 지우지 않게 함 | 키·접근 장애 동안 최근 성공값 또는 공통값 사용. 환산의 실제 공정성은 운영 자료가 생기면 재검토 |
| 오류 수정 · 반영 | 짧은 관리자 코드의 동시 추측 요청도 DB에서 순서를 잡아 횟수 제한 | 인증 시 짧은 DB 잠금을 사용. 여러 서버·프록시 운영에서 제한이 불편해지면 재검토 |
| 위임받은 선택 · 반영 | 명확한 경기 근거만 역할 제안. 챔피언 이름·초상화는 고정 로컬 묶음 | 미지정이 더 남고 설치 묶음이 커짐. 새 챔피언·LCU 힌트가 나오면 근거와 자산 갱신 |
| 오류 수정 · 반영 | UI 용어와 내부 상태를 분리하고 이전 사람이 고른 초안을 새 제안보다 우선 | 사람 초안의 오래된 선택은 최종 확인으로 수정. 자동 제안만으로 등록하지 않음 |

[실행 보고서](../../validation/2026-10-28-ux-implementation-report.md)는 실제 DB·HTTP·브라우저·Electron 검사와 가상 LCU·Riot 응답을 구분한다. 작성 당시 제안·기존 실기 결과를 이번 외부 연동 성공으로 바꾸지 않는다.

## 독립 검토 뒤 보완

보완일 2026-10-28. 독립 검토자는 코드·시험·화면을 읽기 전용으로 대조해 중요한 오류 다섯 건을 지적했다. 개발 담당자는 각각 실패를 재현한 뒤 수정하고 전체 검사를 다시 실행했다. 이는 별도 사용자 정책 변경이나 운영 실연동 검증이 아니다.

캐시된 같은 이름을 즉시 소급 연결에 쓰던 구현은 철회했다. 새 프로필 생성 뒤 들어온 현재 계정 관측으로만 연결한다. 잘못된 사람에게 과거 기록이 넘어가는 일을 막는 대신, 수집기의 다음 최신 계정 확인까지 연결 대기가 남는 비용이 있다. 초기 입력은 여전히 Riot ID 하나이며 수동 식별자나 전원 설치를 요구하지 않는다.

추가로 적격 명단 캐시가 있는 경기는 이름 관측을 업로드하기 전에 PC에 저장하고, 서버 취소 응답은 수집기의 주 상태에도 반영한다. 회원 편집의 이름 중복을 막고 공식 계정 조회의 재시도 시간을 전달한다. 연결 중 계정 행이 달라져도 이전 정상 등급을 옮겨 조회 실패 때 공통값으로 떨어지지 않게 했다. [수정별 근거](../../validation/2026-10-28-ux-implementation-report.md#독립-검토와-수정-근거)는 실행 보고서에 있다.

## 운영 배포 ZIP 요청

보완일 2026-10-28. 사용자는 구현·검증 뒤 운영 적용에 쓸 ZIP 생성을 요청했다. 이에 따라 새 설치 묶음 준비를 이번 범위에 포함한다. 기존 [업데이트·인증 손상 실기 제외](2026-10-22-overnight-decisions.md#d30--2026-10-28-업데이트인증-손상-시험-제외와-기존-요청-처리)는 유지하며 실제 서버 적용·외부 게시를 자동으로 수행하는 요청으로 해석하지 않는다.

개발 담당자는 기존 수집기와 새 통신 규약을 쓰는 설치판을 구분하기 위해 새 앱 버전을 선택했다. 버전 원본은 [수집기 설정](../../../apps/collector/package.json)이다. 기존 설치 식별자·자료 경로와 서버 Compose 프로젝트·볼륨은 유지한다. 버전만으로 실기 검증이나 운영 적용 성공을 표시하지 않으며 [묶음 검증](../../validation/2026-10-28-ux-deployment-package-report.md)에서 실제 확인 범위를 구분한다.

## 수집기 사용 간소화 추가 요구

편집·보완일: 2026-10-28. 사용자는 실제 설치·사용 과정에서 터미널 실행, 상시 연결 폼, 수동 전송 재개와 경기 확인 절차가 번거롭다고 설명하고 새 구현을 요청했다. 이는 앞의 P03·P07과 배포 실행 안내를 바꾸는 후속 결정이며 이전 구현·시험 결과를 소급 변경하지 않는다.

| 분류·주체 | 상태 | 지금 판단할 사항 |
| --- | --- | --- |
| 사용자 확정 · 사용자 | 자동 전송과 경기별 안내 채택, 구현 요청 | 재승인 없이 구현 |
| 사용자 확정 · 사용자 | 고정 서버·설치 직후 실행·바탕화면 아이콘, 페이지당 3경기, 연결 팝업·문구·등록 간소화 | 구체 작업은 [구현 계획](../plans/2026-10-28-collector-ease.md) |
| 사용자 확정 · 사용자 | 모임 코드 숫자 6자리, 관리자 코드 2005 고정·발급 관리/이력 화면 제거 | 기존 세션·경기·대기 자료 보존 |
| 위임받은 선택 · 구현 담당자 | 같은 계정/회원 검증, 기존 긴 공통 코드 호환, 필터 변경 시 첫 페이지 | 연결 해제는 기존 재발급·삭제 때 적용 |
| 조사 및 검증 · 구현 담당자 | 구현 전 | 실제 실행 결과는 별도 보고 |

사용자는 자동 전송의 안내 방식을 제안받고 채택했다. 자동 재개는 이미 저장한 요청에 한정하며 미확인 경기를 등록하지 않는다. 코드 입력 팝업은 닫은 뒤 반복 개방하지 않고 재개방 동작을 둔다. 서버 접수 확인 전에는 서버 처리 중으로 표현하지 않는다.

관리자 고정값은 일회용·만료 코드의 보호를 포기한다. 공개 서버에서 값을 아는 사람이 운영 권한을 얻을 수 있다는 불이익을 설명했고, 사용자는 이 요구들을 구현하도록 지시했다. 기존 실패 제한·브라우저 세션·요청 위조 방지는 유지하며 이 선택을 보안 강화로 표현하지 않는다. 이전 코드 이력은 화면/API에서 제거하되 과거 DB 행·감사 근거는 보존한다.

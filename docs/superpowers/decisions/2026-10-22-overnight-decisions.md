# 야간 단계 0–3 결정 기록

> **기록일 2026-10-22.** 현재: [정본](../../spec.md).

이 문서는 단계 0–3에서 무엇을 선택했고, 다른 방법과 비교해 어떤 비용을 받아들였는지 정리한 기록이다. 사용자 확정, 위임받은 선택, 임시 선택, 조사·오류 수정 기록을 구분한다. 위임받아 구현했다는 사실이 사용자가 대안을 직접 비교해 확정했다는 뜻은 아니다. 이미 확정한 결정을 일괄 재승인할 필요는 없으며, 아래 요약표와 각 항목의 비교를 보고 바꾸고 싶은 선택을 검토하면 된다. 목표물 공격의 포지션별 지표는 2026-10-24 사용자가 D24에서 최종 확정했다.

**2026-10-25 편집 보완:** 공통 동작 설명과 최신 상태 요약은 정본 링크로 정리했다. 아래 결정 주체·이유·대안·당시 검증 수치와 한계는 원래 날짜의 기록이다. 현재 작업은 [상태 정본](../../status.md), 적용할 규칙은 [제품 명세](../../spec.md)와 [수집·API 계약](../../contracts/api.md)을 따른다. 현재 링크의 내용이 당시 값과 같다는 뜻은 아니다.

**읽는 방법**

- 현재 범위는 D22, 최신 피해량 조사는 D23, 사용자가 확정한 목표물 공격 지표는 D24를 먼저 읽는다. D01–D21은 개발 경위를 설명한다.
- 각 항목의 분류·정본 링크·대안 비교에서 결정 이유와 사용자 영향을 확인한다. 당시 설정·검증 수치·변경 비용은 접힌 상세 기록을 펼쳐 읽는다.
- 상세 기록의 ‘현재’, ‘미완료’, ‘보류’는 그 항목을 작성했을 당시의 상태다. 이후 바뀐 범위와 판정은 D22·D23·D24를 함께 확인한다. 작업에서 제외했다는 사실을 실제 검증 성공으로 해석하지 않는다.
- **2026-10-24 보완:** 분류와 대안 비교를 추가했다. 비교표의 ‘현재’는 기존 기록의 선택이고, ‘이전 안’은 기존 계획에서 확인한 안이다. 그 밖의 대안과 장단점은 이번에 보완한 검토이며, 당시 실제로 검토·기각했다는 주장이 아니다. 기존 결정·검증 수치·미확인 범위·D번호와 제목은 유지한다.
- **2026-10-24 이후 사용자 확정:** 위 가독성 보완 뒤 사용자가 현재 목표물 공격 지표를 최종 채택했다. D24에 별도로 기록하고, D04·D19·D23의 현재 상태 안내를 갱신했다. 당시 상세 기록은 보존한다.
- 대안 비교는 설계상의 차이를 설명한다. 별도 표기가 없으면 대안 구현이나 성능 비교 실험은 수행하지 않았다. 기존 테스트 통과를 대안보다 우수하다는 증거로 사용하지 않는다.

## D01 — HOLD 중 단계 1–3의 조건부 draft 개발

**대안 비교 — 2026-10-24 보완:** 실제 환경 접근이 막혔을 때, 개발 시간과 추후 수정 비용 중 무엇을 우선할지의 선택이다.

| 선택지 | 장점 | 비용·제약 |

## D02 — 공개 후보와 검증 완료 fixture 분리

**분류·상태:** 위임 선택. 공개할 자료의 범위와 ‘후보’ 표시를 정했으며, 전체 검증 완료 판정은 아니다.

- **사용자 영향:** 서버와 수집 앱을 같은 경기 자료로 반복 검사할 수 있다. 실제 계정명·원본·화면·가명 대응표는 공개하지 않는다. 합성 시각으로 실제 반영 시간을 측정하거나, 이 자료를 공개 서비스의 데모 경기로 사용하지 않는다.

## D03 — 실측 범위에 한정한 엄격한 정규화 초안

**분류·상태:** 필수 자료 검사 방식은 위임 선택이며, 관찰한 경기 형식에 한정한 지원 범위는 임시다.

적용 기준: [관련 정본](../../contracts/api.md#lcu-원본을-정규화하는-규칙). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 필수 통계가 빠지거나 팀 구성·승패가 맞지 않으면 자료를 거절할 수 있다. 확인한 경기 형식부터 지원하고, 최종 포지션은 사람이 확인한다. 경기 ID는 문자열로 보존하며, 이름이나 배열 순서로 사람을 연결하지 않는다. LCU와 공식 API의 계정 식별값도 별도로 다룬다. 필요한 값이 정상이라면 응답에 추가 항목이 있다는 이유만으로 거절하지 않는다.

**대안 비교 — 2026-10-24 보완:** 불완전한 자료를 점수 계산에 넣지 않으면서 어디까지 받아 보관할지의 선택이다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 필수 값·참가자 연결이 틀리면 정규화 거절 — 현재 | 잘못된 자료를 정상 경기로 등록하는 일을 막기 쉽다. | 일부 통계만 빠진 경기라도 정상 등록할 수 없다. |
| 불완전 자료를 별도 상태로 보관하고 등록·평가 차단 | 원인을 조사하거나 나중에 재처리하기 좋다. | 별도 상태·보관 정책·복구 화면이 필요하다. |
| 누락 지표를 제외한 제한 기능만 제공 | 확인된 경기 정보 일부를 볼 수 있다. | 비교 가능한 점수와 불완전 기록을 구분하는 별도 제품 규칙이 필요하다. |

- **선택 근거·감수한 비용:** 통계를 추측해 채우지 않는 정확성을 우선했다. 실제 0과 누락은 구분한다. 추가 필드까지 모두 거절하는 정책은 아니다.
- **근거·재검토 조건:** 당시 검사 도구의 오류 입력 검증은 아래에 있다. 실제 누락 사례가 반복되면 별도 보관 방식을 검토할 수 있지만, 누락을 0으로 바꾸거나 미확인 형식을 자동 지원하지 않는다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: [후보 계약](../../validation/lcu-candidate-contract.md)의 타입·필수 필드·문자열 ID·0/누락 구분·참가자/팀 join을 T01 권고 입력으로 사용한다. observed queueId=3130을 draft 지원 조합으로 제한하되 다른 큐도 동일 의미라고 추정하지 않는다. 역할은 명시적 확인, LCU와 공식 API PUUID는 별도 네임스페이스다.

</details>

## D08 — 단계 1의 작은 규모 트랜잭션 직렬화

**분류·상태:** 위임 선택. 공통 상태 행의 비관적 쓰기 잠금으로 변경 요청을 조율하도록 구현했다. 사용자가 대안별 성능까지 비교해 확정한 기록은 아니다.

적용 기준: [관련 정본](../../contracts/api.md#계산-규칙-검증게시복구). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 여러 변경 요청이 겹치면 순서대로 기다릴 수 있다. 일반 조회는 이 잠금으로 막지 않으며, 새 경기의 임시 저장만으로는 재계산을 요청하지 않는다. 사용량이 늘면 잠금 범위를 나누는 방식으로 바꿀 수 있다.

**대안 비교 — 2026-10-24 보완:** 같은 경기 중복 등록·인증 코드 중복 사용을 막고, 경기 변경·변경 번호·재계산 작업이 함께 저장되어야 한다. 기법뿐 아니라 함께 조율할 대상의 범위가 판단 기준이다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 공통 상태 행의 비관적 락 — 현재 | 먼저 잠금을 얻은 요청이 처리하므로 여러 종류의 변경 규칙을 한 경계에서 설명하기 쉽다. | 서로 다른 경기·인증 작업도 대기한다. 긴 변경 작업 하나가 다른 변경을 늦춘다. |
| 경기·코드별 비관적 락 | 서로 다른 대상은 동시에 처리할 수 있다. | 여러 대상의 잠금 순서, 최초 삽입 경합, 공통 변경 번호·재계산 작업의 조율을 별도로 설계해야 한다. |
| 버전 검사에 의한 낙관적 락 | 읽고 처리한 뒤 저장할 때 변경 충돌을 확인한다. | 충돌하면 트랜잭션을 취소하고 재시도하거나 충돌을 알린다. 공통 행 하나를 검사하면 충돌 범위는 여전히 넓다. |
| 조건부 원자적 UPDATE·충돌 처리 INSERT | ‘미사용 코드만 사용 처리’처럼 조건 확인과 변경을 DB 명령 하나로 묶기 좋다. | 변경된 행 수와 중복 요청 결과를 처리해야 한다. 여러 테이블의 변경을 함께 저장하는 트랜잭션은 여전히 필요하다. |

낙관적 락은 보통 버전을 조건으로 한 UPDATE를 사용하므로 마지막 두 방식은 겹칠 수 있다. 대상별 잠금과 조건부 갱신을 함께 쓸 수도 있다. 원자적 UPDATE도 같은 행을 바꾸면 잠금을 기다릴 수 있다. 공통 상태 행의 잠금을 공통 행 UPDATE로 바꾸기만 해서는 대기 범위를 줄이지 못한다. [JPA의 버전 검사·낙관적 락](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html#_optimistic_locking), [PostgreSQL의 UPDATE 동시 처리](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

- **선택 근거·감수한 비용:** 기록된 근거는 약 30명 규모에서 조율·복구 규칙을 단순하게 유지한다는 것이다. 다른 방식도 일관성을 보장하도록 설계할 수 있으며, 현재 선택이 유일하게 정확한 방식이라는 뜻은 아니다.
- **근거·미확인:** [공통 잠금·변경 번호·작업 저장 구현](../../../apps/server/src/main/java/cw/db/MutationCoordinator.java)과 [단계 1 검증 보고서](../../validation/stage1-report.md)에 구현·동시 요청 검사의 근거가 있다. 이 기록에는 실제 운영의 잠금 대기 시간·충돌률이나 대안별 처리량 비교가 없다. 인원수만으로 성능이 입증되지는 않는다.
- **재검토 조건·변경 영향:** 관계없는 요청의 대기나 긴 트랜잭션이 실제 문제로 확인되면 범위를 나눈다. 변경 시 중복 등록·동시 코드 소비·작업 저장 실패의 전체 취소 검사를 유지하고 확장해야 한다. 수치로 된 대기 허용 기준은 아직 정하지 않았다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: 모든 데이터 mutation은 singleton `service_state` 행의 pessimistic write lock을 먼저 획득한다. DB `(platform_id,game_id)` UNIQUE를 함께 유지하고 읽기는 잠그지 않는다. 신규 임시 저장은 revision을 올리지 않으며 실제 확정/정정/취소/회원 팀 입력 변경만 revision과 durable job을 함께 저장한다.
- 이유: 30명 규모에서는 한 트랜잭션 경계가 명확하며 중복·확정·코드 소비·복구 경합의 결과가 결정적이다. 별도 브로커와 분산 락이 필요 없다.
- 되돌리기 비용: 요청량이 증가하면 행별 잠금/원자 upsert로 분리하고 동시성 회귀 테스트를 확장한다. 현재에는 mutation 처리량이 한 DB 트랜잭션씩 제한된다.

</details>

## D09 — 보존·마이그레이션·후속 평가 경계

**분류·상태:** 위임 선택. 원본과 정규화 자료의 분리 저장·저장 구조 변경 절차를 정했다. 평가 구현은 이후 D19로 이어졌다.

적용 기준: [관련 정본](../../spec.md#원본계약호환성). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 저장 오류로 경기만 등록되고 관련 이력이 빠지는 등의 불완전한 상태를 막는다. 여기서 원본 보존은 JSON 값의 보존이며, 공백과 숫자의 표기 모양까지 동일하게 복사한다는 뜻은 아니다. 이 기록 당시 후속 작업으로 남긴 점수 재계산 구현은 D19에서 이어진다.

**대안 비교 — 2026-10-24 보완:** 원본 재처리를 가능하게 하면서 DB 내부 JSON 검색을 얼마나 지원할지 비교한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 원본·정규화 JSON을 별도 text로, 검색 항목은 관계형 열로 저장 — 현재 | 앱의 숫자 보존 규칙으로 재처리하고 일반 SQL로 검색한다. | JSON 형식 검사를 앱이 맡는다. 원본 내부 검색에는 별도 처리가 필요하다. |
| 원본·정규화를 DB의 json 또는 jsonb 타입으로 저장 | DB의 JSON 형식 검증과 연산을 사용할 수 있고, jsonb는 검색 인덱스를 지원한다. | json과 jsonb의 보존·숫자 허용 범위가 다르므로 이관 전 확인이 필요하다. 타입 선택만으로 앱 파싱의 정밀도 손실은 막지 못한다. |
| 원본 text를 유지하고 검색용 jsonb 사본 추가 | 원본 보존과 JSON 내부 검색을 함께 지원한다. | 중복 저장·인덱스와 사본 갱신 비용이 생긴다. |

- **선택 근거·감수한 비용:** 현재 검색은 참가자 열로 가능하므로 원본 검색 인덱스보다 보존·재처리의 단순성을 우선했다. text 저장 자체가 숫자 보존을 보장하는 것은 아니며 D13의 파싱 수정도 필요했다. [PostgreSQL JSON 타입의 차이](https://www.postgresql.org/docs/18/datatype-json.html)
- **근거·재검토 조건:** 아래에 원본 값 보존과 실제 DB 저장 실패 시 전체 취소 검사 결과가 있다. 원본 내부를 반복 검색할 필요가 생기면 JSON 타입·검색 사본을 검토한다. 이관은 새 DB 변경 파일로 수행하고 기존 원본을 보존한다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: raw JSON과 정규화 JSON은 별도 `text` 열로 저장하고 JPA participant 행에는 회원/팀/챔피언/승패/최종 역할을 둔다. 원본은 추가 필드를 보존하되 중복 JSON 키는 거절한다. Flyway 표준 이름 `V1__core.sql`을 사용하며 이후 단계는 V2 이상 migration을 추가한다. `service_state`와 durable `recalculation_jobs`를 먼저 만들고 평가 세대/점수/참고 표본 테이블은 T08–T12에서 추가한다.
- 이유·검증: JSON 파싱이 큰 정수 토큰을 lossless 보존하며 30자리 ID 문자열과 원본 수치를 훼손하지 않는다. SQL 검색은 필요한 participant 열과 Specification EXISTS를 사용하므로 raw JSON 검색 인덱스가 필요 없다. 전체 원문 바이트/공백이 아니라 JSON 값의 보존이다. JUnit 실제 PostgreSQL 테스트에서 ingest/confirm 중 audit/job 실패를 주입해 전체 rollback을 확인했다.
- 되돌리기 비용: JSONB가 필요해지면 새 migration에서 캐스팅하고 기존 raw 보존 정책을 유지한다. job/세대 테이블 확장은 기존 revision 의미를 지켜야 한다. 아직 평가가 없어 공개 DTO는 계산 중으로만 표시한다.

</details>

## D10 — 인증과 HTTP 기본값의 명시적 운영 한계

**분류·상태:** 운영자 한 명·친구 모임의 기존 범위 안에서 인증과 제한 방식을 정한 위임 선택. 실제 배포 접속 경로 확인은 남아 있다.

적용 기준: [관련 정본](../../contracts/api.md#인증과-권한). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 운영자 인증과 복구 절차를 제공한다. 실패 횟수 제한은 서버를 재시작하면 초기화되며, 접속 중계 서버 뒤에서는 여러 사용자가 같은 IP로 보일 수 있다. 운영 접속 경로와 중계 서버 설정은 서버 배포 작업(T14)에서 확인해야 한다.

**대안 비교 — 2026-10-24 보완:** 작은 모임의 관리 부담과 운영 확장 시 비용을 비교한다. 인증 방식과 요청 제한 저장소는 별도 선택이다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 발급 코드·서버 세션과 쿠키 — 현재 인증 | 외부 로그인 서비스 없이 등록·폐기·로컬 복구를 운영한다. | 코드 전달·세션 수명·복구 절차를 직접 관리해야 한다. |
| 아이디·비밀번호 계정 | 사용자에게 익숙한 반복 로그인 방식이다. | 비밀번호 보호·변경·분실 복구를 추가로 구현·운영해야 한다. |
| 외부 계정 로그인 연동 | 외부 계정으로 로그인하고 인증 기능 일부를 맡길 수 있다. | 외부 서비스·등록 설정에 의존하며 모임 회원 권한과의 연결은 여전히 필요하다. |
| 메모리의 인증 실패 횟수 제한 — 현재 제한 | 별도 저장소 없이 단일 서버에서 관리한다. | 재시작 때 초기화되고 여러 서버에서 합산되지 않는다. |
| DB·공유 저장소의 실패 횟수 제한 | 재시작·여러 서버에 걸쳐 제한 상태를 공유할 수 있다. | 저장·만료·장애 처리와 추가 요청 비용이 생긴다. |

- **선택 근거·감수한 비용:** 별도 로그인 제품과 공유 제한 저장소의 운영 부담을 줄였다. 그 대신 코드 관리와 재시작 시 제한 초기화를 받아들였다. 제한된 횟수나 HTTPS 사용은 외부 접속 설정 검증을 대신하지 않는다.
- **근거·재검토 조건:** 아래는 코드 소비·쿠키·HTTP 경계의 검사 기록이다. 여러 운영자·다중 서버가 필요하거나 제한 초기화가 문제가 되면 변경을 검토한다. 접속 중계 서버 설정은 T14에서 확인한다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: 고엔트로피 코드/토큰의 SHA-256만 DB 보관, 관리자 쿠키와 동일 origin+CSRF, 1 MiB write body cap, 직접 remote IP의 bounded 메모리 인증 실패 제한을 사용한다. 기본은 Secure `__Host-cw-admin`; dev/test profile과 명시 설정이 함께 있을 때만 HTTP `cw-admin-dev`를 쓴다. CSRF는 인증된 `GET /api/admin/session`에서 재확보한다. forwarded 헤더는 기본 비신뢰다.
- 이유·검증: 추가 로그인 제품 없이 한 운영자/친구 모임 모델에 맞는다. 동시 코드 소비 양 scope, 만료/폐기/계정 불일치, 실제 chunked HTTP, 쿠키 플래그, 코드/계정 로그 비노출, 실제 실행 JAR 복구를 검사했다. 로컬 복구는 웹 리스너 없이 종료하고 새 코드 1회 출력만 한다.
- 되돌리기 비용: 분산 인스턴스나 운영 proxy를 도입하면 중앙 rate-limit/신뢰 proxy 설정을 바꾸고 HTTP 보안 테스트를 재실행한다. 현재 limiter는 재시작 시 초기화되고 proxy 뒤 사용자가 같은 remote IP로 묶일 수 있으므로 T14에서 고정된 proxy 범위를 설정해야 한다.

</details>

## D11 — v1 소비자 계약과 안정적 조회

**분류·상태:** 위임 선택. 서로 다른 언어의 계약 검사와 공개 목록의 조회 방식을 구현했다.

적용 기준: [관련 정본](../../contracts/api.md#공개-기록과-관리자-정정). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 공개 응답에 계정 식별값·원본 자료·인증 정보를 넣지 않는다. 페이지를 넘기는 동안 수정되거나 취소된 경기는 최신 상태를 따르므로, 전체 조회 시점이 고정되는 기능은 아니다. 회원의 허용 포지션 목록에서 순서만 바꾼 경우에는 불필요한 재계산을 만들지 않는다.

**대안 비교 — 2026-10-24 보완:** 계약 관리와 목록 탐색은 별도 선택이며 조합할 수 있다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 각 언어 구현 + 공통 문서·독립 기대값 검사 — 현재 계약 | 한쪽 구현의 오류를 다른 쪽과 대조하기 좋다. | 자료형·문서·검사 예제를 함께 갱신해야 한다. |
| 공통 API 정의에서 자료형·클라이언트 생성 | 반복 작성과 일부 형식 불일치를 줄인다. | 생성기 관리가 필요하며 실제 응답·업무 규칙 검사는 남는다. |
| 마지막 경기 시각·키 다음부터 조회 — 현재 목록 | 동일 시각 경기의 순서를 정하고 다음 목록을 이어 본다. | 페이지 번호로 바로 이동하기 어렵고, 페이지 간 변경·취소는 최신 상태를 따른다. |
| 페이지 번호·건너뛸 개수로 조회 | 원하는 페이지 번호를 지정하기 쉽다. | 앞쪽 자료가 바뀌면 페이지 경계가 달라지고 큰 건너뛰기는 비용이 늘 수 있다. |
| 조회 시점의 목록을 고정해 탐색 | 순회하는 동안 동일한 목록을 유지할 수 있다. | 목록 버전의 보관·수명·취소 자료 공개 규칙을 추가로 정해야 한다. |

- **선택 근거·감수한 비용:** 독립 검증과 최신 공개 상태를 우선했다. 현재 커서는 전체 조회 시점을 고정하는 기능이 아니다. [PostgreSQL의 정렬·OFFSET 제약](https://www.postgresql.org/docs/18/queries-limit.html)
- **근거·재검토 조건:** 아래에 같은 시각·여러 참가자 조건의 중복·누락 검사가 있다. 페이지 직접 이동이나 고정 목록 내보내기가 필요하면 별도 조회 계약을 검토한다. 계약 변경 시 모든 소비자를 함께 갱신한다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: 계약은 `docs/contracts/stage1-api.md`, JSON Schema `$defs`, Java records, 별도 독립 매핑 G1–G3 expected JSON으로 제공한다. 평가/팀 모델은 T08–T12 handoff 타입이며 stage 1에서 점수 계산을 수행하지 않는다. 공개 페이지는 `(startedAt,matchKey)` 내림차순 keyset cursor와 한 참가자에 대한 correlated EXISTS Specification을 사용한다. 내부 pending 큐는 소규모 전체 배열이다.
- 이유·검증: 서버 Java와 수집기 TypeScript의 구현을 공유하지 않고도 wire-format을 대조한다. 공개 DTO에서 PUUID/raw/auth를 제외하며 같은 timestamp와 여러 matching participant에서도 중복/누락 없이 페이지를 순회한다. allowedRoles의 순서만 바뀐 요청은 의미 있는 변경이 아니므로 역할 순서를 정규화하여 audit/revision/job을 만들지 않는다.
- 되돌리기 비용: API를 변경하면 schemaVersion/문서/기대값과 모든 소비 테스트를 함께 바꾼다. 내부 큐가 커지면 public과 같은 cursor 계약을 별도 버전으로 추가한다. cursor는 페이지 간 DB snapshot을 고정하지 않으며 새로 수정/취소된 자료는 최신 공개 상태를 따른다.

</details>

## D12 — 재현 빌드와 CI 범위

**분류·상태:** 빌드·자동 검사 구성은 위임 선택이고, 성공 여부는 당시 커밋과 실행 환경에 한정한 검증 기록이다.

적용 기준: [관련 정본](../../development/setup.md). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 로컬 검사 성공과 GitHub 자동 검사 성공을 별도로 확인한다. 특정 커밋의 성공을 이후 수정까지 검증한 결과로 사용하지 않는다. 운영 배포와 운영용 Java 업데이트 확인은 별도 작업으로 남긴다.

**대안 비교 — 2026-10-24 보완:** 빌드 재현성, 갱신 부담, 실제 DB 차이 발견 가능성을 비교한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 버전·해시 고정 + 실제 PostgreSQL 자동 검사 — 현재 | 입력을 추적하고 실제 저장·잠금 동작을 검사한다. | 업데이트를 명시적으로 반영하고 DB 실행 시간·환경을 관리한다. |
| 버전 범위를 허용하고 실행 때 새 의존성 선택 | 새 패치를 반영하는 고정 파일 수정이 줄어든다. | 동일 커밋의 실행 결과가 달라질 수 있어 별도 갱신 통제가 필요하다. |
| 빠른 단위 검사와 실제 DB 검사를 다른 주기로 실행 | 자주 실행하는 검사의 대기 시간을 줄일 수 있다. | 실제 DB 검사 전에 병합하면 DB 관련 오류 발견이 늦어진다. |

- **선택 근거·감수한 비용:** 재현성과 실제 저장 동작 확인을 우선했다. 가벼운 검사는 함께 추가할 수 있지만 실제 DB 검사와 같은 근거로 취급하지 않는다.
- **근거·재검토 조건:** 아래 성공은 당시 로컬 실행 기록이며 원격 자동 검사와 구분한다. 검사 시간이 실제 개발을 지연시키면 실행 분리를 검토하되, 어느 시점에 실제 DB 결과를 요구할지 명시해야 한다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

## 단계 1 마지막 검토 보완

## D13 — 독립 리뷰의 JSON 계약 결함 수정

**분류·상태:** 오류 수정. 기존의 문자열 포지션 계약과 원본 수치 보존 요구를 복원했으며 새로운 평가 정책을 정한 항목은 아니다.

적용 기준: [관련 정본](../../contracts/api.md#공통-형식과-오류). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 잘못된 숫자 포지션 요청은 거절하고, 원본 소수의 수치값을 보존한다. 이미 정밀도를 잃고 저장된 값은 자동 복원하지 못하므로 보관한 원본에서 다시 가져와야 한다. 수정된 커밋의 자동 검사 결과도 따로 확인해야 한다.

**판단 범위 — 2026-10-24 보완:** 숫자 포지션 허용과 원본 소수 손실은 기존 요구에 어긋나는 오류이므로, 그대로 둘 것을 동등한 제품 대안으로 제시하지 않는다. 수정 방식의 세부 구현보다 계약 복원 여부와 이미 저장된 자료의 영향을 확인한다.

- **근거·한계:** 아래 기록에는 오류 재현, 수정 후 HTTP·실제 DB 검사, 평가용 소수 타입 유지의 근거가 있다. 이미 잃은 정밀도를 복원했다는 근거는 없다.
- **재검토 조건·변경 영향:** JSON 처리 도구나 설정을 바꾸면 같은 회귀 검사를 유지한다. 계약 자체를 바꾸려면 D03·D09·D11과 소비 앱의 영향을 별도 결정하며, 이 오류 수정의 승인으로 대신하지 않는다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 발견·권한: 별도 리뷰 dispatch가 `727e2e0`의 실제 코드와 PostgreSQL 테스트를 검토하고 P2 두 건을 재현했다. 숫자 역할 0–4가 enum 순번으로 변환되어 확정/정정에 사용됐고, 추가 raw JSON의 고정밀 소수는 저장 전에 double로 반올림됐다. 코디네이터는 리뷰 종료 후 새 구현 dispatch로 두 수정을 승인했다. 조건부 draft·`objective-provisional-v1`은 승인된 결정이며 단계 0 HOLD는 유지한다.
- 결정: Jackson 3의 `EnumFeature.FAIL_ON_NUMBERS_FOR_ENUMS`와 `DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS`를 활성화한다. 역할 계약은 문자열만 받고 raw JSON tree는 임의 정밀도 소수의 수치값을 보존한다. 명시적으로 선언된 평가 `double`/`Double` 필드는 기존 타입을 유지한다. 원문 공백·소수 표기 형식 자체 보존이나 기존 저장값의 복원은 주장하지 않는다.
- 검증: 먼저 HTTP/실DB 회귀 5개를 추가해 숫자 역할 확정·정정의 200 응답과 raw 소수 손실로 정확히 3개 실패를 확인했다. 수정 후 5개 모두 통과했고, 거절 후 상태/역할/audit/revision/job 불변·정상 문자열 역할 처리·중첩 소수 저장/관리자 조회·큰 정수 ID·필수 통계의 소수 토큰 거절·평가 double 호환성을 검사했다. 관리자 정정 audit 실패와 취소 job 실패의 rollback 테스트 2개도 추가했다. 전체 재실행은 서버 **70/70**, Node **31/31**, skipped 0이다.
- CI 경계: 코디네이터가 이전 HEAD `727e2e0`의 Ubuntu 실PostgreSQL [CI 성공](https://github.com/SangHyeok0908/Civil-War/actions/runs/39643558919)을 확인했다. 이번 수정 커밋은 코디네이터 push 후 별도 CI 결과를 확인해야 하며, 이전 성공을 새 커밋 검증으로 대체하지 않는다.
- 되돌리기 비용: mapper 설정과 회귀 테스트를 함께 검토하면 된다. migration/API 버전/fixture 수정은 없다. 이미 정밀도를 잃은 raw 자료가 있다면 보존된 원본에서 재수집해야 하며 자동 복구하지 않는다. [리뷰 결과와 최종 검증](../../validation/stage1-report.md#independent-review-and-resolution)에 상세를 남긴다.

</details>

## D15 — 인증·LCU·렌더러 경계

**분류·상태:** 권한 분리·인증 정보 보관에 대한 위임 선택과 검증 기록. Windows 보호 저장의 실제 확인은 남아 있다.

적용 기준: [관련 정본](../../spec.md#인증과-개인정보). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 암호화에 실패해도 인증 정보를 평문으로 저장하는 방식으로 바꾸지 않는다. Windows 보호 기능의 실제 동작은 별도 확인이 남아 있다. 이 보호 기능만으로 같은 Windows 사용자 권한의 악성 프로그램까지 막을 수 있다고 보장하지 않는다. macOS 검증은 예제 자료 모드로 제한했다.

**대안 비교 — 2026-10-24 보완:** 인증 정보를 보관하는 편의와 보호 범위, 권한 있는 처리 부분의 분리 비용을 비교한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 운영체제 기능으로 암호화해 별도 파일 저장 — 현재 | 재시작 후 등록을 이어 가며 화면에 토큰을 전달하지 않는다. | 복호화 실패 시 재등록이 필요하다. 같은 OS 사용자 권한의 악성 앱까지 막는 보장은 아니다. |
| 실행 중 메모리에만 인증 정보 보관 | 디스크에 인증 정보를 남기는 범위를 줄인다. | 앱 종료·재시작 때 재등록이 필요해 자동 재시도 흐름이 달라진다. |
| Windows 자격 증명 저장소에 직접 연동 | OS의 전용 저장소에서 인증 정보를 관리할 수 있다. | 별도 연동·배포·사용자별 복구 검증이 필요하며 이 대안은 구현하지 않았다. |
| LCU 연결을 별도 작업 프로세스로 추가 분리 | 연결 처리의 오류·지연을 분리하는 데 도움이 될 수 있다. | 프로세스 수명·통신·인증 전달을 추가 관리한다. 화면에 비밀값을 주지 않는 경계는 그대로 필요하다. |

- **선택 근거·감수한 비용:** 화면의 권한을 제한하고 재시작 편의를 유지하는 구성을 택했다. 보호 저장이 실패할 때 평문으로 전환하는 방식은 현재 보안 원칙을 충족하는 대안이 아니다. 전용 저장소 대안의 기능 범위는 [Windows 자격 증명 관리 안내](https://learn.microsoft.com/en-us/windows/win32/secauthn/credentials-management)를 참고한다.
- **근거·재검토 조건:** 아래 Electron 격리·허용 항목 검사와 공식 지침을 근거로 한다. 보호 저장 장애가 반복되거나 연결 처리 분리가 필요하면 보관·프로세스 구성을 검토한다. 실제 Windows 보호 범위 확인은 T13에서 이어 간다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: 기존 감사된 LCU transport를 재사용하며 매 요청마다 lockfile을 다시 읽는다. loopback HTTPS 한 요청에만 로컬 인증서 예외를 적용한다. main만 코드 교환과 Windows safeStorage 암복호화를 수행하고 토큰 전체를 암호화된 파일로 원자 교체한다. 보호 저장소를 사용할 수 없거나 복호화에 실패하면 재등록을 안내하며 평문으로 전환하지 않는다. preload는 제한된 기능만 노출하고 IPC 발신 창·정확한 local URL·top frame·payload를 검사한다.
- 이유·검증: renderer에는 safe account와 명시적 normalized DTO만 전달한다. contextIsolation/sandbox true, nodeIntegration false를 실제 Electron UI 테스트에서 확인했다. 원본 LCU·token·credentialId는 IPC snapshot에 없고 임의 raw/stat 쓰기 명령도 없다. 서버 DTO에 추가 raw/secret 필드가 있어도 allowlist decoder가 제거하는 테스트가 있다. [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security)과 [safeStorage의 OS별 범위](https://www.electronjs.org/docs/latest/api/safe-storage)를 확인했다. 실제 Windows DPAPI는 HOLD다.
- 되돌리기 비용: IPC 확장 때 command/DTO validator와 발신자 검증을 유지해야 한다. Linux/macOS 일반 사용은 허용하지 않고 macOS 검증은 fixture 모드만 사용한다. Windows DPAPI는 다른 사용자 보호이며 같은 사용자 권한의 악성 앱까지 차단하는 저장소라고 설명하지 않는다.

</details>

## D16 — 로컬 원본·소유자·순서 보존

**분류·상태:** 위임 선택. 전송 순서·인증 변경 시 재개·로컬 자료 보관 기간과 보호 범위를 정했다.

적용 기준: [관련 정본](../../spec.md#오프라인-대기와-재시도). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 첫 작업이 재시도를 기다리면 뒤의 다른 경기도 기다린다. 같은 회원이 새 인증으로 이어 보내는 경우에도 확인 후 명시적으로 재개한다. 미완료 자료는 자동 삭제하지 않으며, 정상 등록·전송을 마친 경기의 큰 자료만 30일 뒤 정리하고 상태와 변환한 기록은 남긴다. 경기 자료는 로컬 데이터베이스에 평문으로 저장되고 인증 정보는 별도 보호 파일에 저장된다.

**대안 비교 — 2026-10-24 보완:** 전송 순서, 보관 기간, 자료 암호화는 서로 다른 선택이다. 전송 자료의 원래 소유자 확인은 어느 방식에서도 유지해야 한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 대기열 전체에서 먼저 들어온 작업부터 전송 — 현재 | 순서와 장애 원인을 설명하기 쉽다. | 첫 작업이 실패하면 관계없는 경기까지 기다린다. |
| 경기별 순서를 지키면서 서로 다른 경기는 병렬 전송 | 한 경기의 재시도가 다른 경기 전송을 덜 막는다. | 경기별 의존성·동시 실행 수·재시작 복구를 관리해야 한다. |
| 미완료 자료 유지, 완료 원본만 30일 후 정리 — 현재 보관 | 미전송 자료를 보존하고 최근 완료 문제도 조사할 수 있다. | 미완료 자료는 계속 쌓일 수 있고 완료 원본도 일정 기간 남는다. |
| 완료 원본을 즉시 정리하거나 더 오래 보관 | 즉시 정리는 저장량·자료 노출 범위를 줄이고, 장기 보관은 재조사 범위를 늘린다. | 전자는 조사·재처리 자료가 줄고 후자는 디스크·보호 부담이 늘어난다. |
| 경기 자료는 평문 DB, 인증 정보만 별도 보호 — 현재 보호 | 현재 DB로 조회·복구하기 쉽다. | 로컬 DB에 접근할 수 있으면 비공개 경기 자료를 읽을 수 있다. |
| 경기 DB·원본도 암호화 | 저장 매체에서 경기 자료를 읽는 일을 더 제한할 수 있다. | 별도 암호화 구성·키 보관·키 분실 시 복구를 설계해야 한다. |

- **선택 근거·감수한 비용:** 기록된 전송 순서의 근거는 진단·복구의 단순성이다. 30일 보관의 적정성이나 평문 DB와 암호화 DB의 비용을 비교한 측정은 이 기록에 없다. 보관 기간을 사용자 확정으로 확대하지 않는다.
- **근거·재검토 조건:** 아래에 재시작·응답 유실·계정 변경·순서 검사가 있다. 독립 경기의 대기가 불편하거나 로컬 저장량·자료 보호 요구가 달라지면 해당 축을 검토한다. 변경에는 DB 이관·기존 자료 해독·미완료 자료 보존 검사가 필요하다.


<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: SQLite WAL/FULL, transaction, schema version 1, immutable 원래 memberId/credentialId/puuid, kind/dependency 및 미완료 unique index를 사용한다. 원본 HTTP body 문자열을 별도로 보존하고 ingest envelope에 그대로 넣어 큰 정수와 추가 고정밀 소수를 반올림하지 않는다. 확인 역할과 초안은 재조회로 바꾸지 않으며 registered 표시에서는 서버 확정 역할을 우선한다.
- 결정: pending 작업은 엄격 FIFO다. 선두가 backoff 중이면 젊은 독립 경기 전송도 기다린다. 5초→15초→1분→5분→15분 및 최대 15분 이내 jitter, 429 Retry-After를 적용한다. permanent/auth/canceled는 확인 필요로 멈추며 canceled 화면은 등록 취소다. 같은 회원의 새 자격은 새 authenticated roster로 member/PUUID를 확인하고 명시적 재개를 눌러 별도 rotation 허용행을 만든다. 원래 actor 열을 바꾸지 않는다.
- 이유·검증: 파일 reopen/sending 복구, 두 종류 ACK 유실, 다른 회원/자격 차단, strict FIFO, concurrent drain, revoked/invalid/canceled, 기존 확인 역할 보존을 검사했다. 확인 전후 GET으로 상태를 확인하고 등록 상태가 확인되지 않으면 성공으로 처리하지 않는다. 최초로 로컬 ingest를 만드는 경우에도 이미 받은 server record를 덮어쓰지 않는다. 완료된 ingest tombstone은 이후 재조회에서 raw 재전송 대신 서버 GET 상태 갱신에 사용한다.
- 보관: 미완료 자료는 자동 삭제하지 않는다. registered + succeeded ingest의 큰 payload만 30일 뒤 정리하고 키·상태·normalized/역할을 남긴다. SQLite 자체에는 비공개 자료가 평문 저장되며 credential은 별도 보호 파일에만 있다.
- 되돌리기 비용: DB 변경은 forward migration과 기존 요청 decoder가 필요하다. strict FIFO는 한 네트워크 장애가 다른 전송을 지연시키지만 순서와 진단이 명확하다. 성공 tombstone 정책을 바꿀 때 서버 취소/기존 역할을 새 raw로 덮어쓰지 않는 회귀를 유지한다.

</details>

## D17 — 느린 서버·꺼진 League와 명시적 사용자 확인

**분류·상태:** 버튼 조회·명시적 등록은 기존 제품 원칙이다. 로컬 우선 초기화·명단 캐시와 기존 전송 복구 방식은 그 범위 안의 위임 선택이다.

적용 기준: [관련 정본](../../spec.md#경기-수집확인등록). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 서버가 느리거나 인터넷이 끊겨도 가능한 로컬 작업을 계속할 수 있다. 재시작 후에는 사용자가 이미 전송을 요청한 작업만 자동 재시도하며, 새 경기를 임의로 내전 등록하지 않는다. 명단이 오래됐을 수 있으므로 최종 등록 때 서버 검증은 유지한다.

**대안 비교 — 2026-10-24 보완:** 새 경기를 자동 등록하는 대안은 기존 원칙과 맞지 않는다. 서버가 느릴 때 앱이 어디까지 먼저 동작할지를 비교한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 로컬 자료·캐시 명단을 먼저 표시하고 원격 갱신 — 현재 | 서버 지연·오프라인에서도 저장 자료를 확인하고 가능한 작업을 한다. | 명단이 오래될 수 있어 서버의 최종 권한·등록 검증이 필요하다. |
| 온라인 명단 확인 후 기능 시작 | 시작 시 최신 명단을 기준으로 안내한다. | 서버가 느리거나 끊기면 로컬 자료 이용도 지연될 수 있다. |
| 창·저장 자료는 먼저 표시하되 새 편집은 원격 확인 후 허용 | 저장 자료 접근과 최신 명단에 의존하는 편집을 구분한다. | 온라인 확인 전 가능한 동작이 줄고 상태 안내가 복잡해진다. |

- **선택 근거·감수한 비용:** 앱 시작과 복구를 서버 응답에 묶지 않는 사용성을 우선하고 캐시의 오래됨을 받아들였다. 새 경기 조회와 이미 요청한 전송의 재시도는 구분한다.
- **근거·재검토 조건:** 아래에 미응답 서버·오프라인 수집·재시작 후 전송 검사가 있다. 오래된 명단 때문에 혼란이 생기면 안내·갱신 조건을 보완한다. League 실행을 기존 전송의 필수조건으로 바꾸려면 복구 동작의 변경 영향을 별도 판단한다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: local 초기화와 원격 초기화를 분리해 창 표시를 서버 timeout 뒤로 미루지 않는다. 최초 온라인 enrollment/roster 이후에는 캐시를 즉시 사용하고 roster refresh는 별도로 수행한다. LCU 새 기록은 버튼만 조회한다. 기존 저장 또는 서버 pending 경기의 명시적 확인·전송은 League가 꺼져 있어도 원래 인증 소유자로 가능하며, 알고 있는 다른 LCU 계정은 차단한다.
- 이유·검증: unresolved server promise 중에도 local snapshot과 실제 LCU fixture collection의 durable 저장이 가능하다. 재시작 전 명시적으로 큐에 넣은 confirm만 자동 재전송하며 새로운 confirm은 생성하지 않는다. 실제 Electron fixture UI에서 offline 수집→5+5/내전 확인→등록 대기→종료→재시작 후 ingest/confirm 순차 성공과 history 0건을 검사했다. 서버 pending은 LCU 목록에서 없어도 표시하며, 재조회가 외부 등록·취소를 갱신한다.
- 되돌리기 비용: 캐시는 서버 최신 명단보다 오래될 수 있으므로 서버의 최종 검증을 유지해야 한다. live LCU를 기존 전송의 필수조건으로 바꾸면 장애 복구 요구를 깨므로 제품 변경 승인이 필요하다.

</details>

## D18 — 솔로 참고 자료와 검증 범위의 정직한 handoff

**분류·상태:** 공식 API만 사용하는 기존 경로, 연동 전 ‘이용 불가’라는 임시 상태, 5분 이상 표본을 쓰는 위임 선택, 검증 범위 기록이 함께 있다.

적용 기준: [관련 정본](../../spec.md#초기-포지션-참고-자료). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 실제 공식 API 연동을 완료하기 전에는 수집 앱에서 참고 파일을 내보낼 수 없다. 5분 기준은 솔로 참고 자료에만 적용하며 내전 적격성이나 점수 기준으로 확대하지 않는다. 참고 자료로 주·부 포지션을 자동 변경하지 않는다. 실제 Windows 확인과 예제 자료 테스트도 구분한다.

**대안 비교 — 2026-10-24 보완:** 공식 경로 사용과 결과를 정직하게 표시하는 원칙은 유지한다. 참고 기능 제공 시점과 표본의 최소 길이를 비교한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 연동 전에는 사유와 함께 이용 불가 표시 — 현재 | 구현·검증하지 않은 수집 성공을 보여 주지 않는다. | 앱에서 솔로 참고 파일을 내보낼 수 없다. |
| 공식 API 연동까지 이번 범위에 추가 | 실제 참고 자료를 내보내는 흐름을 완성할 수 있다. | 키 운영·요청 제한·계정 연결과 실제 통합 검증 작업이 늘어난다. 접근 제한 해제가 선행되어야 한다. |
| 알려진 역할·조기 종료 아님·5분 이상 — 현재 표본 | 너무 짧은 참고 경기를 보수적으로 거른다. | 정상적인 짧은 경기도 제외할 수 있다. 5분이 최적이라는 비교 근거는 없다. |
| 역할·조기 종료만 검사하거나 다른 길이 기준 적용 | 사용할 표본을 늘리거나 더 엄격히 제한할 수 있다. | 짧은 경기의 편향과 표본 부족 사이에서 새 기준·설명이 필요하다. |

- **선택 근거·감수한 비용:** 연동을 가장하지 않는 상태 표시와 보수적인 초기 참고 표본을 택했다. 경로·실패 상태·표본 기준은 별도이며, 표본 길이를 바꿔도 내전 점수나 적격성 기준은 바뀌지 않는다.
- **근거·재검토 조건:** 아래는 변환 규칙과 예제 자료 검사의 근거다. C11에서 공식 API 조회는 성공했지만, 수집 앱의 실제 공식 API 내보내기는 미확인이다. 앱 연동이 가능해지거나 참고 표본의 부족·편향이 확인되면 해당 부분을 검토한다. D22에서 제외한 경기 검증을 다시 요구하지 않는다.

<details>
<summary>당시 결정과 검증 근거 펼치기</summary>

- 결정: C11에서 확인한 Account-v1→Match-v5를 유일한 솔로 참고 경로로 유지한다. 직접 HTTP가 차단된 기존 상태를 우회하거나 새로 재시도하지 않고 수집기 export는 `OFFICIAL_API_UNAVAILABLE`와 한국어 사유를 반환한다. 다른 플레이어 LCU 성공이나 참고 파일 생성을 가장하지 않는다. 순수 role-reference adapter는 queue420, 알려진 역할, 조기 종료 아님, 5분 이상 표본만 인정하고 LCU PUUID와 공식 PUUID를 분리한다. `RoleReferenceSample`은 기존 Java handoff의 puuid/source/gameId/playedAt/role/evidence 형태를 따른다.
- 이유·검증: 실제 키와 통합 경로가 없는 상태에서 데이터 생성보다 명시적 unavailable이 정확하다. 5분 기준은 초기 참고 표본을 보수적으로 거르는 선택이며 내전 적격성/점수 계산에는 적용하지 않는다. 정상 짧은 솔로 경기 일부를 제외할 수 있다. 표본으로 사용자 주·부 포지션을 자동 변경하지 않는다.

## D19 — 같은 세대의 불변 평가와 작업 시도 fencing

**분류·상태:** 재계산·결과 공개·작업 복구 방식은 위임 선택이다. 서로 다른 기준을 섞지 않는 것은 기존 평가 원칙이다. 목표물 공격 지표는 D24에서 사용자가 최종 확정했으며, 새 계산 버전 반영·검증은 후속 작업이다.

적용 기준: [관련 정본](../../spec.md#변경재계산일관성). 당시 선택과 근거는 아래 기록을 따른다.

- **사용자 영향:** 재계산 중에는 공개 집계를 ‘계산 중’으로 표시해 서로 다른 기준의 결과가 섞이지 않게 한다. 공개 점수에는 운영자 초기 실력값이나 솔로랭크 자료를 넣지 않는다. 화면 점수와 순위는 같은 소수 둘째 자리 반올림을 쓰고, 내부 누적에는 반올림 전 정밀도를 유지한다.

**대안 비교 — 2026-10-24 보완:** 계산 범위, 재계산 중 공개, 결과 저장, 작업자 수는 별도로 고를 수 있다. 어떤 조합이든 결과 버전 일치와 늦게 끝난 옛 작업의 덮어쓰기 방지는 유지해야 한다.

| 선택지 | 장점 | 비용·제약 |
| --- | --- | --- |
| 모든 유효 경기를 다시 계산 — 현재 계산 | 변경에 영향받는 표본을 빠뜨리지 않고 같은 규칙을 적용하기 쉽다. | 자료가 늘면 계산량이 커진다. |
| 영향받는 결과만 부분 재계산 | 변경 범위가 작으면 계산량을 줄일 수 있다. | 한 경기 변경이 다른 경기의 과거 비교 표본에도 영향을 주므로 의존 관계 추적이 복잡하다. |
| 재계산 중 공개 집계에 ‘계산 중’ 표시 — 현재 공개 | 오래된 결과를 최신 입력의 결과처럼 보여 주지 않는다. | 완료·복구 전까지 공개 점수·랭킹을 볼 수 없는 시간이 생긴다. |

| 한 계산 묶음을 JSON 하나로 저장 — 현재 저장 | 경기·누적·포지션 실력 결과를 같은 묶음으로 공개하기 쉽다. | 일부 결과만 DB에서 검색하거나 갱신하기 어렵고 묶음이 커진다. |

| DB에서 작업을 나눠 가져가는 여러 작업자 | 독립된 계산을 병렬로 처리할 수 있다. | 중복 실행·작업 소유권·재시도와 공개 순서를 더 관리해야 한다. |

- **선택 근거·감수한 비용:** 소규모 전체 재계산과 한 묶음 공개로 일관성·복구의 단순성을 우선했다. 현재 규모에서 장기적으로도 충분히 빠르다는 측정은 아니다. 입력을 같은 시점으로 읽는 것과 최종 공개 직전 변경 여부를 확인하는 것은 둘 다 필요하다. [PostgreSQL의 반복 읽기 보장 범위](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)
- **추가로 받아들인 표시 정책:** 화면과 순위는 같은 소수 둘째 자리 반올림을 쓰므로 표시가 같은 점수는 같은 순위로 다룬다. 내부 원정밀도로 순위를 나누는 대안은 가능하지만 화면상 같은 점수의 순위 차이를 설명하거나 표시 자릿수를 늘려야 한다. 누적 계산의 원정밀도 보존은 별개다.
- **근거·재검토 조건:** [단계 3 보고서](../../validation/stage3-report.md)와 아래에 입력 동시 변경·작업 중단·옛 시도 차단 검사 기록이 있다. 계산 지연·JSON 크기·공개 중단 시간이 문제가 되면 해당 축을 검토한다. 새 저장·실행 방식도 최종 공개 조건과 실패 복구 검사를 유지해야 한다.
